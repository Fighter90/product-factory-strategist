# Сравнение с обычным чатом: baseline против агента (демо «Связь для близких»)

> Один и тот же бриф руководителя — два ответа.
> **Baseline:** [baseline_svyaz.md](baseline_svyaz.md) — ответ обычного чата без инструментов и реестров,
> сгенерирован намеренно средним (без улучшений); запрос дословно из `projects/связь-для-близких-и-собственных-устройств/project.json`.
> **Агент:** [BRIEF_RESPONSE.md](../../projects/связь-для-близких-и-собственных-устройств/outputs/BRIEF_RESPONSE.md) —
> ответ 12-шагового прогона (бриф, выбор варианта и утверждение решения — с человеком; полный пакет — REPORT.md,
> six-pager RU/EN, Excel, дека). Предыдущее сравнение по демо-задаче «антиспам» (2026-11-12) — в истории git.

## Методика и границы

- Сравниваются **артефакты на один и тот же запрос**, а не модели: baseline — один ответ чата без инструментов,
  агент — прогон с реестрами источников и утверждений, red team-субагентом и pre-registration плана проверки.
- Baseline получил текст запроса руководителя (без учебной таблицы данных брифа) — как реальный руководитель
  присылает краткий запрос. Baseline — не соломенное чучело: это типовой сильный ответ по языку и структуре;
  его слабости системные (нет реестра, нет порогов, нет продолжения после решения), а не «плохо написано».
- Это демонстрация разницы процесса, не контролируемый эксперимент; синтетика (ИИ-респонденты S002–S003)
  в прогоне агента порождает только гипотезы, не доказательства спроса.

## Таблица измерений

| Критерий | Обычный чат (baseline) | Агент (BRIEF_RESPONSE.md) |
|---|---|---|
| Источники у чисел | **0** — числа без источников, вперемешку с придуманными («по разным оценкам», «конверсия в единицы процентов») | каждое число с тегом `[C###]`/`[S###]`; **26 документированных утверждений** в реестре `claims.jsonl` (10 факт · 8 допущение · 4 гипотеза · 4 вывода) |
| Факт/гипотеза разделены | **нет** — всё подано одинаково уверенным тоном | **да — 4 типа** (fact / assumption / hypothesis / inference); чекер не пускает факты на синтетику; «чего не знаем» — отдельный раздел ситуации |
| Вариантов решения | **1–2**, без возражений и без сравнения | **5 (A–E)**, включая «оставить как есть» и «закрыть услугу»; **red team — 20 ударов** (15 возражений + 5 скрытых допущений), встроены порогами в выбранный вариант |
| План проверки с порогами до данных | **нет** — общие слова («A/B-тест», «опросы») без порогов и базы сравнения | **да — pre-registration**: A/B 600 семейных групп (6 недель набора + 14 дней наблюдения, ITT), порог расширения −3 п.п., стоп-метрики (precision ≥80%, темп набора <50 групп/нед, повторные списания) — зафиксированы **до** сбора данных |
| Соответствие 5-частной структуре брифа | **частично** — тема раскрыта «по мотивам»: части 4–5 (польза с расчётом, план по кварталам с прогнозом, ресурсы, просьба) отсутствуют | **да** — Часть 1–5 ровно по требованию брифа, расчёты стоят рядом с решениями, которые обосновывают |
| Воспроизводимость расчётов | **нет** — числа воспроизвести нельзя | **да** — `analysis/economics.py` → `economics_out.txt`: сценарии +6,75/+4,5/+1,5/−1,5/−3,5 млн от базы 279 [C003,C021] |
| Продолжение после решения | **нет** — ответ заканчивается «могу детализировать» | **да** — **D001** в `decisions.jsonl`: основания C###, ответственный, метрики, пересмотр 2027-04-30, 4 обязательства; `pfs decision due` поднимает просроченное |

## Вывод: какой ценой

Разница не бесплатна — и это честная часть сравнения:

- **Время:** ~59 минут прогона агента против одного запроса обычному чату (минуты).
- **Участие человека:** **3 обязательные паузы** — бриф, выбор варианта, утверждение решения D001.
  Руководитель решает существенное сам; агент не подменяет его выбор.
- **Стоимость:** CLI-часть — **$0.00** (реестры, гейты, линтер комитета, Excel, экспорт — stdlib Python, 0 токенов);
  LLM-сессии зависят от тарифа среды (см. `docs/SUBMISSION.md` §8).

Что куплено за эти ~59 минут: числа проверяемы до первоисточника (тег → реестр → текст источника),
провал гипотезы виден заранее заданными порогами, а не по факту потраченного бюджета, расчёт повторяется
одной командой, и работа не исчезает после ответа — решение продолжает жить в реестре с обязательствами
и датой пересмотра. Обычный чат даёт текст; агент даёт текст плюс след, по которому можно проверить
каждое слово и вовремя пересмотреть решение.
