# Этап 4 — Заседание

**Вход:** `case.md` + `council_profiles.md` · **Выход:** `verdict.md`

## Оркестрация

Оригинал написан под OpenCode. Здесь:

| Этап | Механизм |
|---|---|
| Раунд 1 (независимые оценки) | **изолированные субагенты среды** (Agent tool в Claude Code, task/subagent в OpenCode), 5 параллельно, по одному на участника |
| Red Team | **отдельный субагент** после сбора раунда 1 |
| Разногласия, раунд 2, пересмотр, синтез | основная сессия — нужен общий контекст |

Каждому субагенту раунда 1 передать: общий бриф + `case.md` + **только его профиль**. ⛔ Не передавать позиции других участников.

Субагенты недоступны — выполни независимые оценки последовательно сам: анализируй каждого отдельно, **не используя выводы предыдущего**, зафиксируй все позиции, только потом сравнивай. Отсутствие мультиагентности — не причина не проводить совет.

⛔ **Не создавай** внешнюю инфраструктуру, Python/JS-обвязку, MCP-серверы, orchestration framework. Не проси API-ключи. Не перекладывай оркестрацию на пользователя.

## 1. Проверь входные файлы

`case.md`: решение · варианты · критерии · ограничения · факты · предположения · неизвестные · цена ошибки.
`council_profiles.md`: участники и оптика каждого.

Отсутствует несущественное поле — продолжай. Отсутствует сам предмет решения или непонятно, что сравнивается — сообщи о конкретной проблеме, но ⛔ **не начинай новый общий опрос**.

## 2. Общий бриф — одинаковый для всех

Решение · Альтернативы · Критерии · Ограничения · **Ключевые предположения** (3–10 с наибольшим влиянием) · **Критические неизвестные** (какие данные могут изменить решение).

## 3. Независимый первый раунд

Каждый участник возвращает:

| Поле | Формат |
|---|---|
| **Позиция** | поддерживает / скорее поддерживает / нейтрально — недостаточно данных / скорее против / против |
| **Главный вывод** | 2–5 предложений |
| **Сильные стороны решения** | максимум 5 |
| **Главные проблемы** | максимум 5 |
| **Какие предположения оспаривает** | конкретно |
| **Что кажется недоказанным** | конкретно |
| **Какие данные изменят позицию** | только decision-relevant |
| **Рекомендация** | конкретное действие |
| **Уверенность** | высокая / средняя / низкая + почему |

## 4. Собери результаты

Только после завершения **всех** независимых оценок. До этого участники не влияют друг на друга.

Сводная таблица: Участник | Позиция | Главный аргумент | Главный риск | Уверенность

## 5. Найди существенные разногласия

⛔ Различие в формулировках — не разногласие. Существенно только то, что **может изменить решение**.

Для каждого: **Вопрос** · **Позиция A** · **Позиция B** · **Причина расхождения** · **Тип**:
разные исходные предположения · разные оценки вероятности · разные критерии · разная цена ошибки · разные временные горизонты · разные представления о реализации · разные фактические основания.

Типизация важнее, чем просто «эксперты не согласны».

## 6. Второй раунд — критика

Покажи каждому: его первоначальную оценку · существенные аргументы других · список разногласий.

Попроси: с какими аргументами согласен · какие считает ошибочными · какие требуют данных · что заставило бы изменить позицию · изменился ли вывод.

⛔ Запрещено «Я согласен с Иваном». Нужно: **с каким аргументом · почему · что из этого следует**.

## 7. Red Team

Отдельный агент, **не представляет никого из совета**. Атакует решение, которое начинает выглядеть наиболее вероятным.

Проверяет:
- какое ключевое предположение может оказаться ложным
- какие данные неправильно интерпретированы
- что совет мог **коллективно** недооценить
- не возник ли groupthink
- не ориентируется ли совет на статус участников
- какую альтернативу недостаточно рассмотрели
- что произойдёт при неблагоприятном сценарии
- какой аргумент против текущего решения самый сильный

**Red Team должен пытаться изменить вывод. Не удалось — объясни почему.**

## 8. Финальный пересмотр

Таблица: Участник | Было | Стало | Что изменило позицию

Позиция не изменилась — нормально. ⛔ Не заставляй демонстрировать изменение ради видимости дискуссии.

## 9. Проверка предположений

Вернись к предположениям из `case.md`. Таблица: Предположение | Статус после совета | Основание | Риск ошибки | Как проверить

Статусы: подтверждено · скорее подтверждено · неизвестно · скорее опровергнуто · опровергнуто.
⛔ Не путай отсутствие подтверждения с опровержением.

## 10. Консенсус и разногласия — два раздела

**Где совет согласен** — только содержательные точки: тезис · основание · влияние на решение.

**Где не согласен** — вопрос · стороны · причина расхождения · может ли это изменить решение · какие данные нужны для разрешения.

⛔ **Не усредняй конфликтующие позиции.**

## 11. Синтез

Перестань моделировать участников. Перейди в роль **независимого модератора**.

> ⛔ **Итог не определяется голосованием.**
> Вес аргумента задают: качество доказательств · релевантность · влияние на решение · цена ошибки · обратимость · устойчивость к критике.
> **Известность участника не увеличивает вес его аргумента.**

Один итог: **ДА** · **НЕТ** · **ДА, ЕСЛИ** · **НЕТ, ПОКА** · **ВЫБРАТЬ ВАРИАНТ X** · **СНАЧАЛА ПРОВЕРИТЬ X**.

- Есть дешёвый эксперимент перед дорогим решением → предпочитай эксперимент
- Решение труднообратимое → требуй более сильных доказательств

## 12. Операционализация

Максимум **5** действий. Для каждого: **Действие** · **Какое предположение проверяет** · **Что измерить** · **Критерий**:

```
IF [наблюдаемый результат] THEN [как меняется решение]
```

Пример: `IF не менее 5 из 10 целевых клиентов готовы перейти к оплачиваемому пилоту, THEN предположение о коммерческом спросе усиливается.`

⛔ Не придумывай числовые пороги без основания. Точного порога нет — укажи, что его должен установить пользователь.

## Финальный ответ

**Вердикт** (решение · почему · главный риск · главное неизвестное · следующий шаг) → **Карта совета** → **Главные аргументы** (по убыванию влияния) → **Главные возражения** (сильнейшие против итога) → **Что изменилось после дискуссии** → **Где совет согласен** → **Где не согласен** → **Проверка предположений** → **Решение модератора** (рекомендация · почему · уверенность · что может сделать вывод ошибочным) → **Следующие действия** (≤5) → **Короткая карта решения**:

| Вопрос | Ответ |
|---|---|
| Что делать? | |
| Почему? | |
| Главный риск | |

## Не создавай театр

⛔ Плохо: «Безос: А я думаю…» · «Маск: Не согласен!»
✅ Хорошо: «Перспектива Безоса указывает на проблему X, поскольку…»

Моделируй профессиональную логику, а не личность.

## Не додумывай

Используй только: `case.md` · `council_profiles.md` · доступные материалы проекта · результаты анализа участников. Информации недостаточно — обозначь неопределённость. ⛔ **Не компенсируй отсутствие данных уверенной риторикой.**

## Главная проверка качества

Перед выдачей ответа четыре вопроса себе:

1. Совет реально **проверил** решение или просто красиво его обсудил?
2. Независимый первый раунд действительно был независимым?
3. Появился ли хотя бы **один сильный аргумент**, который мог изменить исход?
4. Понимает ли пользователь после ответа, **что конкретно делать дальше**?

Нет — исправь анализ до выдачи результата.
