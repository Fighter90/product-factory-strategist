# Дизайн решения

## Обязательные правила работы с внешними данными

**КРИТИЧЕСКИ ВАЖНО:** Любая информация из внешних источников должна быть верифицирована и снабжена ссылками.

### Когда искать в интернете

Используй веб-поиск (WebSearch/WebFetch) **обязательно** в следующих случаях:
- Оценка размеров рынка (TAM/SAM/SOM) — ищи актуальные отчёты аналитических агентств
- Данные о конкурентах — выручка, доли рынка, количество пользователей
- Бенчмарки метрик — средние значения Retention, Conversion Rate, NPS для конкретной индустрии и типа продукта
- Статистика рынка — темпы роста, тренды, прогнозы
- Примеры реальных кейсов — как конкретные компании решали аналогичные задачи

### Как верифицировать данные

1. **Ищи первоисточники** — отчёты Statista, McKinsey, CB Insights, SimilarWeb, Crunchbase, а не пересказы в блогах
2. **Проверяй дату** — данные должны быть не старше 2 лет. Если свежих данных нет, укажи дату источника
3. **Сравнивай минимум 2 источника** для ключевых цифр (размер рынка, доли)
4. **Если данных нет** — честно напиши «данные не найдены в открытых источниках» и дай свою оценку с пометкой «экспертная оценка»

### Формат цитирования

**Ссылки ставятся ПРЯМО НА цифрах и утверждениях — как гиперссылки в тексте, а НЕ списком внизу.**

Правильно:
- «A/B тесты показывают, что [персонализированный онбординг увеличивает конверсию на 30%](https://example.com/study)»
- «Компания X решила аналогичную проблему и [достигла retention 45%](https://example.com/case)»

Неправильно:
- Текст без ссылок с пометкой «Источник: ...» без URL
- Просто список ссылок в конце документа без привязки к конкретным утверждениям

Каждое число, факт или заявление из внешнего источника = гиперссылка на этом числе/факте.

### Что искать для конкретного типа продукта

Перед анализом сделай поисковые запросы по шаблонам:
- `"[тип продукта] market size [год]"` — для TAM/SAM/SOM
- `"[тип продукта] benchmark metrics"` — для бенчмарков метрик
- `"[тип продукта] retention rate benchmark"` — для retention
- `"[тип продукта] conversion rate industry average"` — для конверсий
- `"[конкурент] revenue users funding"` — для данных о конкурентах

Этот навык помогает перейти от проблемы к решению: сгенерировать гипотезы, оценить их и спланировать валидацию.

## Блок 1. Формулировка гипотез решений

### Формула гипотезы решения

> **Если [мы сделаем ___], то [пользователи смогут ___], что приведёт к [результату для бизнеса].**

Компоненты:
- **Мы сделаем** — конкретное действие (функция, сервис, изменение)
- **Пользователи смогут** — какую проблему/потребность решим
- **Результат для бизнеса** — какие метрики улучшим и как

**Пример:** Если мы добавим чат-бот для быстрых вопросов по заказу, то пользователи смогут решать вопросы без обращения в поддержку → ускорим ответы → вырастим конверсию в оформление заказа на X%.

### Чек-лист хорошей гипотезы (проверяй каждую)

1. **Есть явная связь с проблемой пользователя**
2. **Формулировка конкретна** — не «улучшим сервис», а «снизим время ожидания с 2 мин до 30 сек»
3. **Есть предположение о влиянии на пользователя**
4. **Есть ожидаемый бизнес-эффект**
5. **Проверяема** — можно измерить
6. **Содержит критерии успеха** — «увеличим клики на 10%»
7. **Одна идея = одна гипотеза**

## Блок 2. Методы генерации решений

- **Бенчмаркинг / конкурентный анализ** — как решают подобные проблемы другие
- **Брейншторминг** — генерация в кросс-функциональной команде
- **Customer co-design** — совместная генерация с пользователями

**Важно:** если проблема конкретная, не закапывай ресурс. Пример: нет Apple Pay → добавить Apple Pay.

## Блок 3. Приоритизация решений

**ICE = Impact × Confidence × Ease**

**RICE = (Reach × Impact × Confidence) / Effort**

### Источники для assumptions

| Источник | Что даёт |
|---------|---------|
| Аналитика | Конверсия воронки, retention, % с проблемой |
| Исследования | Реальные боли, частотность |
| Продажи/саппорт | Количество обращений |
| Бенчмарки | Данные конкурентов |
| Предыдущие эксперименты | Эффект похожих фичей |
| Экспертные оценки | Техзатраты, UX-сложность |

### Пример скоринга

| Гипотеза | Reach | Impact | Confidence | Effort | RICE |
|----------|-------|--------|-----------|--------|------|
| Гарантия возврата → конверсия +10% | 4 | 4 | 5 | 4 | 20 |
| Отзывы на продавцов → конверсия +10% | 3 | 4 | 3 | 3 | 12 |
| Бейдж «надёжный» → конверсия +5% | 2 | 3 | 3 | 2 | 9 |

## Блок 4. Оценка рисков

| Тип риска | Что проверяем | Пример |
|-----------|--------------|--------|
| **Value risk** | Не даст ценности | Push-уведомления → отключают как спам |
| **Usability risk** | Не смогут использовать | Сложные фильтры → конверсия падает |
| **Feasibility risk** | Дорого реализовать | AI-распознавание → дорогие серверы |
| **Business viability** | Не окупится | Бесплатная доставка → убытки |
| **Legal / репутационный** | Юридические последствия | Платные отзывы → клевета |

## Блок 5. Способы проверки

### Что проверить

1. Ценность (Value) — нужно ли?
2. Удобство (Usability) — могут ли пользоваться?
3. Бизнес-эффект (Viability) — принесёт ли выгоду?
4. Контр-метрики — не ломаем ли другое?

### Методы

| Что проверяем | Метод |
|--------------|-------|
| Ценность | Интервью, Fake Door Test, опрос / NPS / Conjoint |
| Удобство | Прототип Figma, Usability-тесты, A/B-тест |
| Бизнес-эффект | A/B-тест, когортный анализ |

### Полный чек-лист проверки

1. **Сформулировать гипотезу** — «Если мы ___, то ___». Есть критерий успеха.
2. **Определить что проверить** — ценность, удобство, бизнес-эффект, контр-метрики.
3. **Выбрать методы** — интервью, прототип, Fake Door, A/B-тест.
4. **Подготовить эксперимент** — аудитория, канал, материалы, критерии.
5. **Провести и оценить** — сравнить с критериями, зафиксировать инсайты, решить что дальше.

## Выходной артефакт

1. **Гипотезы решений** — по формуле с чек-листом
2. **Приоритизированный список** — по RICE/ICE
3. **Оценка рисков** — по 5 типам
4. **План валидации** — метод, аудитория, критерии успеха
