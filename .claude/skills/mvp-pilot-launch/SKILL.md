# MVP, пилот и запуск

## Обязательные правила работы с внешними данными

**КРИТИЧЕСКИ ВАЖНО:** Любая информация из внешних источников должна быть верифицирована и снабжена ссылками.

### Когда искать в интернете

Используй веб-поиск (WebSearch/WebFetch) **обязательно** в следующих случаях:
- Оценка размеров рынка (TAM/SAM/SOM) — ищи актуальные отчёты аналитических агентств
- Данные о конкурентах — выручка, доли рынка, количество пользователей
- Бенчмарки метрик — средние значения Retention, Conversion Rate, NPS для конкретной индустрии и типа продукта
- Статистика рынка — темпы роста, тренды, прогнозы
- Примеры реальных кейсов — как конкретные компании решали аналогичные задачи

### Как верифицировать данные

1. **Ищи первоисточники** — отчёты Statista, McKinsey, CB Insights, SimilarWeb, Crunchbase, а не пересказы в блогах
2. **Проверяй дату** — данные должны быть не старше 2 лет. Если свежих данных нет, укажи дату источника
3. **Сравнивай минимум 2 источника** для ключевых цифр (размер рынка, доли)
4. **Если данных нет** — честно напиши «данные не найдены в открытых источниках» и дай свою оценку с пометкой «экспертная оценка»

### Формат цитирования

**Ссылки ставятся ПРЯМО НА цифрах и утверждениях — как гиперссылки в тексте, а НЕ списком внизу.**

Правильно:
- «[74% стартапов](https://example.com/study) терпят неудачу из-за преждевременного масштабирования»
- «Средний срок запуска MVP в финтехе — [3-4 месяца](https://example.com/benchmark)»

Неправильно:
- Текст без ссылок с пометкой «Источник: ...» без URL
- Просто список ссылок в конце документа без привязки к конкретным утверждениям

Каждое число, факт или заявление из внешнего источника = гиперссылка на этом числе/факте.

### Что искать для конкретного типа продукта

Перед анализом сделай поисковые запросы по шаблонам:
- `"[тип продукта] market size [год]"` — для TAM/SAM/SOM
- `"[тип продукта] benchmark metrics"` — для бенчмарков метрик
- `"[тип продукта] retention rate benchmark"` — для retention
- `"[тип продукта] conversion rate industry average"` — для конверсий
- `"[конкурент] revenue users funding"` — для данных о конкурентах

Этот навык помогает спроектировать минимальную версию продукта, выбрать формат проверки и спланировать запуск.

## Блок 1. Пилот vs MVP vs MLP

### Определения

| Формат | Что это | Срок | Вовлечение | Ключевое отличие |
|--------|---------|------|-----------|-----------------|
| **Пилот** | Самый быстрый способ тестирования базовых гипотез с минимальными усилиями | ~1 месяц | Discovery + точечно delivery | Пользователь не знает, что находится в тесте |
| **MVP** | Минимальная жизнеспособная версия — рабочий продукт с вложенными ресурсами разработки | 2–4 месяца | Полная команда | Закрывает конкретную потребность тем же способом, что и итоговая версия |
| **MLP** | Минимальный привлекательный продукт | 3–6 месяцев | Полная команда | Не только базовый функционал, но и первичная польза и хороший UX |

### Когда что использовать

- **Пилот** — когда нужно проверить базовые предположения. Если база не выполняется, дальше разрабатывать не стоит
- **MVP** — когда базовые гипотезы подтверждены, нужно проверить ключевую ценность на реальных пользователях
- **MLP** — когда рынок конкурентный и «голый» MVP не привлечёт пользователей

### Примеры пилотов

- Рассылки
- Fake Door тесты
- Решенческие интервью
- Маркетинговые эксперименты

## Блок 2. Типы MVP

| Тип | Описание | Пример |
|-----|---------|--------|
| **Однофункциональный** | Готовый продукт с минимальным набором функций | WhatsApp 2009 — только статусы контактов, потом добавили сообщения |
| **Разрозненный** | Сложный продукт из готовых простых решений | Groupon — WordPress + PDF + email |
| **Предзаказ** | Продажа продукта до его создания | ОККО и заказ фильмов |
| **Консьерж** | Человек выполняет работу вручную, пользователь знает об этом | Поиск фрилансеров вручную |
| **Wizard of Oz** | Человек выполняет работу, но пользователь думает, что это автоматизация | Автоматизация брони столиков (на самом деле вручную) |
| **Чужой продукт** | Используем существующий продукт для проверки гипотезы | Электронный москвич |

## Блок 3. User Story Mapping

USM помогает определить, какой функционал должен войти в MVP.

### Как строить

1. Определи основной пользовательский сценарий (backbone)
2. Разложи на шаги пользователя (activities)
3. Под каждым шагом — конкретные задачи (tasks)
4. Проведи горизонтальную линию — всё выше линии = MVP
5. То, что ниже — следующие релизы

### Связь с прототипированием

Прототипирование помогает приоритизировать гипотезы и определить:
- Что критично для MVP
- В каком виде реализовать
- Какие фичи отложить

## Блок 4. JTBD для MVP

### Формула JTBD

> **Когда я [контекст], я хочу [мотивация], чтобы [результат].**

### User Story vs JTBD

| User Story | JTBD |
|-----------|------|
| Как модница Елена, я хочу купить платье в один клик, чтобы больше времени тратить на шопинг | Когда у меня 2 минуты перекусить между встречами, я хочу быстро и просто поесть, чтобы продержаться до обеда |
| Фокус на персоне и действии | Фокус на ситуации и мотивации |

## Блок 5. Цели продакта на этапе MVP

1. Максимизировать осведомлённость о проблемах и потребностях пользователей
2. Провести UX-исследования потенциального решения
3. Определить, какие фичи войдут в MVP, а какие позже
4. Определить сегмент и долю пользователей для тестирования
5. Определить сроки, метрики и критерии успеха
6. Проконтролировать создание MVP и его соответствие ТЗ
7. Создать роадмап дальнейшего развития
8. Решать проблемы по ходу MVP
9. Оцифровать и зафиксировать результаты
10. Принять решение о дальнейшем развитии

## Блок 6. Этапы создания MVP

1. **Описание проблемы** — что решает продукт, чего ожидает пользователь
2. **Определение сегмента ЦА** — для кого создаём
3. **Анализ конкурентов** — есть ли такие же решения, чем отстроиться
4. **Сбор потребностей** — USP, ключевые гипотезы, фичи
5. **CJM и User Story Mapping** — выбор основных функций MVP
6. **Разработка** — координация (планирование, дейли, грумминги, демо, ретро)
7. **Тестирование и доработки** — итерации на живых пользователях
8. **Принятие решения** — будущее продукта по результатам MVP

## Блок 7. Метрики и тестирование MVP

### Выбор метрик

- Ключевые input-метрики продукта из трекшн-модели + ожидания по ним
- Качественные контр-метрики (CSAT, NPS, CSI)

### Как тестировать

- Тестируется на **живых пользователях**
- Сегмент определён на первом этапе
- Чаще раскатывают **не на всех**, а на часть
- Держим тест до **статистической значимости**
- По результатам определяем вехи доработки

## Блок 8. Команда MVP

| Роль | Что делает |
|------|-----------|
| Дизайнер | Готовит макеты, тестирует прототип |
| Продакт | Контролирует процесс |
| Исследователь | Определяет скоуп, тестирует прототип |
| Редактор | Готовит тексты |
| Маркетолог / PMM | «Продаёт» продукт (если нужно) |
| Бизнес-лидер | Работа с внешними партнёрами |
| Аналитик | Дизайн эксперимента, анализ результатов |
| Тимлид + разработка | Реализация |
| Проджект | Контроль процессов и зависимостей |

## Блок 9. 13 типичных ошибок MVP (чек-лист)

1. Не закрывают ключевую потребность или плохо доносят USP
2. Желание создать идеальный продукт (слишком большой скоуп)
3. Недостаточное количество фичей (слишком маленький скоуп)
4. Не собирать обратную связь
5. Везде применять MVP (не всегда подходит)
6. Не применять MVP (когда стоило бы)
7. Применять MVP там, где нельзя
8. Слишком быстро приступать без прототипирования
9. Не иметь чёткого плана
10. Не использовать выводы по результатам
11. Не формировать метрики и критерии успеха
12. Плохо контролировать процесс разработки и срывать сроки
13. Не привлекать всех критичных участников

## Блок 10. Преимущества и ограничения MVP

### Преимущества

**Продуктовые:** быстрая проверка бизнес-модели, ускоренный запуск, простота доработки, лёгкая система, проверка масштабируемости.

**Финансовые:** привлечение клиентов почти сразу, снижение рисков, привлечение инвесторов, экономия на исследованиях, быстрая окупаемость.

### Ключевое ограничение

MVP **несовместимо с инновациями**. Если делаешь супер-стандартный или супер-инновационный продукт — MVP может не помочь. Для революционных решений невозможно провести полноценное исследование аудитории (она может быть не готова).

3. **Скоуп MVP** — через User Story Mapping
4. **Метрики и критерии успеха** — что измерять и какие пороги
