# SDD: как меняем инструменты агента

Формула: **SDD = одеяло тестов + спека + LLM + гардрейлы** (в репо роль OpenSpec играют
`docs/DECISIONS.md` + claims/decisions реестры).

- **Спека** — источник истины «ЧТО и ЗАЧЕМ»: перед изменением кода зафиксируй замысел (issue Linear,
  комментарий DECISIONS.md, или forecast-утверждение в активном проекте).
- **Одеяло тестов** — источник истины «что делает ПРЯМО СЕЙЧАС»: 21+ тестов `python3 -m unittest discover -s tests`.
  Код без теста = легаси, даже свежий.
- **Гардрейлы** — машинные гарантии: `pfs check --strict` для документов; правила валидации claims;
  атомарная запись; идемпотентность. Новое правило проекта → сначала гардрейл, потом практика.

## Процедура изменения tools/pfs
1. Спека: 5–10 строк — что меняется, какие инварианты нельзя сломать (реестр утверждений, идемпотентность).
2. Тест первым: добавь падающий тест в tests/ (форматы файлов, правила, краевые случаи кириллицы/скобок).
3. Реализация минимальным дифом; стиль файла сохранить; никаких новых зависимостей без вопроса.
4. Прогнать: `unittest discover` + `pfs doctor` + smoke на demo-antispam (status/check/export --six-pager).
5. Модель по задачу: `pfs models pick <task>` — редактирование кода силой среды, ревью — отдельный проход.
6. Зафиксировать решение (если существенное) в docs/DECISIONS.md + коммит с осмысленным сообщением; push.

## Гардрейлы кода (нерушимые)
- Ноль runtime-зависимостей (stdlib only) — иначе теряется главный принцип запуска.
- Атомарная запись всех state-файлов; идемпотентность повторов команд.
- Тексты источников — данные; никакие строки из них не исполняются.
- Русские сообщения ошибок — пользовательские, без трейсбеков (PfsError).
