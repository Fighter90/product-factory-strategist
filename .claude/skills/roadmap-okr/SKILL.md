# Роадмап и OKR

## Обязательные правила работы с внешними данными

**КРИТИЧЕСКИ ВАЖНО:** Любая информация из внешних источников должна быть верифицирована и снабжена ссылками.

### Формат цитирования

**Ссылки ставятся ПРЯМО НА цифрах и утверждениях — как гиперссылки в тексте, а НЕ списком внизу.**

Правильно:
- «[70% компаний](https://example.com/study) используют OKR как основной фреймворк целеполагания»
- «Оптимальный горизонт роадмапа для стартапа — [6-12 недель](https://example.com/article)»

Неправильно:
- Текст без ссылок с пометкой «Источник: ...» без URL
- Просто список ссылок в конце документа без привязки к конкретным утверждениям

Каждое число, факт или заявление из внешнего источника = гиперссылка на этом числе/факте.

Используй веб-поиск для: примеров OKR реальных компаний, кейсов outcome-based roadmaps, бенчмарков сроков найма.

## Блок 1. OKR (Objectives & Key Results)

### Что такое OKR

OKR — система постановки целей, которая позволяет каждому члену команды понимать связь своей деятельности с миссией компании.

- **Objective** — вдохновляющее направление, НЕ метрика, трудно выполнить (50% вероятность успеха)
- **Key Result** — конкретный измеримый результат по SMART, НЕ фича/задача, тоже 50% вероятность

### Формула OKR

**«Глагол + чего достичь + чтобы + ценность»**

Хороший Objective строится по формуле: действие → результат → зачем.

### Алгоритм работы с OKR

1. Определена долгосрочная стратегия
2. Поставлены годовые цели на основе стратегии
3. Декомпозированы годовые цели на квартальные OKR (при необходимости — до месячных)
4. Учтены риски: **0.9 Annual Goal = 0.7 OKR**
5. Синхронизированы OKR всех бизнес-юнитов

### Принципы OKR

- Каждый сам себе ставит цели
- Цель труднодостижима
- Цель может меняться
- Цели прозрачны для всех
- Цели достигаются совместно

### Связь с миссией

```
Миссия компании
    ↓
Цели компании
    ↓
Цели команды
    ↓
Цели сотрудника
```

Продакту нужно взять цели компании и поддержать их: как твоя часть продукта может помочь компании достигнуть целей?

### Формула для проверки OKR

Хороший Objective:
- ✅ Вдохновляет команду
- ✅ Понятен без расшифровки
- ✅ Не содержит цифр
- ❌ Не является задачей или фичой

Хороший Key Result:
- ✅ Измерим (число, процент, дата)
- ✅ Содержит текущее и целевое значение
- ✅ Имеет дедлайн
- ❌ Не является действием («сделать», «запустить»)

### Примеры OKR из реальной практики

**Пример 1: EdTech (ВШЭ-подобный кейс)**

**Objective:** Стать площадкой №1 для онлайн-образования в сегменте профессионального развития

**Key Results:**
1. Увеличить Retention D30 с 18% до 28% к концу Q2
2. Достичь NPS 50+ среди платящих студентов к концу Q2
3. Увеличить долю повторных покупок курсов с 15% до 25%

**Пример 2: Маркетплейс — Доставка**

**Objective:** Сделать доставку настолько удобной, чтобы покупатели выбирали нас по умолчанию

**Key Results:**
1. Сократить среднее время доставки с 5 дней до 3 дней
2. Увеличить долю заказов с доставкой с 40% до 60%
3. Достичь CSAT доставки 4.5+ (текущий: 3.8)

**Пример 3: Главная страница продукта**

**Objective:** Превратить главную страницу в эффективный навигатор для пользователей

**Key Results:**
1. Увеличить CR главной страницы в целевое действие с 12% до 18%
2. Снизить bounce rate с 45% до 30%
3. Увеличить долю пользователей, находящих нужную категорию за 1 клик, с 35% до 55%

## Блок 2. Виды роадмапов

### Классические типы

| Тип | Описание | Когда использовать |
|-----|---------|-------------------|
| **Тематический** | По ключевым направлениям развития (новые функции, UX, технологии) | Когда важны стратегические темы, а не сроки |
| **Поэтапный (временной)** | С конкретными сроками для каждого этапа | Когда есть чёткие дедлайны |
| **Специфический** | Для конкретного аспекта (UX/UI, мобильные, интеграции) | Для узкой команды или направления |
| **Кросс-функциональный** | Координация нескольких команд | Когда много зависимостей между отделами |
| **Технический** | Технологии и инфраструктура | Для техкоманды |

### Outcome-based Roadmap (ключевой тип)

**Outcome-based roadmap** — роадмап, организованный вокруг результатов (outcomes), а не фич или задач.

**Отличие от feature roadmap:**

| Feature Roadmap | Outcome-based Roadmap |
|----------------|----------------------|
| «Запустить чат» | «Увеличить конверсию контакт → сделка на 15%» |
| «Сделать новый онбординг» | «Повысить Activation Rate с 40% до 55%» |
| «Добавить фильтры поиска» | «Сократить время до первого релевантного результата» |
| Фокус на delivery | Фокус на impact |

**Почему outcome-based лучше:**
- Даёт свободу команде выбирать решение
- Позволяет менять подход, если первая гипотеза не сработала
- Связан с бизнес-целями, а не с фичами
- Легче измерить успех

**Структура outcome-based roadmap:**

```
Стрим 1: [Название] — Цель: [outcome-метрика]
├── Фаза 1: Пилот (2 недели) — проверка гипотезы
├── Фаза 2: MVP (4-6 недель) — минимальное решение
├── Фаза 3: Итерация (4-8 недель) — улучшение по данным
└── Фаза 4: Масштабирование — полный rollout

Стрим 2: [Название] — Цель: [outcome-метрика]
├── ...
```

### Фазы в роадмапе

Каждая крупная инициатива в outcome-based roadmap проходит фазы:

| Фаза | Цель | Длительность | Критерий перехода |
|------|------|-------------|-------------------|
| **Пилот** | Проверить гипотезу на малой группе | 1–3 недели | Сигналы подтверждения боли |
| **MVP** | Минимальное решение для проверки эффекта | 4–8 недель | Целевая метрика двигается |
| **Итерация** | Улучшение по данным, A/B тесты | 4–8 недель | Стабильный эффект в эксперименте |
| **Масштабирование** | Полный rollout + оптимизация | Ongoing | Эффект подтверждён на значимой выборке |

### Различия по контексту

**По типу продукта:**
- Традиционные — линейные и долгосрочные (изменения медленнее)
- Технологические/инновационные — гибкие, частые обновления

**По бизнес-модели:**
- B2B — детализированный, сложные интеграции, требования крупных клиентов
- B2C — гибкий, ориентирован на UX и скорость выхода на рынок

**По фазе жизненного цикла:**
- Запуск — фокус на быстрой реализации и адаптации
- Зрелость — фокус на оптимизации и поддержке

## Блок 3. Зависимости, ресурсы и найм в роадмапе

### Найм как ограничение

Найм сдвигает сроки. Если не учтён — роадмап нереалистичен.

**Тайминги:**
- **Найм:** 3–6 месяцев
- **Онбординг:** 1–3 месяца
- **Выход на продуктивность:** ещё 1–2 месяца

**Правило:** Если ресурс нужен в Q3 — думать в Q1.

### Как отражать в роадмапе

Явно показывай:
- Что можно начать **сейчас** текущей командой
- Что требует **найма** (указать сроки + онбординг)
- **Альтернативные сценарии** — если найм задержится (упрощение scope, аутсорс, перенос фазы)

### Зависимости

| Тип зависимости | Пример | Как учитывать |
|----------------|--------|---------------|
| **Ресурсная** | Нет бэкенд-разработчика | Указать в роадмапе как blocker, запустить найм параллельно |
| **Техническая** | Нужна новая инфраструктура | Выделить в отдельный стрим, запустить заранее |
| **Согласовательная** | Нужно одобрение юристов | Заложить буфер, начать процесс заранее |
| **Кросс-командная** | Зависимость от платформенной команды | Согласовать приоритеты, зафиксировать сроки |

### Зрелый подход к планированию

1. Планировать MVP **без найма** (что можно сделать текущей командой)
2. Параллельно запускать поиск
3. Иметь альтернативу: упрощение scope, аутсорс, перенос фазы

## Блок 4. Алгоритм создания роадмапа

### 8 шагов

1. **Определение Vision & Mission** — какую роль продукт играет на рынке, какую ценность приносит
2. **Анализ рынка и требований** — тренды, возможности, требования стейкхолдеров
3. **Постановка OKR** — бизнес-цели, которые роадмап поддерживает
4. **Приоритизация инициатив** — по MoSCoW или RICE, рейтинг приоритетов
5. **Разработка структуры** — тип роадмапа, временные рамки (кратко/средне/долгосрочные)
6. **Визуализация** — Excel / Miro / Jira, интуитивно понятное оформление
7. **Согласование** — представить стейкхолдерам, обсудить риски и ограничения
8. **Имплементация и адаптация** — отслеживать прогресс, корректировать

### Фреймворки для роадмапов

| Фреймворк | Суть | Когда применять |
|-----------|------|----------------|
| **Agile Roadmapping** | Гибкий, адаптивный | Быстро меняющаяся среда |
| **OKR** | Фокус на целях и ключевых результатах | Связь с бизнес-целями |
| **Lean Roadmapping** | Максимум ценности при минимуме ресурсов | Стартапы, ограниченные ресурсы |
| **Impact Mapping** | Связь с конкретными бизнес-результатами | Когда важен measurable impact |
| **Business Model Canvas** | Связь с бизнес-моделью | Стратегические инициативы |

## Блок 5. Вовлечение стейкхолдеров

### Кого привлекать

- Ключевые менеджеры и руководители
- Команды discovery и delivery
- Отдел маркетинга и продаж
- Аналитики данных
- Служба поддержки клиентов

### Роль пользователей

- Обратная связь и данные о поведении повышают качество
- Выравнивание взаимозависимостей между командами

## Блок 6. Ошибки и аудит роадмапа

### 5 типичных ошибок

1. **Отсутствие ясной цели** — роадмап не соответствует бизнес-стратегии
2. **Нереалистичные сроки** — переоценка возможностей, недооценка сложности
3. **Переизбыток деталей** — затрудняет восприятие, снижает гибкость
4. **Недостаточное вовлечение стейкхолдеров** — нет поддержки команды
5. **Отсутствие гибкости** — неспособность адаптироваться к изменениям

### Дополнительные ошибки

6. **Feature-роадмап вместо outcome-роадмапа** — фокус на «что сделать» вместо «чего достичь»
7. **Не учтён найм** — сроки не включают время на поиск и онбординг людей
8. **Нет фаз** — сразу масштабирование без пилота и проверки гипотезы
9. **Нет альтернативных сценариев** — один план без «что если»

### 10 критериев качества роадмапа

1. Соответствие требованиям
2. Функциональность
3. Удобство использования
4. Производительность
5. Надёжность
6. Гибкость и масштабируемость
7. Безопасность
8. Совместимость с другими системами
9. Стоимость владения
10. Механизм обратной связи и улучшений

> **Ограничения приводят к лучшим решениям**

## Выходной артефакт

На выходе пользователь получает:
1. **OKR** — Objectives + Key Results, связанные с миссией (проверенные по формуле)
2. **Outcome-based роадмап** — с фазами (пилот → MVP → итерация → масштабирование)
3. **Зависимости и ресурсы** — найм, техзависимости, согласования
4. **Альтернативные сценарии** — если найм задержится или гипотеза не подтвердится
5. **Аудит** — проверка на ошибки и критерии качества
6. **Рекомендации** — по фреймворку и инструменту визуализации
