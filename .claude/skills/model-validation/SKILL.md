## Что такое валидация модели

Валидация модели — систематический процесс проверки корректности, реалистичности и обоснованности трекшн-модели перед принятием решений.

### Три компонента валидации

1. **Проверка логики** — концептуальная обоснованность (правильные ли драйверы, правильная ли структура)
2. **Поиск технических ошибок** — верификация расчётов (формулы, ссылки, округления)
3. **Обоснование допущений** — реалистичность прогнозов (бенчмарки, ретро-данные, экспертиза)

### Критические риски модели без валидации

- Принятие решений на основе некорректных данных
- Недооценка/переоценка потребности в ресурсах
- Потеря доверия инвесторов и стейкхолдеров
- Провал стратегических инициатив

### Когда валидировать

Валидация — не разовое событие, а непрерывный процесс. Обязательные точки:
1. Перед презентацией стейкхолдерам/инвесторам
2. После значительных изменений в модели
3. Перед началом планирования на основе модели
4. При передаче модели другой команде

## Блок 1. Проверка драйверов

### Критерий достаточности

Каждый компонент целевой метрики должен быть объяснён драйвером модели:

1. Берём целевую метрику (например, MRR для SaaS)
2. Раскладываем математически: `MRR = Число клиентов × ARPU`
3. Проверяем: каждый компонент либо является драйвером, либо раскладывается дальше
4. Продолжаем до атомарных драйверов

**Критерий успеха:** все компоненты формулы объяснены драйверами модели.

### Признаки корректных драйверов

- Причинно связаны с результатом (а не просто коррелируют)
- Измеримы и отслеживаемы
- Команда может на них влиять
- Не дублируют друг друга
- Покрывают целевую метрику без пробелов

## Блок 2. Четыре типа технических ошибок

### 1. Ошибка округления

Накопление погрешностей при округлении промежуточных результатов.

**Правило:** округляйте только финальный результат для презентации. Храните промежуточные расчёты с полной точностью (в Google Sheets просто убирайте знаки после запятой визуально).

**Как обнаружить:** сумма помесячных округлённых значений ≠ округление годовой суммы.

**Формула автопроверки:**
```
=IF(ABS(SUM(B10:M10) - N10) > 0.1; 1; 0)
```

### 2. Ошибка временной привязки

Самая частая категория ошибок в трекшн-моделях.

**Рассогласование периодов:** сравниваются затраты одного момента времени с доходами за годы → искажение unit-экономики.

**Смешивание точечных и накопительных метрик:** MAU — это уникальные пользователи за 30 дней, а не накопительный баланс. Нельзя складывать как остаток на счёте.

**Правильная формула MAU:**
```
MAU(месяц N) = MAU(N-1) + New Users(N) - Churned Users(N)
```

### 3. Противоречия в формулах

Разные части модели считают одну и ту же величину по-разному.

**Правило SSOT (Single Source of Truth):** каждая величина считается в одном месте. Все остальные листы ссылаются на это значение. Используйте именованные диапазоны для критических ячеек.

### 4. Логическая несогласованность

Модель нарушает физические или экономические законы.

**Нарушение баланса:**
```
Клиенты начало месяца + новые - ушедшие ≠ клиенты конец месяца
```

**Нарушение неотрицательности:**
- Retention rate = 120% — невозможно
- Number of users = -500 — невозможно

**Нарушение физики:**
- CR1 (landing → reg) = 85%, CR2 (reg → pay) = 90%
- CR Total = 85% × 90% = 76.5%
- Но в модели: Overall conversion = 80% — противоречие

## Блок 3. Автоматические проверки (формулы для Google Sheets)

Создайте отдельную вкладку **CHECKS** в модели. Используйте бинарную систему: 0 = ошибок нет, 1 = есть ошибка. Глобальный статус:

```
=IF(SUM(Check_Range) > 0; "ERROR"; "OK")
```

### Проверка «битых» ячеек

Ищет #REF!, #DIV/0!, #N/A во всём листе:
```
=IF(SUMPRODUCT(--ISERROR('P&L'!A1:Z1000)) > 0; 1; 0)
```

### Проверка отрицательных значений

Количество пользователей или сессий не может быть < 0:
```
=IF(MIN(B20:M20) < 0; 1; 0)
```

### Проверка границ процентов

Конверсия, Retention и Churn всегда от 0 до 1:
```
=IF(OR(MAX(B25:M25) > 1; MIN(B25:M25) < 0); 1; 0)
```

### Проверка монотонности Retention

В классическом когортном анализе Retention месяца 2 не может быть выше Retention месяца 1 (без реактивации):
```
=IF(SUMPRODUCT(--(B31:M31 > B30:M30)) > 0; 1; 0)
```

### Проверка непревышения TAM

Сумма трафика по каналам не должна превышать ёмкость рынка:
```
=IF(SUM(B50:B55) > 'Assumptions'!$B$5; "TAM Exceeded"; "OK")
```

## Блок 4. Бенчмарки и ретро-данные

### Функции бенчмарков в валидации

- **Sanity check** — быстро выявить нереалистичные допущения
- **Калибровка** — скорректировать параметры модели
- **Объяснение отклонений** — обосновать, почему ваша модель отличается

### Источники бенчмарков

| Тип | Примеры |
|-----|---------|
| **Публичные отчёты** | SEC filings, квартальные отчёты (Яндекс, Ozon) |
| **Отраслевые исследования** | SimilarWeb, Sensor Tower |
| **Бенчмарк-платформы** | OpenView, ChartMogul Metrics, Lenny's Newsletter |
| **Исторические данные** | Собственные A/B-тесты и эксперименты |

### Как применять бенчмарки

- Бенчмарк — это диапазон, а не точное число
- Сравнивайте с компаниями на той же стадии и в том же сегменте
- Объясняйте отклонения: почему ваша конверсия выше/ниже рынка

### Что делать, если данных нет

| Подход | Описание |
|--------|----------|
| **Proxy-метрики** | Данные из похожего региона, сегмента или продукта |
| **Экспертные интервью** | Собрать диапазоны значений от экспертов |
| **MVP** | Запустить минимальную версию, собрать данные за 1-2 месяца, экстраполировать с дисконтом |
| **Сценарное планирование** | Не одна модель, а 3 сценария: pessimistic, base, optimistic |

## Блок 5. Ревью модели

### Зачем нужно независимое ревью

Проблема слепоты «автора»:
- **Confirmation bias** — ищем подтверждение своих гипотез
- **Anchoring** — привязка к первому варианту
- **Curse of knowledge** — не замечаем неочевидные места

### Цели ревью

1. Найти технические ошибки
2. Проверить логику и обоснованность допущений
3. Оценить понятность и прозрачность модели
4. Дать рекомендации по улучшению

### Кто участвует

- Продуктовый аналитик — техническая проверка
- Финансы — проверка экономики и допущений
- Другой продакт — проверка логики и здравого смысла
- Стейкхолдер — проверка соответствия целям

## Блок 6. Do's и Don'ts

### Don's (красные флаги)

- Нереалистичные input-метрики: слишком высокие на старте или завышенная динамика
- Перенос недовыполнения текущего периода на будущие без обоснований
- Нет учёта исторических данных и трендов → завышение baseline
- Не учтена каннибализация существующих продуктов
- Нет кросс-валидации с экспертизой или другими кейсами
- Коммит без input-метрик — автоматический красный свет
- Привязка к одной сильной предпосылке, ослабление которой ломает все output-метрики

### Do's (зелёные флаги)

- Рост input-метрик обоснован A/B-тестами, исследованиями, рыночными трендами
- Рыночные тренды и исследования продисконтированы
- «Доля рынка» НЕ используется как input-метрика
- Отставание по ключевым метрикам учтено или есть recovery-план
- Падение одной input-метрики НЕ перекрывается повышением других
- Каннибализация учтена экспертно или по результатам A/B
- Реалистичность предпосылок провалидирована
- Изменение каждой предпосылки к baseline не приводит к непропорциональному изменению output-метрик

## Блок 7. Итоговый чек-лист валидации

| # | Категория | Что проверяем |
|---|-----------|---------------|
| 1 | **Драйверы** | Каждый драйвер причинно связан с результатом |
| 2 | **Технические ошибки** | Хардкод, округления, битые ссылки |
| 3 | **Валидация допущений** | Сравнение с бенчмарками |
| 4 | **Ревью** | Модель ревьюил независимый эксперт |
| 5 | **Документирование** | Резолюция или «светофор» от согласующего |

---

## Выходной артефакт

При валидации модели результат включает:

1. **Статус модели** — OK / WARNING / ERROR с обоснованием
2. **Список найденных ошибок** — по типам (технические, логические, допущения)
3. **Вкладка CHECKS** — автоматические проверки с формулами
4. **Сравнение с бенчмарками** — где модель в пределах нормы, где отклоняется
5. **Рекомендации** — что исправить перед защитой
6. **Чек-лист** — заполненный по всем 5 категориям
