# Ответ на бриф: единый документ из 5 частей (BRIEF_RESPONSE.md)

Брифы заказчиков (шаблон от заказчика или адаптированный) требуют **один читабельный документ**,
а не россыпь шагов агента. После завершения шагов 4–7 (04/05/06) собери `outputs/BRIEF_RESPONSE.md`
— каноническая структура «документа из пяти частей» (проверено на брифе «Связь для близких
и собственных устройств», проект «связь-для-близких-и-собственных-устройств»).

Шаблон: `knowledge/templates/brief_response.md` (если отсутствует — структура ниже полная).
Карты: `M-customers`, `M-jtbd`, `M-mvp-pilots`, `M-unit-economics`, `M-ab-testing`.

## Структура (5 частей — по брифу)

**Часть 1 · Первые клиенты, проблема, предложение, ожидаемый результат** — в самом начале:
кто первые клиенты (сегмент + доступная база [C###]), выбранная проблема (одна фраза — какая помощь
и в какой момент), предложение (название услуги + что человек видит и делает), ожидаемый результат
планового периода с целевыми числами заказчика.

**Часть 2 · Разбор проблемы клиента** — обязательно:
- *Восстановить один случай*: сигнал → кто заметил → что сделал → чем разрешилось → последствие →
  последний момент, когда мы ещё могли помочь. История не дана? Реконструкция по типовой механике,
  каждое значение — помеченное допущение.
- *Различить сигнал и причину*: версии (не исчерпание / неоплата / устройство выключено) и как
  каждая меняет действие.
- *Обосновать первый приоритет*: сопоставление с одной серьёзной альтернативой (у скольких клиентов,
  как часто, тяжесть последствий, доля случаев с вовремя возможной помощью) + почему этот ущерб важнее.
- *Проверяемое предположение в конце*: какое действие изменит результат + какое наблюдение заставит
  сменить приоритет. Нет решающего числа → как его получить и при каком значении другой путь.
  Диапазон вместо одного прогноза.

**Часть 3 · Предложение и путь к клиенту** — услуга глазами пользователя (момент ценности →
что видит → какое действие → как узнает, что решено); обещание + на каких тарифах/с чьего согласия;
весь путь для КАЖДОЙ роли (приглашение без ответа, отказ, отзыв согласия); **одна операция до конца**
(условия → шаги → где виден итог → повторное нажатие не приводит ко второму списанию); сравнение
с привычными способами клиента (какой шаг исчезает, насколько раньше вмешаться); состав первого
запуска (есть / добавить / без чего обойтись; что в тарифе, что платно); проверка удобства
(старый vs новый способ); что пригодится второй группе, что проверять заново; привлечение
(два доступных рынка, кому подходит первый сценарий, момент уместности показа, допущения конверсий,
шаги остановки); сведение чисел (начало года + новые − выбывшие; один способ привлечения на подключение;
вклад показа = факт − обычное обслуживание; CAC канала); активность (какая доля подключённых должна
совершить действие; часть роста от числа групп, часть от доли активных).

**Часть 4 · Польза для клиента и прибыль** — один главный результат + признак наступления
(открытие предупреждения ≠ результат; нужна запись о факте); таблица «польза / работа услуги /
нежелательные последствия» с уточнениями (числитель/знаменатель, период, единица счёта); порог
улучшения и разброс — записаны ДО запуска (два способа записи разницы: п.п. и «на четверть» — разный
смысл); сравнение с более простым способом (обоснование бюджета); пробный запуск (кого включать /
с чем сравнивать / что считать / хватит ли времени / как действовать по результату); прибыль:
база сравнения → + вклад доп. оплаченных месяцев по ставке → − новые прямые расходы (у каждого
слагаемого объём, цена, период); удержание и как проверить по платежам; другие пути денег
(экономия поддержки = действительно исчезающие затраты); граница решения (формула при неизвестной
цене); окупаемость разработки отдельно + предельная сумма вложений за выбранный срок.

**Часть 5 · Стратегический выбор, план по кварталам, ресурсы, риски, просьба** — сравнение
выбранного с двумя другими путями (одна ситуация, один горизонт: польза, клиенты, затраты, срок,
последствия ошибки; что оправдает переход к дорогому); план по кварталам (что станет известно →
какое решение); **собственный прогноз по всем строкам таблицы заказчика** (основной и менее
благоприятный ход; каждую разницу с «без изменений» связать с действием и допущением; для каждой
недостижимой цели — разрыв, цена устранения, решение руководителя); ориентир на конец третьего года
(числитель/база/условие изменения); ресурсы (кто нужен / что известно / что решить; ответственный
и срок для старт-зависимых работ; что можно сделать, если обязательная система недоступна);
риски при отклонении (наблюдаемый признак → последствия → ответственный → действие; подтверждение
исправления перед возобновлением); **конкретная просьба**: какое решение требуется сейчас, какие
люди и деньги, кто отвечает, что руководство увидит к следующей точке.

## Чек-лист соответствия брифу (включить в 07)

Каждое требование брифа → где закрыто (файл/раздел). Пример-эталон: `07_quality_review.md`
проекта «связь-для-близких-и-собственных-устройств» (таблица ~25 строк).

## Правила

1. Расчёты — рядом с решениями, которые они обосновывают [S001].
2. Все числа — с тегами [C###]/[S###]; значения до проверки — допущения с планом проверки.
3. Тон: решения руководителя называть прямо; каждая часть заканчивается наблюдаемым артефактом.
4. `pfs check --strict` должен оставаться на 0 ошибок: заголовки канонические
   («Чего мы не знаем», «Осознанные отказы», «Подтверждение», таблица «Обещание → Чем подтверждено»).
5. Red team (20+ ударов) встраивается ДО сборки BRIEF_RESPONSE — порогами в 04/06.

`pfs check` → включить BRIEF_RESPONSE в REPORT (`pfs export`) → `pfs step validation done`.
