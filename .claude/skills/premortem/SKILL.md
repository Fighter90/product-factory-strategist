# Premortem — предразбор провала

## Суть

Кляйн/Канеман, prospective hindsight: люди точнее объясняют уже случившееся, чем предсказывают будущее. Поэтому
план разбирают не в режиме «что может пойти не так» (абстрактно, безобидно), а в режиме «цель УЖЕ провалилась
N месяцев назад — как мы к этому пришли»: конкретная механика провала, точки отказа, неверные допущения.

Это не пессимизм и не терапия — это обязательный фильтр перед утверждением решения. Аудит планов.

## Алгоритм

1. **Сценарий провала.** Прошедшее время, 4–8 предложений: «Прошло N месяцев, решение не сработало, потому что…».
   Топ-3 точки отказа по вероятности + самый критичный сценарий (по ущербу; он может не совпадать с топ-1).
2. **Ранние сигналы.** Чекбоксы `- [ ]`, каждый привязан к наблюдаемому событию или метрике проекта
   (через C###, если есть данные; «если не могу придумать, как риск будет виден в данных — риск бесполезен, замени»).
3. **Скрытые допущения.** Карта допущений со статусами: **подтверждено** (C### с источником) / **неизвестно**
   (hypothesis C###, план проверки) / **опровергнуто** (тогда пересматривается само решение, не только план).
4. **Контрмеры.** Чекбоксы, каждый привязан к точке отказа или допущению. Конкретно и проверяемо:
   «лучше планировать» — плохо; «ревью сигналов каждую среду, ответственный X» — хорошо.
5. **Пересобранный план.** Обновлённые шаги с временными рамками; показать человеку на утверждение.

Правила режима: не ищи аргументы «у нас получится» (это анти-оптимистичный режим — всё «получится» вытесняй
в раздел допущений); пиши в прошедшем времени; не успокаивай пользователя. Полные правила и шаблон документа —
`references/premortem-protocol.md` (§5, §7, §10).

## Интеграция с агентом: шаг decision

**Когда:** premortem ПОСЛЕ choice (вариант уже выбран человеком) и ДО утверждения решения (шаг 10): после
черновика `pfs decision add` (D###) и до `pfs ask` «утверждаешь?» / `pfs step decision done`.

**Вход:** `04_product_strategy.md` (обещания и их подтверждения), `06_validation_plan.md` (гипотезы, контрметрики,
критерии), черновик решения D###, риски и возражения выбранного варианта из `03_options.md`.

**Документ premortem:** `projects/<slug>/analysis/premortem_<D###|короткое название>.md` по шаблону протокола §5.

**Выходы — записывать в артефакты проекта, не оставлять в чате:**

| Находка premortem | Куда записать |
|---|---|
| Новый риск / точка отказа | Реестр рисков в `03_options.md` (раздел «Риски» варианта) + `pfs claim add "…" --kind hypothesis` (C###; фактом не записывать) |
| Ранний сигнал | Чекбокс в документе premortem + контрметрика с порогом в `06_validation_plan.md` («Нежелательные последствия») |
| Контрмера | Обязательство: `pfs decision add --commit "что\|кто\|когда"` к тому же D### |
| Опровергнутое допущение | `pfs claim supersede`/`retract` для затронутых C###, пересборка документа, escalate человеку (`pfs ask`) |
| Итог premortem | Пересобранный план показан человеку до утверждения; свежая запись в журнале ревизий документа |

**Ревизии:** при возврате к решению (шаг monitoring) — проверь, сработали ли предсказанные сигналы (протокол §6C);
обновляй diff'ом с записью в журнал ревизий, никогда не затирая старые секции.

**Связь с советом директоров** (сам навык перенесён в `extras/skills/board-of-directors/`, по умолчанию не загружается): совет спрашивает «какое решение принять?» — он работает
ДО выбора (шаг options) и перед утверждением (вердыкт ДА/ДА,ЕСЛИ/НЕТ,ПОКА); premortem спрашивает «как этот план
провалится?» — работает с уже выбранным вариантом. Последовательность: Совет → вердикт → premortem по выбранному
варианту. Premortem не повторяет вердикт: он переводит риски совета в наблюдаемые сигналы и обязательства.

## Указатель: 94 каркаса

`references/index-94.md` — индекс 94 личных premortem-каркасов по 11 категориям (здоровье, психология, финансы,
карьера и т.д.). Сами файлы-каркасы в навык не включены — индекс служит примером категорий провалов и готовых
развёрнутых каркасов; сам контент каркасов — в личном vault автора.

## Чек-лист качества (из протокола §10)

- [ ] Сценарий провала в прошедшем времени и конкретен (не абстрактен).
- [ ] Топ-3 точки отказа упорядочены по вероятности.
- [ ] Самый критичный сценарий отличается от топ-1 точки отказа.
- [ ] Скрытые допущения названы явно, у каждого статус: подтверждено / неизвестно / опровергнуто.
- [ ] Каждый ранний сигнал наблюдаем в метриках проекта или событиях (C###/событие).
- [ ] Каждая контрмера привязана к точке отказа или допущению.
- [ ] Пересобранный план содержит конкретные действия и сроки.
- [ ] Выходы записаны: риски → 03/C###, сигналы → 06, контрмеры → --commit D###; журнал ревизий обновлён.
