# LLM evals: измерять качество LLM-фичи до и после релиза

## Когда применять
LLM-фича спроектирована ([[M-genai-feature-patterns]]) и, возможно, проверена на прототипе ([[M-genai-prototyping]]) —
нужен повторяемый способ измерять качество при каждом изменении (промпт, модель, RAG, каскад) до релиза и на живом
трафике после релиза. Прототип отвечает «достижимо ли качество вообще»; evals — это постоянный контур контроля: LLM
недетерминирован и деградирует незаметно (ротация версий API-модели, дрейф трафика). «Я посмотрел несколько ответов —
стало лучше» — не замер; без evals фича неуправляема.

## Суть

**Иерархия доверия: человеческая разметка > калиброванный LLM-as-judge > автоматически посчитанные прокси.**

1. **Золотой набор (golden set).** Фиксированная выборка реальных примеров — случайная, без чистки, с трудными случаями
   (нехватка данных, противоречия, редкие форматы) и недопустимыми случаями (попытки инъекции, провокации). Сотни, не
   единицы; версия набора фиксируется; между прогонами не меняется — иначе сравнение прогонов бессмысленно.
2. **Регресс-прогон (regression suite).** Каждое изменение промпта, модели или архитектуры = полный прогон золотого
   набора с сохранением входов, выходов и истории шагов; сравнение с предыдущим прогоном. Изменение без регресс-прогона
   — деградация без свидетелей.
3. **Человеческая разметка (human annotation).** Определение качества дают люди; всё остальное — аппроксимация.
   Порядок: чтение и пометки свободным текстом («что не так» своими словами) → чек-лист да/нет из пометок → бинарная
   «приемлемо/нет» с порогом, названным до прогона; для сравнения версий — парное сравнение вслепую («стало ли лучше»;
   лучший из двух может оставаться плохим).
4. **LLM-as-judge.** Сильная модель оценивает ответы фичи по рубрике — масштабирует оценку между человеческими
   прогонами. Обязательная калибровка: на выборке с человеческой разметкой посчитать согласованность с людьми;
   рандомизировать порядок в парных сравнениях; проверить известные смещения — предпочтение длинных ответов,
   self-preference (судья предпочитает ответы, порождённые той же моделью), влияние позиции.
5. **Guardrails (ограждения).** Проверки на входе (инъекции, запрещённые темы, валидация формата) и на выходе
   (структура по схеме, запрещённый контент, сверка фактов с данными продукта). Недопустимые ошибки: ноль в прогоне и
   жёсткий фильтр/отказ в рантайме; вердикты с высокой ценой ошибки — правилам, не модели.
6. **A/B против регрессии (онлайн-проверка).** Старый путь vs LLM-фича на живом трафике: целевая метрика +
   контрметрики (жалобы, ручные правки, возвраты, доля отказов). LLM-фича не является улучшением по умолчанию — она
   должна выиграть замер ([[M-ab-testing]]).
7. **Мониторинг деградации.** Canary-примеры на живом трафике; логирование ответов с выборочной оценкой (judge или
   человек); алерты на падение доли приемлемых, рост отказов, стоимости и латентности; жалобы и «палец вниз»
   пользователя — источник новых ошибок для следующей версии золотого набора.

## Как делать
1. Зафиксировать словесный критерий приёмки («хороший ответ = …»), список недопустимых ошибок и порог доли приемлемых —
   всё до первого прогона.
2. Собрать золотой набор: случайная выборка реальных входов + трудные + недопустимые случаи; зафиксировать версию;
   между прогонами не менять.
3. Встроить регресс-прогон в процесс: любое изменение = прогон + сравнение с прошлым; разбивка ошибок по источникам
   (сборка / данные / постановка / модель).
4. Поставить разметку: человек читает выборку прогона и заполняет чек-лист; затем калибровать LLM-as-judge против
   человеческой разметки (согласованность, рандомизация порядка, тест self-preference); judge — для промежуточных
   прогонов, человек — для релизных.
5. Отстроить guardrails: недопустимые случаи — отдельным прогоном; фильтры входа и выхода; вердикты — правилам; отказ
   при нехватке данных.
6. После релиза: A/B против старого пути по метрике и контрметрикам; мониторинг (canary, логи, выборочная оценка,
   алерты); новые ошибки из логов и жалоб возвращать в следующую версию золотого набора.

## Подводные камни
- **Некалиброванный judge.** Судья-модель смещается: длинные ответы кажутся лучше, свои — лучше, порядок в паре влияет.
  Judge без сопоставления с человеческой разметкой — вы оптимизируете вкус модели, а не качество продукта.
- **Подгонка набора и порога.** «Типичные случаи», чистка данных и порог, названный после просмотра результатов,
  завышают оценку. Случайная выборка, порог — до прогона.
- **Одна цифра без разбивки.** «87% приемлемо» не говорит, что чинить: нужны разбивка по пунктам чек-листа и
  классификация источников ошибок.
- **Деградация после релиза.** Ротация версии модели и дрейф трафика меняют поведение незаметно; без мониторинга
  узнаете от пользователей. Canary + алерты + логи с выборочной оценкой — обязательный минимум.
- **Стоимость и приватность evals.** Прогон сотен примеров на сильной модели стоит денег — считать цену прогона; judge
  удешевляет разметку. Логирование реальных диалогов для оценки — персональные данные: маскирование, права, сроки
  хранения. Guardrails не заменяют замер: фильтр скрывает симптом, но не чинит генерацию.
