# A/B-тесты: полный цикл и альтернативы

## Когда применять
Нужно доказать причинно-следственную связь «изменение X → сдвиг метрики Y» до раскатки на всех, посчитать, сколько трафика и недель это займёт, и честно интерпретировать результат. Альтернативы — когда случайное деление пользователей невозможно (сетевые эффекты, офлайн, «выкатили на всех»).

## Суть

### Определение и место среди методов
A/B-тест (сплит-тест) — случайное деление пользователей на группы, показ каждой группе своей версии и сравнение метрик. Это золотой стандарт, потому что внешние факторы (сезон, конкуренты, маркетинг) бьют по обеим группам одинаково. Иерархия достоверности: опрос (мнение, ошибка самоотбора) → поиск похожих (matching, остаточное смещение) → сравнение до/после (тренды и внешние события) → A/B (причинность). Классика не работает при: сетевом эффекте (поведение одной стороны меняет условия другой), невозможности рандомизации (офлайн-кампании, закон), «уже выкатили на всех».
- **H₀** — эффекта нет; **H₁** — эффект есть. Решение принимается только по заранее зафиксированным правилам.
- Ожидаемая доля «зелёных» тестов в зрелой команде мала (~20%), из них раскатывают ещё меньше — это норма, а не провал.
- **Когда A/B не нужен вообще:** (1) нужен ответ «почему», а не «сколько» — интервью и UX-исследование; (2) нет альтернатив (требование закона, критический баг — просто внедрять); (3) ожидаемый эффект огромен и очевиден — редкость, проверять подозрением к случайности; (4) физическая/этическая невозможность деления (нельзя «поднять зарплату половине»). В этих случаях — альтернативы из последнего раздела.

### Метрики и критерии
- Конфиг метрик: 1–2 **target** (ради них тест), 1–3 **proxy** (чувствительнее, сигнал раньше), ≥2 **guardrail** (контр-метрики риска: конверсия, NPS/жалобы, churn, fraud, latency). Больше метрик = потеря мощности.
- Гипотеза по шаблону: «Вариант B (изменение X) значимо изменит метрику M у сегмента S на ≥ Z% относительно A, при α, β и при условии, что guardrail не хуже порога». Плюс записанная H₀.
- Выбор критерия под природу метрики: средние (чек, выручка/юзер) → классический t-test (опирается на ЦПТ); доли и ratio (конверсия, CTR, ARPU = сумма/счётчик) → линеаризованный t-test (поюзерный «вклад» снижает дисперсию); перцентили и тяжёлые хвосты (p95 времени ответа) → quantile t-test на бутстрэпе; несколько групп → ANOVA + post-hoc (Tukey) с поправкой.

### Расчёт выборки, MDE и длительности
Параметры: α (ошибка I рода — «увидеть эффект, которого нет», обычно 0,01–0,05), β (ошибка II рода — «проспать эффект», обычно 0,1–0,2; мощность power = 1−β ≥ 0,8), MDE — минимальный эффект, который тест обязан поймать. Для долей: baseline p, дисперсия σ² = p·(1−p). Двусторонний тест:
- z_α = квантиль нормального распределения уровня 1−α/2 (для α=5% ≈ 1,96); z_β — уровня 1−β (для β=20% ≈ 0,84).
- **Выборка на группу:** n = (z_α + z_β)² · 2·σ² / MDE² (MDE — в абсолютных долях; округлять вверх по смыслу задачи — вниз округляет в пользу пропуска эффекта). При α=5%, β=20% работает правило n ≈ 16·σ²/MDE².
- **Длительность:** n_дней = n / (суточный трафик × доля трафика на группу). Мини-пример: p=1,8% (4,1/230 контактов на просмотр), σ²≈0,0177, MDE=1 п.п. → n ≈ (1,96+0,84)²·2·0,0177/0,0001 ≈ 2 770 на группу; при 115 000 просмотров/сутки на группу ≈ 0,02 дня по трафику — но тест всё равно держат 7–14 дней, чтобы накрыть полный недельный цикл.
- **Обратный расчёт** (фиксированный трафик/срок): MDE = (z_α + z_β)·√(2σ²/n). Если посчитанный MDE больше экономически значимого эффекта — тест не проводить (не поймает) или менять дизайн.
- Рычаги снижения MDE/срока: больше трафика или дольше тест; ниже дисперсия (линеаризация ratio-метрик, стратификация, CUPED/ML-CUPED, чувствительная proxy); компромисс по α/β (осознанно, до старта). MDE «с потолка» и подгонка задним числом запрещены.

### Дизайн: сплитование, слои, exposure
- **Рандомизация и sticky:** пользователь закрепляется за группой по постоянному ключу (user_id / seller_id / region_id) — «первый контакт → навсегда»; попадание то в тест, то в контроль искажает метрики (эффект привыкания).
- **Слои (bucketing):** независимые эксперименты живут в разных слоях с разными ключами хеширования; внутри слоя — 100 бакетов. Это разводит сотни параллельных тестов без «воровства» трафика.
- **Exposure-флаг** ставится максимально близко к моменту изменения UX и до измеряемого действия: позже — часть увидевших остаётся «вне теста», раньше — в группы утекают посторонние.
- **A/A-тест** перед A/B (≥24 ч, лучше полный недельный цикл): обе группы без изменений; тревога, если p<0,1 по любой метрике или дисбаланс размеров групп. Ловит сломанную рандомизацию, кеши, late-exposure. Дополнительно: «тёмный патч» (код раскатан на 100%, фича выключена флагом) — прогрев latency и мгновенный rollback.

### Множественные сравнения
При m проверках вероятность хотя бы одного ложного «прокраса» (FWER) растёт; при 10+ метриках сырое p<0,05 мало что значит.
- **Бонферрони:** α′ = α/m. Просто и консервативно; ок при 1 target + 2–3 guardrail.
- **Холм (step-down):** сортируем p по возрастанию; p₁ ≤ α/m, следующее ≤ α/(m−1) и т.д.; останавливаемся на первом нарушении. Контролирует FWER, мощнее Бонферрони; для 4–8 проверок с дорогой ошибкой.
- **Benjamini–Hochberg (FDR):** находим максимальное k, где p₍ₖ₎ ≤ (k/m)·Q; все p ≤ p₍ₖ₎ значимы. Контролирует ожидаемую долю ложных среди «прокрашенных» (например, Q=5%); для 10–30 второстепенных проверок, где промах дешевле упущенного роста.
- Поправка фиксируется **до** старта; выбор «по итогу p» — p-hacking.
- **Подглядывание (peeking):** каждая проверка в процессе инфлирует α (10 ежедневных просмотров поднимают реальную α с 5% до ~19%). Варианты: запрет — решение ровно в конце; sequential testing с α-spending (например, границы Pocock); байесовский подход — правило остановки фиксируется на старте («стоп, если P(Δ>0) ≥ 0,95 или P(Δ<0) ≥ 0,95»).

### Проведение и мониторинг
- **SRM / здоровье трафика:** факт vs план по размерам групп (например, 50%±0,5 п.п.); expected vs actual exposures (±3%); ковариатный тест по устройству/возрасту (p>0,3); доля трафика на группу соответствует плану. Любое нарушение — стоп и debug: аномально большой эффект почти всегда техническая ошибка, а не успех.
- **Сторожевые (guardrail) метрики** с порогами до старта; критичное ухудшение = досрочная остановка (единственная легальная причина смотреть в процесс до конца, кроме sequential-схемы).
- Не запускать вечером/ночью без дежурной команды; вести единый реестр экспериментов и согласовывать пересечения.

### Интерпретация
- Считать только после окончания: эффект, p-value, 95% ДИ. Для среднего: ДИ = x̄ ± z·σ/√n; ширина растёт с σ и z, падает с n.
- **ДИ не включает 0 ⇔ p < α** (двусторонний). p-value — вероятность такого или более экстремального результата при верной H₀, НЕ размер эффекта. Значимость ≠ бизнес-значимость: +0,2% может быть значимым и бесполезным.
- Отчёт по эффектам строить по сегментам (лесной график: точка-эффект + 95% CI по каждому сегменту, вертикальная линия 0) — но сравниваемые сегменты объявлять заранее.
- Сценарии и действия: **зелёный** (target ↑ значимо, guardrail в норме) → проверка разрезов и динамики, затем раскатка; **зелёный с нюансами** (guardrail чуть просел, суммарный инкремент > 0) → катить с мониторингом/доработкой; **красный** (guardrail просел сильнее прироста, или target ↓) → не катить, искать причину; **серый** (ничего не значимо) → не «продлевать ради удачи», а проверить баги и мощность (CUPED, proxy), пересобрать гипотезу. По каждому — запись в базу знаний; решение: Scale / Iterate / Drop.
- Частотный vs байесовский: частотник отвечает «есть ли значимая разница», байес — «с какой вероятностью B лучше A и каким может быть эффект» (posterior из Beta/Binomial для долей: posterior = Beta(α₀+успехи, β₀+неудачи), P(Δ>0) по Монте-Карло). Байес удобен для low-traffic и коммуникации; decision rule (порог P, expected loss) фиксируется заранее.

### Типовые ошибки интерпретации
- **Подглядывание** — остановка на первом прокрасе → инфляция α (см. выше).
- **Ошибка выжившего** — вывод по случайно запрокрасившимся метрикам вне гипотезы (при m метриках ~α·m прокрасится случайно).
- **Парадокс Симпсона** — рост в каждом сегменте при падении тотала из-за изменения структуры трафика. Пример: каналы с CTR 10% и 90% пополам дают 50%; после перераспределения 90%/10% при CTR 11%/91% тотал = 0,11·0,9 + 0,91·0,1 ≈ 19% — «рост везде», падение в сумме. Проверять структуру и тотал.
- **Эффект новизны/привыкания** — эффект первых дней исчезает; проверять динамику по неделям и держать подвыборку «старых» пользователей.
- **Смещение доступа** — в тесте только «обновившие приложение», в контроле все: сравнивать сопоставимые подгруппы.
- **Пересечение экспериментов** — чужой тест в вашей контрольной группе; лечится слоями и реестром.
- Игнор сезонности — «эффект» от сезонного пика; тест минимум 1–2 полных недели.

## Процедура («золотые» шаги дизайна)
1. Сформулировать проблему и гипотезу по шаблону (X → M → Z%, сегмент, α/β) + H₀.
2. Выбрать метрики: 1–2 target, 1–3 proxy, ≥2 guardrail с порогами; выбрать критерий под природу метрики.
3. Обосновать MDE экономикой (какой минимальный эффект окупает изменения); посчитать n и длительность; проверить, что «влезает» в трафик. Обосновать, почему именно классический A/B.
4. Определить сплит: ключ, слой, sticky, доля трафика; запланировать тёмный патч и A/A.
5. Запустить: A/A → A/B; следить только за health-метриками и guardrail; не подглядывать в целевые.
6. Проанализировать по плану: эффект + p-value + 95% CI (с поправкой), разрезы и динамика, проверка Симпсона и новизны.
7. Принять решение Scale / Iterate / Drop; записать результат в базу знаний с выводом.

Чек-лист перед запуском: A/A пройден (p>0,1) · размер групп по плану · exposure до действия · поправка и решение-правило задокументированы · MDE обоснован экономикой · есть дата и владелец решения.

## Типичные ошибки
- MDE «взят с потолка» или подогнан после старта; α/β меняются «на лету».
- 10+ метрик без поправки; вывод по метрикам вне гипотезы.
- Продление серого теста «ещё на недельку»; остановка на первом прокрасе.
- Нет A/A и health-дашборда — «победа» оказывается багом кеша или late-exposure.
- Сравнение неэквивалентных подгрупп (обновившие vs все); игнор структуры трафика (Симпсон).
- Запуск без плана отката; конфликт с параллельным тестом другой команды.

## Вопросы, которые могут изменить решение
- Какой минимальный эффект экономически оправдан и какой MDE реально достижим при нашем трафике?
- Есть ли сетевой эффект или пересечение с чужими экспериментами, ломающие рандомизацию?
- Достаточно ли мощности, чтобы вообще поймать эффект; не нужен ли другой критерий или proxy?
- Какое правило остановки и что делаем с серым результатом?
- Эффект устойчив по неделям и сегментам или это новизна/сезон/один сегмент?

## Альтернативы, когда классический A/B невозможен
- **Региональный тест** — единица рандомизации город/магазин: matching «пар-близнецов» по историческим метрикам (GMV, заказы), затем случайное распределение пар. Сохраняет сетевой баланс внутри региона; минус — мало единиц (при <30 регионов — Welch/бутстрэп, выше MDE).
- **Switch-back (переключение во времени/гео-блоками)** — один и тот же регион поочерёдно в тесте и контроле (блок = час/день/смена ≥ полного цикла пользователя; порядок ABBA/BAAB против тренда; кластерный t-test, кластер = регион×период). Для сильных сетевых эффектов (прайсинг, матчинг); не для долгих и заметных изменений — эффект «течёт» между блоками.
- **До/после с контролем — Diff-in-Diff:** эффект = Δ(тест: после−до) − Δ(контроль: после−до). Ключевое допущение — параллельность трендов до вмешательства; проверяется на предыстории.
- **Synthetic control** — «синтетический» контроль взвешенной комбинацией похожих объектов, совпадающих с тестом до вмешательства; для одного уникального региона/канала; требует длинной истории.
- **PSM (propensity score matching)** — ретроспективно подобрать «похожих» пользователей воспользовавшимся фичей и сравнить; риск остаточного смещения и чувствительность к набору признаков.
- **Interleaving** — обе версии (например, алгоритмы ранжирования) показываются в одной смешанной выдаче одному и тому же пользователю; сравнение по кликам/действиям на пары позиций. Намного чувствительнее классики при малом трафике, годится для относительного порядка алгоритмов, но не для абсолютного эффекта на бизнес-метрики.
- **Мультиарм/bandit** (epsilon-greedy, Thompson sampling) — трафик перетекает к лидеру, меньше «цена упущенного успеха»; теряется строгая p-value-интерпретация.
- **Fake door** — замер спроса кнопкой «скоро появится» до разработки.
Правило выбора: можно разделить заранее по юзерам → классика; только по гео → региональный; сетевой эффект → switch-back/geo-split; выкатили на всех, есть история → DiD/synthetic control/PSM; сравнение алгоритмов одной ленты → interleaving; мало данных → байес или честно признать «ответа нет». Предпосылки и ограничения метода документируются в отчёте.
