# Валидация модели (бэктест, бенчмарки, sensitivity)

## Когда применять
Перед презентацией модели стейкхолдерам; когда модель становится бюджетом/планом (коммитментом); после крупных изменений допущений; при отклонении факта от плана >10–15%. Валидация — не «проверка формул», а процесс согласования (buy-in): ошибка в модели, ставшей планом, стоит очень дорого.

## Суть
**Пирамида валидации** — снизу вверх, не пропуская уровни:
1. **Механические ошибки** — формулы, ссылки, округления (самый частый слой).
2. **Логическая согласованность** — противоречия допущений и здравому смыслу.
3. **Допущения и бенчмарки** — каждое assumption с источником.
4. **Бэктест** — работает ли модель на прошлых данных.
5. **Концептуальная проверка** — верна ли сама логика моделирования.

**Механический слой** — самый частый и самый легко исправимый:
- баланс периода: `Конец = Начало + приращения − убытия` (допуск ~0.01 на округление);
- произведение конверсий по шагам = итоговая конверсия (сложение вместо умножения — классика: 50%×30%×20%×10% = 0.3%, а не 110%);
- retention ≤ 100%, конверсии ∈ [0;1], неотрицательность пользователей и выручки;
- метрика, посчитанная «двумя путями» (demand vs supply), сходится;
- нет #REF! после удаления строк; протянутые формулы проверены в крайних ячейках (сдвиг относительной ссылки — типичная причина retention = 120%);
- ретро/факт отделены от прогноза.

**Логический слой:** значения метрик соответствуют стадии бизнеса (стартап ≠ зрелый SaaS); части модели не противоречат друг другу; учтена сезонность. Приблизительные рамки:

| Метрика | Стартап (0–1 год) | Масштабирование | Зрелый (3+ года) |
|---|---|---|---|
| Month-1 retention | 10–30% | 25–50% | 40–70% |
| Конверсия в оплату | 1–5% | 5–15% | 10–30% |
| MoM-рост MAU | 10–30% | 5–15% | 1–5% |
| Месячный churn | 5–15% | 3–8% | 1–5% |
| LTV/CAC | 0.5–1.5 | 1.5–3 | 3–5+ |

Красные флаги: retention > 50% у стартапа, конверсия шага воронки 90% («так не бывает»), 3+ метрики в красной зоне = пересмотр допущений. Приём «обратного чтения»: от итоговой выручки вверх по цепочке — какие допущения потребовались, реалистичны ли они.

**Бенчмарки:** опорные значения из индустрии, конкурентов или внутренних данных. Золотое правило: **каждый бенчмарк = источник в модели**; источника нет — честно признать.

| Источник | Плюсы | Минусы |
|---|---|---|
| Публичные отчёты (IPO, годовые) | проверяемы | не всегда детальны |
| База AB-тестов компании | самый релевантный для эффектов фич | нужна зрелость аналитики |
| Бенчмарковые агентства | структурированы | платные |
| Собственная история | максимально релевантны | только для существующих продуктов |
| Экспертные оценки | быстро и дёшево | субъективны |

Проверка релевантности по 4 критериям: индустрия, сегмент, стадия, бизнес-модель («правило 2 из 4» — можно использовать с оговоркой). Источники расходятся: согласованные — среднее, умеренно — медиана, сильно — **консервативное значение** (дисперсия 10–80% — это шум, а не информация). Здоровая пропорция: большинство допущений в рамках рынка, выше бенчмарка — единицы с объяснением; >40–50% допущений выше бенчмарка = нереалистичная модель.

**Бэктест:** подставить прошлые данные, сравнить прогноз модели с фактом, посчитать MAPE (средняя абсолютная процентная ошибка).

| MAPE | Интерпретация | Действие |
|---|---|---|
| < 5% | отличная модель | уверенно планировать |
| 5–15% | хорошая | закладывать запас на отклонение |
| 15–30% | удовлетворительная | пересмотреть ключевые допущения |
| > 30% | слабая | не годится для бюджетирования |

**Rolling backtest:** каждый месяц заливается факт → модель перепрогнозирует → ошибка должна снижаться; нестабильный прогноз = переобучение или хрупкое допущение. Ловушки: «утечка из будущего» (в модели данные, недоступные на момент прогноза), переобучение (делить данные train/test), нестабильность.

## Процедура
1. **Автопроверки (см. Шаблон):** вкладка Checks с бинарными формулами и happy-checker `SUM(всех проверок)`; 0 = чистая модель. Это снимает когнитивную нагрузку с ревьюера.
2. **Sanity check итогов:** итоговые Revenue/MAU/Profit реалистичны для рынка и стадии? Обратное чтение цепочки допущений.
3. **Сверка с бенчмарками:** каждое допущение — источник и класс достоверности ([[M-source-criticism]]); отклонение от бенчмарка объяснено одной строкой.
4. **Сверка факт/план:** декомпозиция отклонения на рыночный / продуктовый / операционный / модельный фактор; каждый против бенчмарка; модель обновляется фактом.
5. **Бэктест** (если есть история): MAPE по 6+ месяцам, rolling backtest, проверка на утечку из будущего.
6. **Sensitivity analysis:** для 2–3 ключевых драйверов — сценарии ±10/20/30%; ответ на «что будет, если пойдёт не так». Правило трёх вопросов: какой параметр влияет сильнее всех; какой известен хуже всего; при каком значении проект нежизнеспособен (**threshold** — ниже порога падать нельзя; понятен любому инвестору).
7. **Сценарии bull/base/bear:** три набора допущений → три итога; при большой дисперсии значений показывать диапазон, а не «точный» прогноз.
8. **Ревью без «одного котла»** — разнообразие перспектив обязательно, пир из той же команды подвержен тем же искажениям:

| Ревьюер | Что проверяет | Время | Ограничение |
|---|---|---|---|
| Бизнес-пир | логика, «ощущение» цифр | 30 мин | те же biases |
| Финансы / FP&A | формулы, дисконтирование | 1–2 ч | слабый продукт-контекст |
| Дата-аналитик | качество данных, бенчмарки vs факт | 1–2 дня | нет бизнес-контекста |
| Внешний аудитор | крупные допущения, рынок | 3–5 дней | дорого, опционально |

9. **Контроль когнитивных искажений:** confirmation bias («аргументы опираются на нас», а не мы на них), anchoring (влюблённость в первый вариант/мнение авторитета), нежелание ломать «стройную картинку». Противоядия: челленджер (копает один драйвер до дна), поиск 3 аргументов ПРОТИВ модели, sensitivity, внешний ревьюер.
10. **Документирование:** отчёт о валидации — happy checker, найденные проблемы и решения, кто ревьюил, buy-in всех участников. Только после этого модель становится планом.

## Шаблон / чек-лист
Вкладка `Checks`, бинарно (0 ок / 1 ошибка), глобальный статус `=IF(SUM(cheка)>0;"ERROR";"OK")` — формулы см. [[M-traction-model]]:
```
Баланс периода:        =IF(ABS(End−(Start+In−Out))<0.01;0;1)
Неотрицательность:     =IF(MIN(диапазон)<0;1;0)
Retention ≤ 100%:      =IF(MAX(диапазон)>1;1;0)
Воронка невозрастает:  =IF(SUMPRODUCT(--(шаг_след>шаг_пред))>0;1;0)
Не выше рынка:         =IF(SUM(модель)>SOM_cap;1;0)
Сходится demand/supply:=IF(ABS(путь1−путь2)>0.01;1;0)
Битые ссылки:          =IF(SUMPRODUCT(--ISERROR(диапазон))>0;1;0)
```
Чек-лист готовности модели: структура по вкладкам и понятная навигация · описанная логика построения · assumptions выделены отдельно от формул · у каждого допущения источник (или честное «нет») · sensitivity и сценарии · threshold · ревью подписано · результаты задокументированы · buy-in.

Сценарная таблица: `Параметр (retention, CAC, конверсия, ARPU) | Bear (−20%) | Base | Bull (+20%) → Revenue, Profit по годам | Threshold: Profit < 0 → красный флаг`.

## Типичные ошибки
| Ошибка | Как заметить |
|---|---|
| Валидация «на глаз» без вкладки Checks | ревьюер ищет механику вместо логики |
| Красивая модель без внешнего ревью | «замыленный глаз» автора не видит retention 120% |
| Бенчмарк из нерелевантной индустрии/стадии | конверсия одежды 2–3% для доставки еды с её 15–25% |
| Расхождение двух путей расчёта проигнорировано | revenue от demand ≠ revenue от supply — всегда искать причину |
| Подгонка допущений под желаемый итог | «экономика не сходится — поднимем конверсию» вместо честного вывода |
| Оценка по одному месяцу бэктеста | нестабильный прогноз принят за «норму» |
| Один ревьюер (или все из одной команды) | общие когнитивные искажения не видны |
| Ранние месяцы взяты как база | первые 1–2 месяца — early adopters, непоказательны; ждать 2–3 месяца данных |

Когда данных нет совсем (новый бизнес/рынок): прокси-метрики (`целевая = прокси_1 × прокси_2 × поправка`, ожидаемая ошибка 30–60%), экспертные оценки, дешёвый MVP-тест, аналогия со смежным рынком — и сценарное планирование вместо «точного» прогноза.

## Вопросы, которые могут изменить решение
- Какое одно допущение, если оно неверно на 30%, валит модель — и как быстро мы это узнаем из реальности?
- Где threshold проекта и что мы делаем при его пробитии?
- Какие допущения мы знаем хуже всего (им — sensitivity в первую очередь)?
- Можно ли проверить самое рискованное допущение дёшево и быстро (MVP, первая маркетинговая кампания даёт реальный CAC за 1–2 недели)?
- Что в модели появилось «для красоты» и не выдержит вопроса «откуда цифра?»?
