# ML для продуктового менеджера

## Когда применять
Команда думает «здесь нужен ML»: подсказка цены, антифрод, рекомендации, прогноз спроса. Нужно решить, оправдан ли ML, превратить идею в проверяемую ML-гипотезу, договориться о метриках качества модели и бизнес-метриках и проверить эффект в продукте, включая усиление A/B-тестов методами ML.

## Суть

### Где ML оправдан (и где нет)
ML оправдан, когда закономерность сложная/многомерная и не выражается правилами: 
- **Поиск и ранжирование** — семантика запроса, поведение пользователя, качество объекта; без ML маркетплейс и контент-сервисы не масштабируются.
- **Рекомендации** — персональные блоки «похожее», ленты; растят вовлечённость и конверсию.
- **Классификация рисков** — антифрод, модерация контента, скоринг (Recall критичен).
- **Регрессия/прогноз** — цена, время до сделки, спрос, нагрузка, всплески фрода.
- **Кластеризация** — поиск сегментов и генерация гипотез.
- **Прайсинг и автобиддинг** — динамические цены и ставки.
ML НЕ нужен, когда: данные отсутствуют (нет ML без данных), зависимость простая и хорошо ловится правилами/SQL, решение принимает человек на качественных данных, а точность модели не окупает сложность и риски. Правило: сначала простая модель/правило как baseline, ML — когда он доказанно лучше baseline по бизнес-метрике.

### Типы ML-задач глазами продакта
| Задача | Вопрос | Продуктовые примеры | Метрики |
|---|---|---|---|
| Регрессия | предсказать число | цена, время до сделки, спрос | MAE, MAPE, RMSE |
| Классификация | предсказать вероятность/класс | фрод, нарушение правил, «купит/не купит» | Precision, Recall, ROC-AUC |
| Кластеризация | найти сегменты | сегменты работодателей/покупателей | силуэт + интерпретируемость сегментов |
| Ранжирование | порядок объектов | поиск, рекомендации, лента | NDCG, MRR, Recall@k, Precision@k |
Пояснения: Precision — доля верных среди «покрашенных» моделью; Recall — доля найденных среди всех реальных (для фрода/модерации ≥90% — типовая планка); ROC-AUC — качество разделения классов; NDCG/MRR — качество порядка выдачи. Ошибка типа «precision для регрессии» — признак неверной постановки.

### Шаблон ML-гипотезы (7 шагов)
1. **Проблема/бизнес-контекст** с числами: «в категории X владельцы занижают цену на 20–30%, это снижает GMV и маржу».
2. **Узкая ML-задача**: из проблемы выделить подзадачу — классификация «хорошая/плохая цена», регрессия «оптимальная цена», ранжирование «какую цену показывать».
3. **Данные**: есть ли исторические примеры, разметка, поведенческие данные; возможны ли они в будущем в момент применения. Нет данных → гипотеза провальна.
4. **Точка принятия решения (decision point)** — где результат модели «встаёт» в продукт: при создании объявления, в ленте, при оплате. ML без места применения бессмыслен.
5. **Бизнес-метрика** — KPI гипотезы: GMV, CR, retention, время сделки, доля фрода.
6. **Метрики качества модели** — второй уровень KPI по типу задачи (таблица выше).
7. **Критерии успеха по всем трём осям**: бизнес (например, +4% GMV в категории), модель (например, MAE < 12%), UX (например, ≤10% пользователей отклоняют подсказку).
Примеры пар «бизнес ↔ модель»: модерация — снижение риска/рост доверия ↔ Recall > 90%; прогноз времени до сделки — рост CR продаваемости ↔ MAPE < 20%; рекомендации — рост GMV ↔ NDCG > 0,25. Планируя, проверить достижимость порогов (AUC > 0,75 / MAPE < 20% достижимы ли на этих данных?).

### Метрики качества модели vs продуктовые метрики
- Модельные метрики — инструмент разработки, бизнес-метрика — критерий успеха. Высокая точность модели ничего не гарантирует продукту: AUC 0,95 при нулевом влиянии на CR — бесполезная модель.
- Баланс классов и цена ошибок: порог классификации выбирается под продукт (антифрод — жертвуем Precision ради Recall; подсказки цены — наоборот).
- Офлайн-метрики ≠ онлайн-эффект: раскатывать только после проверки на живых пользователях (A/B). Расхождение офлайн/онлайн — нормальный повод для исследования, а не для «подгонки порога».
- Ранжирование проверяется на сложных метриках (NDCG/MRR/Recall@k), т.к. простого CTR мало.

### ML как инструмент аналитики и генерации гипотез
- **Анализ факторов:** модель (например, градиентный бустинг) показывает, какие признаки реально влияют на целевую метрику (важности/SHAP) — источник гипотез («что влияет на покупку подписки/цены объекта»).
- **Кластеризация:** поиск сегментов, которых не видно в отчетах, → персонализированные гипотезы и кампании.
- **Прогнозирование:** компоненты временного ряда и модели — см. [[M-forecasting-product]]; типовые ошибки: игнор сезонности, плохая очистка, leakage, слепое доверие, отсутствие бизнес-логики.
- **ML в A/B-тестах** ([[M-ab-testing]]):
  - **CUPED / ML-CUPED** — снижение дисперсии: ковариата X = значение метрики до теста (классика) или прогноз ML-модели «какой была бы метрика без фичи» (ML-версия учитывает больше данных и динамику). Скорректированная метрика = Y − θ·(X − E[X]); θ оценивается по предпериоду. Эффект — до 2–3-кратного ускорения теста (21 день → 7–10).
  - **Propensity score / стратификация** — выравнивание гетерогенных групп, когда разбиение получилось неравным по «сильным» пользователям: модель оценивает вероятность попадания в группу, взвешивание убирает смещение.
  - **Uplift-моделирование** — когда средний эффект ≈ 0, но эффект есть в сегментах: модель предсказывает индивидуальный эффект (T/S/X-learner, causal forests, uplift-деревья); продакт выбирает сегмент с сильнейшим эффектом и катит адресно.
  - **Сложные метрики** (поиск, рекомендации) — тесты на NDCG/MRR/Recall@k с ML-методами снижения дисперсии.
  - Риски: ML без проверки смещения, плохая ковариата (учитывает пост-тестовый период = leakage), применение без бизнес-понимания.

### Валидация ML-решений
1. **Офлайн:** разметка/ретроспектива, метрики качества по типу задачи, сравнение с простым baseline (правила, среднее, наивный прогноз).
2. **Онлайн:** A/B-тест бизнес-метрики с guardrail (конверсия, жалобы, latency) — ML-фича доказывает себя как любой продукт.
3. **Пост-запуск:** мониторинг дрейфа данных и качества модели (распределения признаков плывут — точность падает), цикл переобучения, фоллбек-логика при отказе модели.
4. Разрезы: не ухудшился ли опыт в minority-сегментах (модель оптимизирует среднее).

### Три пары «задача → механика в продукте → критерии» (шаблоны)
| Задача | Механика (decision point) | Бизнес-метрика | Метрика модели |
|---|---|---|---|
| Модерация объявлений (классификация) | остановка публикации + ручная проверка | снижение рисков, рост доверия | Recall > 90% |
| Подсказка «время до сделки» (регрессия) | подсказка при создании объявления | рост CR продаваемости | MAPE < 20% |
| Похожие товары (ранжирование) | блок «Похожее» на карточке | GMV | NDCG > 0,25 |
Паттерн у всех: узкая задача в точке контакта + пара «бизнес-метрика / метрика модели» + онлайн-проверка. Модель без decision point не строится.

## Процедура
1. Проверить, нужен ли ML: есть ли данные, не решается ли задача правилами, окупает ли эффект сложность.
2. Заполнить шаблон гипотезы (7 шагов): проблема с числами → узкая ML-задача → данные → decision point → бизнес-метрика → метрика модели → критерии успеха по трём осям.
3. Зафиксировать простое baseline-решение, с которым сравниваем.
4. Офлайн-обучение и валидация: правильные метрики под задачу, проверка leakage (никаких данных «из будущего»), баланс Precision/Recall под цену ошибок.
5. Спроектировать онлайн-проверку: A/B с CUPED/ML-CUPED при высокой дисперсии, uplift-анализ при среднем эффекте ≈ 0; guardrail-метрики и пороги.
6. Принять решение по бизнес-метрике (а не по модельной), зафиксировать мониторинг дрейфа и план переобучения.
7. Записать выводы в базу знаний: что сработало, какие данные/признаки были решающими.

## Типичные ошибки
- «Улучшить выдачу/рекомендации» вместо узкой задачи с метрикой — не гипотеза.
- Нет бизнес-метрики: модельная точность как цель; AUC ради AUC.
- Нет данных (или данные не будут доступны в момент применения) — гипотезу всё равно отдают в разработку.
- Leakage: признаки, содержащие целевую информацию или «будущее»; офлайн-метрики завышены.
- Слепое доверие модели: нет baseline, нет sanity-check, нет бизнес-логики в проверке.
- Неверный баланс ошибок: для фрода оптимизируют Precision, теряя нарушителей (или наоборот — блокируют нормальных пользователей).
- Ковариата CUPED берётся из пост-тестового периода; разбиение групп не проверено на гомогенность.
- Дрейф данных не мониторится: модель «тихо» деградирует после запуска.
- Объяснимость: там, где модель затрагивает пользователей напрямую (модерация, цены, скоринг), чёрный ящик без объяснений и выборочного аудита решений — риск доверия и регуляторный риск.
- ML ради ML там, где правило/SQL дешевле, понятнее и надёжнее.

## Вопросы, которые могут изменить решение
- Есть ли данные с историей и разметкой — и будут ли они доступны в момент применения модели?
- Какая простая альтернатива (правила, среднее, наивный прогноз) и насколько ML должен её превзойти по бизнес-метрике?
- Какова цена ошибки модели в обе стороны и какой порог Precision/Recall ей соответствует?
- Как эффект будет проверен онлайн и какие guardrail-метрики могут пострадать?
- Что произойдёт с качеством модели через 3–6 месяцев (дрейф данных) и кто отвечает за переобучение?
