# Customer Journey Map: as-is, to-be, поиск барьеров и возможностей

## Когда применять
Когда нужно увидеть, на каком этапе пути клиент теряет результат и почему: перед выбором, что чинить или строить;
для привязки метрик (CSAT, drop-rate) к конкретным шагам; для общего языка команды. Без карты команда видит продукт
фрагментами, и идеи «размазываются» по поверхности вместо попадания в узкие места.

## Суть
**CJM** — визуальная карта пути клиента от возникновения потребности до повторного использования. Не путать:
- **User Flow** — шаги внутри интерфейса (клики, поля, экраны), без эмоций;
- **BPMN** — процесс с ролями, системами и временем ожидания; пользователь там один из «игроков»;
- **CJM** — опыт человека: цели, ожидания, мысли, эмоции, барьеры. Без эмоциональной линии это просто хронология.

**As-is** — как опыт устроен сейчас, строится строго на фактах. **To-be** — целевой опыт после изменений; пока не проверен
на людях, все его утверждения — гипотезы.

Слои карты (шаблон курса):

| Слой | Что фиксируем | Откуда брать |
|---|---|---|
| Этап жизненного цикла | Крупные фазы (осознание → поиск → сравнение → выбор → покупка → использование → лояльность) | Интервью, аналитика |
| Действия клиента | Что делает (без атомарных кликов) | Сессии, наблюдение, логи |
| Точки контакта | Канал/интерфейс: сайт, приложение, push, поддержка | Логи, маркетинг-план |
| Цели и ожидания | Зачем и на что рассчитывает | Интервью, JTBD |
| Мысли и вопросы | Что держит в голове, чего не хватает | Глубинки, поддержка |
| Эмоции | Состояние (слово или смайл, суть — чувство) | Цитаты, наблюдение |
| Барьеры / драйверы | Что мешает / помогает дойти до цели | Интервью, жалобы, NPS-комментарии |
| Важность шага | Насколько критичен для цели | Интервью, опрос |
| Опыт (факт) | Что реально получилось: быстро/долго/неудобно | Метрики, наблюдение |
| Метрика этапа | CSAT, drop-rate, Time-to-X | Аналитика |
| Рекомендации | Идеи улучшений рядом с болью | Воркшоп команды |
| Иллюстрации | Скрин/фото шага | Прототипы, видео |

Правило курса: **один факт — одна ссылка на источник.** Эмоция без цитаты или метрики — «фейковая боль».

## Процедура

### A. CJM as-is
1. **Рамка:** какой сегмент, какой сценарий, какая работа клиента ([[M-jtbd]]), где начало и конец пути. Одна роль на карту.
2. **Данные:** глубинные интервью, анкеты, поведенческая аналитика, обращения в поддержку, дневники, наблюдение и
   догфуддинг ([[M-dogfooding]]). Минимум два типа источников: «что говорят» + «что делают».
3. **Макро-этапы:** не больше 6–7 (при 10+ карта превращается в список). Атомарные действия без необходимости не писать.
4. **Заполнить слои для каждого этапа:** действия → контакты → мысли/вопросы → эмоции → барьеры/драйверы. Каждая ячейка
   несёт тег источника: [цитата n=…], [метрика], [поддержка], [наблюдение]; нет источника — [гипотеза] (можно, но визуально отличать).
5. **Метрика под барьером:** CSAT этапа, drop-rate, время; без цифры карта остаётся постером.
6. **Выделить боли:** отметить этапы, где совпадают минимум два сигнала (падение метрики, негатив в цитатах, ошибка/стоп
   при наблюдении, звонки в поддержку).
7. **Приоритизация:** оценка Боль × Важность (× охват сегмента). В воркшопе — молчаливое голосование точками (по 3 на человека).
8. **Гипотезы для топ-3 барьеров:** Job Story + метрика (baseline → целевой сдвиг) + владелец + грубая оценка трудозатрат.
9. **Версия и срок:** дата, владелец (обычно владелец продукта). В курсе рекомендация — пересмотр раз в квартал или после крупного релиза.

### B. Экспресс-воркшоп на 40 минут (если нужна быстрая диагностика)
Роли: фасилитатор, продакт, аналитик, дизайнер, разработчик. Вход: 2–3 свежих интервью, дашборд по ключевым этапам, топ-10 обращений в поддержку.

| Минуты | Действие | Выход |
|---|---|---|
| 0–5 | Цель, ключевая метрика, правила | Фокус |
| 5–15 | Этапы + 1–2 действия на этап | Скелет |
| 15–25 | Боли и эмоции | Красные/синие стикеры |
| 25–30 | Молчаливое голосование точками | Топ болей |
| 30–35 | Гипотеза на каждую: Job Story, метрика, сдвиг | 2–3 гипотезы |
| 35–40 | Владелец, грубая оценка, срок проверки | План |

Подробнее о ведении сессии — [[M-workshops]].

### C. Как находить барьеры и возможности
- **Барьер** = шаг, где путь рвётся: падение конверсии, возврат назад, пауза >3 с, вопрос вслух («а это точно сюда?»),
  ошибка без объяснения, обходной путь, звонок в поддержку.
- **Тревога** = эмоциональный провал при нормальных действиях (клиент сделал всё, но не уверен, что получилось — типичный
  пример: нет подтверждения или статуса).
- **Возможность** = важный для цели шаг с низким опытом (важность высокая, опыт низкий); массовый обходной путь (люди сами
  придумали замену); недообслуженная работа из опроса важность×удовлетворённость; шаг, где конкурент даёт заметно лучший опыт ([[M-competitors]]).
- **Закономерность, а не случай:** одно наблюдение — случай, повторение у двоих и более — кандидат в паттерн; подтверждать метрикой.
- **Запись барьера:** Этап | Описание (что видно/слышно) | Источник и n | Метрика | Влияние | Гипотеза причины | Что проверить.

### D. CJM to-be
1. Взять топ-барьеры as-is. На каждый — 1–3 варианта изменения (идеи — [[M-design-thinking]], [[M-solution-design]]).
2. Перерисовать затронутые этапы: новые точки контакта/шаги, **ожидаемая** эмоция, **ожидаемая** метрика. Подписать все
   ячейки «гипотеза» до проверки.
3. Проверить ключевые изменения на прототипе ([[M-usability-testing]]) и/или экспериментом ([[M-mvp-pilots]]).
4. Обновить карту фактами после проверки; закрыть гипотезы со статусом «подтверждена / опровергнута» ([[M-ux-backlog]]).

### E. Связь с метриками
CSAT по этапу (короткий опрос после действия); процессные метрики (Time-to-X, drop-rate); алерты при отклонениях;
ключевой этап ценности привязывается к главной метрике продукта ([[M-product-metrics]]). Эффект изменения сравнивать до/после
по одному окну и сегменту.

## Шаблон / чек-лист

**Строка барьера для бэклога:**
`Этап | Барьер (факт) | Источник/n | Метрика (baseline) | Job Story | Гипотеза решения | Целевой сдвиг | Владелец | Статус (гипотеза/подтверждено/опровергнуто)`

**Готовность карты к использованию:**
- Этапы покрывают путь «потребность → результат/лояльность»; не больше 6–7.
- У каждого этапа есть действия, мысли, эмоции.
- Барьеры и драйверы имеют источник; без него помечены как гипотезы.
- Для топ-3 барьеров есть Job Story, метрика и запись в бэклоге.
- Версия, дата, владелец указаны; срок пересмотра назначен.
- Карта построена на одной роли и одном сценарии.

## Типичные ошибки
| Ошибка | Итог | Правильный ход |
|---|---|---|
| Карта рисуется внутри команды по предположениям | Подтверждение своих гипотез | Опираться на истории и данные пользователей, цитаты |
| Смешаны роли (клиент + курьер + склад) | Получился BPMN | Один человек — одна карта |
| Нет эмоций | Чек-лист действий, не опыт | Добавить эмоциональную линию с цитатами |
| Слишком мелкие шаги | 100 клеток, нет инсайта | Макро-этапы, детали — в User Flow |
| Пропущены «раздражающие, но малозначимые» моменты | Люди уходят именно там | Фиксировать и их |
| Нет метрик | «Красивая картинка» | Метрика этапа под каждым топ-барьером |
| Карта лежит отдельно от бэклога | Умирает после релизной гонки | Линковать боль → тикет |
| To-be выдаётся за факт | Ложная уверенность | Все ячейки to-be — гипотезы до проверки |
| Карта устарела (>6 мес.) | Отражает прошлый продукт | Регулярный пересмотр |

## Вопросы, которые могут изменить решение
- Для какого сегмента и сценария строится карта? Есть ли разные пути у новичков и опытных?
- Какие данные реально доступны (логи, интервью, поддержка)? Если только мнение команды — карта будет гипотезой целиком.
- Где заканчивается ответственность продукта (доставка, поддержка, офлайн)? Это CX-проблемы, не интерфейс ([[M-ux-backlog]]).
- Есть ли метрика, по которой видно этап (event в аналитике)? Если нет — сначала настроить измерение.
- Нужен ли as-is целиком или достаточно узкого участка (тогда User Flow)?
