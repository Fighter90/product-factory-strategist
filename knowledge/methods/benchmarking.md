# Бенчмаркинг: эталонные значения метрик и проверка их применимости

## Когда применять
«Какой retention/конверсия/churn/CAC считается нормальным?», «наши метрики хуже или лучше рынка?», «откуда взять допущение для модели, где нет данных?», «этой цифре из статьи можно верить?», «какие best practices взять?». Карта не содержит готовых числовых бенчмарков — она описывает, как их находить и проверять; числа берутся из источников с указанием класса достоверности ([[M-source-criticism]]).

## Суть
**Бенчмарк** — эталонное значение метрики для сравнения. Что считать «эталоном», зависит от цели: лучшее (P95/P99) — ориентир стремления; медиана (P50) — реалистичный уровень индустрии; минимум (P25) — ниже опасно. Всегда использовать **диапазон P25–P50–P95**, а не одно число; бенчмарк — компас, не закон.

Зачем: приоритизировать фичи, найти слабые места, ставить KPI/OKR, калибровать модель (sanity check, калибровка, объяснение отклонений — [[M-traction-model]]).

**Типы метрик и обязательные срезы**
| Тип | Что уточнять |
|---|---|
| Воронка (визит → регистрация → активация → покупка) | новый/возвратный; канал (холодный/тёплый, органика/реклама); платформа (web/mobile, iOS/Android); регион, язык; тип клиента (SMB, Mid-Market, Enterprise) |
| Retention | платящие/бесплатные; когорты по периодам запуска; окно: D1/D7/D30 для потребительских приложений, M1/M3/M12 для B2B SaaS; критерий (любое действие или платящее) |
| Churn | logo churn (% клиентов), revenue churn (% выручки), gross vs net (минус расширение у оставшихся); новые и старые клиенты отдельно |
| Монетизация (UE, LTV, CAC, ARPU) | новые/существующие платящие; валюта и налоги (gross/net revenue); постоянные затраты вне UE; покупательная способность региона (CTR/CPC между странами различаются в 5+ раз по оценке скилла); core vs casual |

**Смещения:** survivorship bias (худшие молчат — видимое среднее выше реального); vendor bias (платформа преувеличивает проблему ради продажи решения); стартапы публикуют лестные метрики (LTV/CAC = 5 на лучшем сегменте); слишком ровные числа (10%, 50%) — вероятно оценка; контекст-убийца (25% чего: D30? D90? платящих?); устаревшие данные.

## Процедура
1. **Определить метрику:** формула, единицы, период, когорта, критерий активности. Пример определения из шаблона скилла — D30 retention; в шаблоне формула записана как `DAU[Day30]/DAU[Day1]`, это образец заполнения: свою метрику фиксируй как «доля пользователей когорты, активных в день N по критерию Z».
2. **Найти источники:** поиск (с фильтром по дате и типу источника); эксперты (инвесторы, ангелы, коллеги по нише, консультанты); отчёты Sequoia, Y Combinator, Greylock, Reforge, Mixpanel, Amplitude, First Round Review; публичная отчётность компаний; собственные A/B и история.
3. **Проверить каждый бенчмарк (7 шагов):**
   1. Происхождение: первичный или пересказ; автор.
   2. Методология: выборка, сегменты, период сбора, определение метрики.
   3. Актуальность: быстро меняющиеся (CAC, CPI, retention) — не старше 24 месяцев; стабильные (валовая маржа, долгосрочный LTV) — допустимо до 3–5 лет.
   4. Сопоставимость: вертикаль/продукт, бизнес-модель, география и язык, целевой сегмент, стадия компании, канал, сезонность, возраст продукта.
   5. Триангуляция: минимум 3 независимых подтверждения; разброс более 30% — осторожность.
   6. Смещения: survivorship, vendor, лестность, «ровные числа».
   7. Диапазон и уровень доверия: P25/P50/P95 + High/Medium/Low (сопоставим с классами A–D в [[M-source-criticism]]).
4. **Оценить сопоставимость по пяти осям** (эвристика карты): определение метрики, сегмент/клиент, период и сезон, бизнес-модель и канал, стадия и география. Все 5 совпали — использовать как есть; 3–4 — скорректировать и объяснить поправку; 2 и меньше — только как порядок величины и гипотеза для проверки.
5. **Сравнить своё значение с диапазоном:** ниже P25 / между P25–P50 / выше P50 / выше P95 (подозрение на ошибку измерения); объяснить отклонение (канал, модель, сегмент, возраст продукта).
6. **Использовать в решении:** цель OKR, допущение модели (с дисконтом, если источник слабый), sensitivity вокруг диапазона.
7. **Best practices:** собрать 3 приоритетных практики (UX/UI, онбординг, юридика, логистика, монетизация, нотификации) через насмотренность на конкурентов, поиск, интервью экспертов, конференции; для каждой — ожидаемый эффект, сложность, источник. Эффект «+X% retention» из чужого кейса — гипотеза, а не прогноз.

## Шаблон / чек-лист
Паспорт: метрика · период исследования · сегменты · источники · автор · дата актуализации.
Таблица бенчмарков:
| Метрика | Определение / формула | P25 / P50 / P95 | Источники (ссылка в тексте) | Возраст данных | Сопоставимость (1–5) | Замечания | Confidence |
|---|---|---|---|---|---|---|---|
Таблица практик: практика · область · описание · ожидаемый результат · сложность · источник.
Выводы: где ниже бенчмарка и почему; какие практики первыми; какие KPI на квартал.

Чек-лист:
- [ ] Метрика и способ измерения определены
- [ ] Найдено минимум 3 источника
- [ ] Для каждой цифры известно происхождение (первичный/вторичный)
- [ ] Возраст в допуске (24 мес. для быстрых; 3–5 лет для стабильных)
- [ ] Сопоставимость по вертикали, модели, гео, сегменту, стадии
- [ ] Построен диапазон и указан уровень доверия
- [ ] Учтён survivorship bias
- [ ] Выбраны top-3 практики; KPI поставлены на основе диапазона

## Типичные ошибки
- Взять одно «среднее» число из одной статьи.
- Сравнивать B2C-приложение с B2B SaaS, SMB с Enterprise, Россию с США без поправки.
- Брать retention за один день и сравнивать с retention за 30 дней.
- Принять число вендора за независимое (Amplitude скажет, что плохой retention — беда).
- Использовать бенчмарк трёхлетней давности для быстро меняющихся метрик.
- Ставить цель по P95 без плана, как её достичь.
- Копировать best practice без проверки сегмента и канала.

## Вопросы, которые могут изменить решение
- Чья метрика сравнивается: платящих или всех, новых или возвращающихся?
- Какой канал даёт основной трафик (SMM — низкий retention, партнёры — высокий)?
- Какой возраст продукта (у молодых приложений бывает скачок retention в месяцы 2–6)?
- Решение чувствительно к этому допущению? Если да — тратить время на сбор собственных данных или мини-эксперимент вместо бенчмарка.
- Можно ли получить ретро-данные или proxy-метрики (близкий регион, сегмент, продукт)?
