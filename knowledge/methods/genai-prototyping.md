# GenAI-прототип: спроектировать, собрать, протестировать

## Когда применять
Когда решение спроектировано ([[M-genai-assistant-architecture]]) и нужно за дни, а не недели, проверить главное —
достижимость ли нужного качества на ваших данных — и решить: развивать, дорабатывать или закрыть. Прототип — источник
знаний о задаче, а не первая версия продукта: «у конкурента работает» не заменяет проверку, потому что у них другие
данные, нагрузка и аудитория.

## Суть

**Четыре задачи прототипа**, главная из них одна: образ решения (как это будет работать — частично заменяемо макетом);
ценность (нужно ли пользователю — проверяется интервью и аналитикой поведения, прототип даёт сигналы, не статистику);
**достижимость качества — ничем, кроме прототипа, не проверяется**; порядок стоимости (не цифра для бюджета: вниз
стоимость снижается оптимизациями, вверх — вырастает от длинных диалогов и повторных обращений).

**Требования к проверке (без них результату нельзя верить):** достоверность — выборка взята случайно из реальных
данных, модель — сильнейшая доступная; интерпретируемость — видно, в каких случаях и почему не сработало; скорость —
дни, срок назван до начала; стоимость проверки — доли от стоимости разработки. Типичный провал: три недели на 15
вручную отобранных примерах и вывод «можно запускать» — нарушены три требования из четырёх.

**Скоуп:** основной сценарий — целиком (ради него делается продукт); реальные данные — без чистки (очистка завышает
результат); типовые И трудные случаи; сильнейшая модель (отделяет «не решается» от «модель слабая»); простой
инструмент сборки; без оптимизаций скорости, обработки сбоев и аккуратного кода. Результаты прогона сохраняются —
иначе версии не сравнить.

**Инструменты** различаются тем, что нужно сделать ради результата: чат с моделью (нащупать промпт, понять, справляется
ли модель в принципе); песочница/консоль (системный промпт и параметры отдельно, объявление инструментов, экспорт кода —
но функцию сама не выполнит); конструктор ассистентов (постоянная инструкция + свои файлы, внутренний помощник; в свой
продукт не встроить); генератор приложений (образ решения и проверка на живых пользователях, но прогон по выборке
придётся строить отдельно); платформа визуальных сценариев (workflow из блоков, прогон по выборке с историей каждого
шага — то, что нужно для проверки достижимости); код (всё возможно, но правки через разработчика). Критерии выбора:
нужен ли прогон по выборке, свой интерфейс, скорость освоения, кто в команде может собрать.

## Процедура

### 1. Написать постановку задачи на прототип (до сборки)
| # | Раздел | Что фиксируется |
|---|---|---|
| 01 | Вход | триггер (когда срабатывает), данные, запрос пользователя |
| 02 | Выход | формат (связный текст для человека / структура для интерфейса); обязательные элементы каждого ответа — основа критерия приёмки |
| 03 | Источники данных | что система читает дополнительно к входу (внутренние сервисы, справочники, веб); чем больше источников, тем сложнее сборка |
| 04 | Правила поведения | чего не утверждает никогда; что делает при нехватке данных (прямо сказать или отказаться); о чём не рассуждает без уточнения |
| 05 | Критерий приёмки | словесное описание приемлемого ответа; кто принимает (продакт + эксперты); что считаем провалом |

Ловушка постановки: описывать форму, а не содержание. «Рекомендация есть» выполняется буквально и бесполезно («берите
первую» без довода). Требование формулируют так, чтобы его нельзя было выполнить бессмысленно: «рекомендация опирается
на названные в ответе отличия, каждый тезис подтверждается данными объявления, выдуманных фактов нет».

### 2. Собрать минимально
1. Базовая схема: триггер → вызов модели (системный промпт + вход) → ответ. Сценарий добавляет проверку входа, второй
   вызов или ответ по полям; агентная логика — по паттернам из [[M-genai-assistant-architecture]].
2. Прогон по выборке должен быть встроен в механику инструмента: данные между шагами передаются списком элементов —
   каждая нода обрабатывает каждый элемент, цикл писать не нужно. Промпт собирается выражениями из полей таблицы.
3. Роли (даже в группе из 3–4 человек): сборщик (воркфлоу, экран), автор промпта, тестировщик (приносит разные примеры
   и замечает плохие ответы), докладчик. Ошибки сборки видны сразу (упало/молчит), ошибки качества — только на разных
   примерах.
4. Техническая гигиена прогона: сбой одного элемента не останавливает прогон (обработка ошибки «продолжить»); история
   запусков сохраняет вход и выход каждой ноды; ответ пишется обратно в строку выборки (run-колонка), оценка — в
   соседнюю (eval-колонка); между замерами выборка не меняется.

### 3. Протестировать: алгоритм
1. **Сценарии:** выписать из постановки основной сценарий и трудные случаи (нехватка данных, противоречивые данные,
   несравнимые пары) — они и есть тестовые ситуации.
2. **Золотой набор:** фиксированная выборка реальных примеров (сотни, не единицы), случайно взятая, без чистки, с
   трудными случаями; хранится и не меняется между прогонами.
3. **Регресс-прогон:** полная обработка золотого набора текущей версией; ответы и история шагов сохраняются. Любая
   правка промпта/модели/архитектуры = повторный прогон того же набора.
4. **Разметка качества** (сначала читают, потом считают):
   - пометки свободным текстом — всегда первыми, на первых 20–30 ответах: что не так своими словами («выдумал
     характеристику, которой нет», а не «плохо»);
   - чек-лист — вопросы да/нет, пункты берутся из пометок (отличия подтверждаются данными? рекомендация опирается на
     отличия? выдуманных фактов нет?); даёт картину «что чинить», а не одну цифру;
   - бинарная разметка «приемлемо/нет» — когда критерий приёмки уже сформулирован; порог называется ДО прогона
     (доля после просмотра = подгонка);
   - парное сравнение вслепую — «стало ли лучше» против текущего опыта пользователя или прошлой версии; лучший из двух
     может всё равно быть плохим.
5. **Метрики трёх видов:** качество (доля приемлемых по бинарной разметке + разбивка по пунктам чек-листа + ноль
   недопустимых ошибок); стоимость (цена ответа по токенам входа/выхода и числу вызовов; проверка «а по самой дешёвой
   модели при том же объёме сходится ли?»); латентность (время ответа на выборке, TTFT/TPOT по наблюдаемым цифрам).
6. **Найти источник каждой плохой ошибки** — вопросы по порядку, от дешёвой проверки к дорогой:
   | Вопрос | Где смотреть | Если нет |
   |---|---|---|
   | Дошли ли данные до модели? | история запусков, вход вызова модели | сборка (выражения, разбор полей) |
   | Есть ли ответ в самих данных? | исходный пример | данные (правило поведения при нехватке, внешний источник) |
   | Просит ли промпт то, что нужно пользователю? | промпт, прочитанный буквально | постановка (требования, правила для трудных случаев) |
   | Всё выше в порядке, а ответ плохой | — | модель (упростить/разбить задачу, пример хорошего ответа, шаг проверки, модель сильнее) |
   Частые ловушки: переписывать промпт, когда модель просто не получила данных; требовать от модели ответ, которого нет
   в данных (она его выдумает); менять модель, когда промпт выполняется буквально; объявлять задачу нерешаемой по
   слабой модели.
7. **Решить судьбу прототипа** — вопросы по порядку:
   - критерий приёмки выполнен (доля приемлемых ≥ порога, недопустимых ошибок нет)? → **развивать**: разработка с
     учётом узнанного, оставшиеся ошибки передаются как известные риски;
   - среди ошибок есть исправимые (сборка, данные, постановка)? → **доработать**: план «что меняем / как проверяем /
     когда останавливаемся» — по одному источнику ошибок за итерацию, тот же прогон на той же выборке, порог и лимит
     итераций названы до первого прогона;
   - ошибки только модельные, проверены на сильнейшей модели и с изменённой архитектурой? → **закрыть**: зафиксировать,
     почему. Это законченный ответ о достижимости, полученный за недели, а не провал.
   Экономика решает независимо от качества: если даже на самой дешёвой модели ответ дороже, чем продукт готов платить,
   — закрыть. Если сходится — цену снижают на доводке, решение она не меняет. Порог после прогона не поднимают.

## Шаблон / чек-лист

**Постановка на прототип:** триггер; входные данные; формат выхода + обязательные элементы; источники; правила
поведения при нехватке данных; словесный критерий приёмки; кто принимает; что считается провалом; срок (в днях).

**Чек-лист прогона:** выборка случайная из реальных данных; трудные случаи включены; модель — сильнейшая доступная;
сбой не останавливает прогон; ответы сохранены в run-колонку; история шагов доступна для разбора; выборка не менялась
между прогонами.

**Чек-лист решения:** разметка сделана после чтения ответов; порог назван до прогона; источники ошибок классифицированы
(сборка/данные/постановка/модель); стоимость посчитана и по самой дешёвой модели; латентность измерена; решение
(развивать/дорабатывать/закрыть) зафиксировано с основаниями.

## Типичные ошибки
| Ошибка | Почему плохо | Как избежать |
|---|---|---|
| Прототип как первая версия продукта | Три недели работы тянут в прод вместе с костылями | Прототип выбрасывают; разработка начинается с учётом узнанного |
| Ручной отбор «красивых» примеров | Результату нельзя верить | Случайная выборка из реальных данных |
| Чистка данных перед прогоном | Завышает результат: в проде данные будут грязными | Прогон на данных как есть |
| «Работает у конкурента» как доказательство | Другие данные, нагрузка, аудитория | Свой прототип на своих данных |
| Считать метрику до чтения ответов | Мерят то, что легко посчитать, а не то, что ломается | Пометки текстом → чек-лист → бинарная разметка |
| Порог приёмки после просмотра результатов | Подгонка под результат | Порог и лимит итераций называются до прогона |
| Одна цифра «82 из 100 приемлемо» | Не говорит, что чинить | Разбивка по пунктам чек-листа + классификация источников ошибок |
| Править всё сразу | Непонятно, что сработало | Один источник ошибок за итерацию, тот же прогон |
| Доводить прототип за порогом приёмки «до идеала» | Доводка промпта не переходит в продукт: там другая архитектура | Критерий выполнен → развивать; остатки — известные риски |
| Вывод «не решается» на бюджетной модели | Смешаны «задача нерешаема» и «модель слаба» | Вердикт о недостижимости — только на сильнейшей модели |

## Вопросы, которые могут изменить решение
- Можно ли описать процесс по постановке (вход/выход/правила/критерий)? Если нет — рано собирать, сначала дизайн задачи.
- Каков объём выборки и есть ли трудные случаи в данных? Десятки примеров не отвечают на вопрос о достижимости.
- Сходится ли экономика при самой дешёвой модели на полном объёме? Если нет — качество не спасёт.
- Какие ошибки недопустимы в принципе (выдуманный факт, неверный вердикт) и есть ли их ноль в прогоне?
- Чем прототип отличается от будущего продукта (архитектура, объём данных, нагрузка) и что из узнанного переносится?
