# Экономика платформы: TCO, эффекты, финмодель, метрики

## Когда применять
«Сходится ли экономика платформы и как это доказать комитету?», «с чем сравнивать платформу и как считать эффект?», «когда окупится и при каком числе подключений?», «какие допущения критичны и как их проверять?». Берётся после концепции ([[M-platform-case-concept]]); связана с юнит-экономикой ([[M-unit-economics]]).

## Суть
Экономика платформы = три части: **TCO** (затраты на разработку, поддержку и интеграции) + **бизнес-эффект** (что станет быстрее, больше, лучше — переведённое в деньги) + **сравнение с альтернативами** (As Is без платформы vs To Be с платформой). Прямой «бизнес-эффект от платформы как продукта» защищать сложно — обычно идут через сравнение TCO платформы и альтернатив.

### Структура затрат
| Локальные решения | Платформа |
|---|---|
| Разработка в каждой команде | Ядро и запуск |
| Повторные доработки | Интеграции клиентов |
| Поддержка и инфраструктура | Миграция и запуски на стороне клиентов; инфраструктура |

Затраты делятся на **разовые** (создание ядра, архитектурные изменения, миграция и инструменты перехода) и **регулярные** (команда платформы, поддержка клиентов, документация). Для внешнего рынка добавляются CAPEX (материальные активы, например серверы) с амортизацией (non-cash, не входит в cash costs) и OPEX (эксплуатация). Единица измерения трудозатрат — FTE-месяц по средней стоимости сотрудника в организации; полную финмодель дорабатывают финансы.

### Шесть источников эффекта
1. Дополнительная выручка или рост других пользовательских метрик. 2. Инфраструктурная экономия. 3. Ускорение запуска (TTM). 4. Снижение run-затрат. 5. Экономия на разработке (несозданные команды и решения). 6. Предотвращённые потери.

### Ключевые формулы
- **Базовое сравнение:** `ΔFCF = FCF_ToBe − FCF_AsIs` по годам; `Cumulative ΔFCF = Σ ΔFCF`; **break-even** — первый год, где накопленный ΔFCF ≥ 0.
- **Порог окупаемости (break-even по числу клиентов):** `Число запусков = (Build + Run за горизонт) / Экономия на один запуск`, где экономия на запуск = (разработка local + поддержка local − подключение к платформе).
- **ROI** = (выгода − затраты) / затраты; **IRR** — ставка дисконтирования, при которой NPV потока ΔFCF = 0 (важнее ROI для комитета).
- **WACC** — средневзвешенная стоимость капитала; выше риск → выше ставка. **Дисконтирование:** `PV = ΔFCF_t / (1+WACC)^t`.
- **Terminal value:** `TV_T = FCF_T_устойчивый / WACC` (только устойчивый годовой FCF после горизонта); `NPV = Σ PV ΔFCF + PV TV`.
- **Инкрементальный эффект (CRM-тип):** `Аудитория → Покрытие (доля дошедших) → Конверсия (доля целевого действия) → Инкремент (разница с контролем, A/B) → Ценность (инкремент × ценность действия → выручка, EBITDA, FCF)`. Инкремент считают от **выручки компании**, не от GMV и не от тейк-рейта напрямую; выручка ≠ маржа (инкремент в объёме продаж при крошечной марже почти ничего не стоит в деньгах).
- **TTM-эффект:** `Экономия/эффект = (Срок запуска local − срок запуска с платформой) × маржинальный эффект в месяц × число запусков`.
- **Для экосистемных (рыночных) платформ:** `Revenue платформы = GMV × take rate`; take rate можно дифференцировать по сторонам; дефицитную сторону субсидируют (бесплатно/отрицательная цена), монетизируют сторону, чья ценность растёт от ликвидности; юнит-экономику считают по сторонам и когортам ([[M-unit-economics]]); ликвидность (доля успешно завершённых поиск→сделка) — главный индикатор здоровья; сетевые эффекты и multi-homing влияют на устойчивость take rate ([[M-platforms-types-criteria]]).

### Метрики платформы
Количество клиентов-команд; количество использований платформы; TTM подключения к платформе; инкрементальный эффект на пользователей «с платформой / без». Adoption платформы отдельно ([[M-platform-risks-rollout]]): по клиентам (ширина базы), по местам/компонентам (глубина замены), по объёму (доля трафика/показов через платформу).

## Процедура
1. **Зафиксировать управленческое решение**, которое должна поддержать модель: запускать / сузить scope / отложить / отказаться / назвать критическое условие / назначить следующую проверку.
2. **Собрать бизнес-кейс из 10 блоков:** часть 1 — проблема, решение, клиенты, альтернатива, adoption (кто и когда подключится); часть 2 — эффект (за счёт чего), затраты, срок окупаемости, сценарии, рекомендация.
3. **Построить модель As Is / To Be** (учебный каркас):
   - Допущения: горизонт (например 3–4 года), график подключений по годам, стоимость FTE-месяца, затраты local (разработка + поддержка на один запуск), build платформы, run в год, стоимость подключения.
   - As Is: `FCF_AsIs = −(затраты local × N_запусков)`.
   - To Be: `FCF_ToBe = −Build − Run − (подключение × N)`.
   - ΔFCF, накопленный поток, break-even. Затем — строка эффектов (экономия на платежах/инфраструктуре, ранний запуск) поверх базового ΔFCF.
4. **Посчитать ROI, IRR, окупаемость, break-even по числу клиентов**; при необходимости WACC, TV, NPV.
5. **Проверить сценарии** (консервативный / базовый / оптимистичный) по чувствительным параметрам: число подключений, затраты local, стоимость build и run, стоимость подключения, темп adoption. Правило честности: цифры брать из утверждённых планов и фактических затрат своей и соседних команд, не из отраслевых бенчмарков — любую строку должно быть можно проверить.
6. **Зарегистрировать допущения** по схеме: параметр и значение → источник (экспертная оценка / прошлые продукты / бенчмарк) → допустимый диапазон → владелец допущения → как и когда проверить.
7. **Связать модель с roadmap** — экономика меняется по этапам и на каждом принимается своё решение: Discovery (оценить диапазон) → Build (инвестировать в ядро) → Pilot (проверить клиента) → Scale (подключать следующих) → Close (выключить legacy-решение).
8. **Сформулировать управленческий вывод:** решение, ограничения, следующий шаг. Для ПР-уровня сдачи: три страницы — решение и альтернатива, экономика, результат и рекомендация.

### Пример (иллюстративные числа, учебная финмодель)
Платформа приёма платежей: local — 15 FTE-мес. разработки (4,5 млн ₽) + 24 FTE-мес. поддержки (7,2 млн ₽/год) на один запуск; платформа — build 30 млн ₽, run 12 млн ₽/год, подключение 2 FTE-мес. (0,6 млн ₽); запуски по годам 0/2/3/4; горизонт 3 года.
- Только TCO: ΔFCF = −30 / +10,2 / +21,3 / +32,4; накопленно: −30 / −19,8 / +1,5 / +33,9 → окупаемость в год 2; IRR ≈ 40%.
- Порог break-even: экономия на запуск = 4,5 + 7,2 − 0,6 = 11,1; затраты = 30 + 12×3 = 66 → 66 / 11,1 ≈ 6 запусков. Меньше шести — не окупается, решение зависит от плана запусков.
- С эффектами (экономия на эквайринге +2 млн ₽/мес., ранний запуск 3 мес. × 2 млн ₽ × N): ΔFCF = −30 / +46,2 / +63,3 / +80,4 → окупаемость ~8 мес. года 1; консервативный сценарий (5 запусков) всё равно положителен только с эффектами — зависимость от adoption критична.

Автопроверки:
- Выручка ≠ маржа; инкремент от выручки, не от GMV; маржа указана отдельно.
- Одинаковые единицы и периоды в FTE-месяцах, годах и рублях; dual run (параллельная работа двух систем) и миграция включены в затраты платформы, а не потеряны.
- Эффект считается только на продуктах из утверждённого плана; «продукты, которые могли бы появиться», в модель не входят.
- Cumulative ΔFCF ≥ 0 в каком-то году → год окупаемости назван; в консервативном сценарии не сходитесь — это и есть вывод.
- Модель пересчитывается на каждом ревью; изменившиеся цифры объяснены.

## Типичные ошибки
- Весь GMV через платформу записать её дополнительной выручкой — эффект считается как ΔFCF двух сценариев, «с платформой» и «без».
- Игнорировать миграцию, dual run и поддержку клиентов — TCO платформы занижено.
- Экономию FTE записать как денежный эффект, если люди остаются в компании и не сокращаются.
- Одна точечная оценка вместо диапазона и сценариев; бенчмарк вместо фактических затрат своих команд.
- ROI вместо IRR как единственный аргумент; забытый TV при устойчивом потоке (или наоборот — TV при неустойчивом).
- Статическая модель: не пересчитана после пилота, хотя экономика обязана уточняться вместе с roadmap.

## Вопросы, которые могут изменить решение
- Сколько запусков реально в утверждённом плане на 3–4 года (консервативный сценарий окупается?).
- Какой параметр в модели самый чувствительный и кто владелец его проверки?
- Экономия — денежная или «освобождённые люди»? Что с ними произойдёт?
- Сколько дней работы клиента стоит подключение — и за счёт чего его снизить?
- Появится ли кросс-продуктовый эффект (единый контур, сквозная лояльность, антифрод) только при доле выше порога — и входит ли он в модель?
- Для рыночной платформы: какой take rate по сторонам выдержит конкуренция и multi-homing?
