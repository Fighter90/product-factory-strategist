# Юзабилити-тестирование: прототипы, модерируемые и немодерируемые тесты, метрики

## Когда применять
Когда нужно проверить на реальных людях, понятен ли интерфейс или сценарий, и увидеть, где и почему люди ошибаются — до
разработки (на прототипе) или после запуска. UX-тест отвечает на «как» и «почему», не на «что изменится в метрике»:
выбрать цвет кнопки или вариант страницы заказа ради конверсии можно только экспериментом (A/B), а UX-тест даст гипотезы и причины.

## Суть
- **Модерируемый тест** (качественный): исследователь наблюдает, как участник решает реалистичные задачи, и уточняет «почему».
  Нужен для нового, сложного, ветвящегося, первого концепта; даёт эмоции и ментальную модель. Минусы: эффект наблюдателя,
  социальная желательность, дороже.
- **Немодерируемый тест** (количественный «что» и «сколько»): участник идёт по ссылке сам, платформа пишет клики, время, ответы.
  Быстро, дёшево, масштабно; нельзя уточнить, ошибка в задании портит все данные, нет контекста.
- **RITE**: после 2–3 сессий критичную проблему сразу чинят и следующие участники видят новую версию. Только для прототипов,
  нужна включённость дизайнера.
- **Полевой / контекстный** формат — когда окружение критично (курьер в движении, плохая связь, солнце на экране).
- Эвристики (внутри команды, без пользователей) — быстрый фильтр до тестов: [[M-ux-heuristics]].

**Выбор метода (по цели):**

| Вопрос | Метод |
|---|---|
| Заметят ли блок, поймут ли ценность, будут ли пользоваться (новый блок на карточке) | Модерируемый |
| Почему бросают процесс на полпути (статистика есть, причина неясна) | Модерируемый (аналитика — где, тест — почему) |
| Удобство в реальных условиях (курьер: езда, свет, связь) | Полевой модерируемый / контекстное интервью |
| Понимают ли термины («углеродный след») | Тест интерпретации на выборке; модерируемый — если нужно понять мышление |
| Заметен ли элемент, находят ли раздел | First click / 5-секундный |
| Какой из 2–3 вариантов предпочитают | Preference (субъективно); поведение — только A/B |
| Как люди группируют разделы | Card sorting (открытая/закрытая) и tree testing |
| Простой линейный сценарий в 2–5 экранов | Сценарное немодерируемое |
| Быстрая обратная связь по прототипу в процессе | RITE, микро-проверки (5–10 мин) |
| Влияние на конверсию | Только эксперимент (A/B) |

## Процедура

### 1. Подготовка прототипа
1. Прототип — способ ошибаться дёшево, но не презентация: кликабельные экраны, связанные переходы, все состояния сценария
   (ошибка, пусто, загрузка, успех). Инструменты: Figma (кадры, автолейаут, компоненты дизайн-системы, ссылки между экранами),
   бумажный прототип, «волшебник страны Оз» (человек имитирует систему — для ассистентов, голосовых интерфейсов).
2. Фиделити по цели: проверка понимания смысла — достаточно статичных кадров; проверка потока — кликабельный путь.
3. Правило «3-S» для задания: один путь, короткая задача, конкретная цель; сценарий проходит без тупиков.
4. Подстраховка: PNG-слайды всех состояний, ссылка проверена в режиме инкогнито, сухой прогон с коллегой.
5. Пример из курса (резюме в один клик, данные лекции): тест показал, что участники не понимали, что резюме нужно опубликовать
   в чате, и думали, что оно уже отправлено одному работодателю; вынесенный отдельный экран «черновик → опубликовать» воспринимался
   легче, а по итогам A/B лекция называет рост базы резюме +158% и покупок +142%. Вывод: тест нашёл причину, эксперимент измерил эффект.

### 2. Модерируемый тест
1. **Бриф:** какой вопрос, какое решение зависит, какой флоу, какие сегменты. Разложить user flow на этапы с контрольными точками.
2. **Гипотезы** (формат: проблема + место в сценарии + ожидаемое наблюдаемое поведение; не «пользователь поймёт интерфейс»,
   а «заметит кнопку фильтров в первые 5 с», «выберет пункт выдачи за ≤20 с без возврата»). Не более трёх на сессию; одна гипотеза — одна задача.
3. **Гайд:** гипотезы → вводное интервью (опыт, привычки, контекст) → формулировки заданий → критерии успеха (измеримые, до теста) →
   вопросы для проверки гипотез → завершающие вопросы. Карта «задача → шаги → видимый результат».
4. **Формулировка задания:** контекст («вы решили заняться бегом…») + мотив + ограничения; цель без названий элементов интерфейса
   («нажмите “Оформить”» нельзя); одинаковый текст для всех участников; контекст не выдумывать, не терять. Плохо: «Купите
   кроссовки в приложении». Лучше: ситуация, зачем, бюджет/предпочтения, результат.
5. **Рекрутинг:** сегмент и поведенческий профиль, устройство; исключить профессионалов UX/IT, если это не ЦА; запас +20% на неявку;
   согласие на запись и обработку персональных данных. Выборка: 5 человек на сегмент (оценка Нильсена ~80% проблем), для первого
   тестирования сложного интерфейса 5–8; сценарий из 10–15 экранов или несколько сегментов — больше.
6. **Пилот** на коллеге/одном респонденте: опечатки, тайминг, ссылки, термины. Сессия ≤45 мин, задача ≤10 мин, ≤3 сценария.
7. **Сессия** (структура): приветствие и роль («тестируем продукт, не вас») 2–3 мин → объяснение процесса и записи 1 мин →
   вводное интервью 3–5 мин → задание → выполнение с think-aloud → доп. вопросы «почему» → шкала сложности (SEQ) + открытый
   вопрос «что изменили бы первым» → благодарность.
8. **Поведение модератора (10 правил курса):** говорить ~20% времени — слушай много; не подсказывать; не задавать наводящих вопросов; держать паузу (~5 с после действия); просить думать вслух; нейтральность лица и голоса (не «отлично!», не хмуриться на ошибки); не оправдывать интерфейс («оно так задумано» — подсказка); управлять ритмом (не спешить, не тащить); не обрывать финальное впечатление (последние эмоции — самые ценные); записывать всегда. Уточнения без подсказки: «что вы ожидали увидеть?», «что помогло бы здесь?», «какие ещё варианты приходят в голову?»; вопросы про **конкретный элемент интерфейса задавать только если участник сам его упомянул**; вопросы в третьем лице («как, по-вашему, поступят другие?») снижают социальную желательность; при сломанном прототипе показать PNG и спросить «что бы сделали дальше?», пометить как технический сбой.
   **Техники уточнения:** «повтор мягкой фразой» (эхо последних слов с вопросительной интонацией); «уточняющая цепочка» (серия коротких «почему» по одному шагу); «петля в прошлое» (вернуться к сказанному ранее и сверить с текущим действием); «снятие чувства вины» («это место путает многих — не вы одни»); «отзеркаливание эмоций» (назвать наблюдаемое: «вы задумались/нахмурились — что случилось?»).
   **Невербальные сигналы трения** (фиксировать как наблюдение, не как факт-причину): наклон ближе к экрану, долгое зависание курсора в одном месте, нервная улыбка, частые оглядки на модератора, «затаивание дыхания» перед нажатием.
9. **Фиксация в моменте:** `время | шаг | действие/цитата | метка (красная — провал, жёлтая — трение, зелёная — «вау») | severity`.
   Записывать слова и поведение, эмоции, невербалику, вопросы участника.
10. **Анализ в тот же день:** тайм-кодовая матрица → группировка одинаковых проблем → приоритизация → паттерны (≥2 участников —
    кандидат, 3 — закономерность) → причина → бизнес-эффект.
11. **Решение после теста:** (A) доработать и повторить, если критичные проблемы; (B) идти в разработку, если гипотезы подтверждены и
    ошибок минимум; (C) пересобрать сценарий, если непонятна сама концепция/ментальная модель не совпадает.
12. **Ретест** после исправлений, дата и владелец назначаются сразу.

**Четыре «болевые зоны» модерируемого теста и защита от них:**
| Зона риска | Что происходит | Снижение ущерба |
|---|---|---|
| Лабораторность | Домашний ноутбук вместо реального окружения | По возможности «в поле»; иначе моделировать давление контекста (время, шум, параллельные задачи) |
| Технический сбой прототипа | «Рвётся» макет — участник путает баг прототипа с багом UX | Атомарные пути, проверка каждого линка до сессии, PNG-резерв и вопрос «что бы сделали дальше?» |
| Социальная желательность | «Всё ясно, классный продукт» | Установка «тестируем интерфейс, не вас»; вопросы в третьем лице |
| Эффект наблюдателя | Меньше ошибок в присутствии исследователя | Дистанционная сессия, модератор молчит ~80% времени, напоминает только про think-aloud |

**«Анти-косяк» — 5 шагов перед каждой сессией:** (1) check-run прототипа (все ссылки и анимации, 5 минут); (2) контрольный таймер (задача ≤ 10 минут, иначе резать); (3) контрольный вопрос в гайде (ловушка внимания); (4) лист наблюдений `время | шаг | действие | метка | severity` уже открыт; (5) план «Б» — папка с PNG и коротким скриптом на случай сбоя. Ссылку на прототип проверять в режиме инкогнито.

### 3. Немодерируемые методы

| Метод | Цель | Что измеряем | Ключевые правила |
|---|---|---|---|
| Тест интерпретации | Понимание смысла текста/иконки/бейджа | Доля верных толкований по кодированию открытых ответов (верно / частично / неверно / не понял) | Вопрос «что означает…», а не «что делает кнопка»; показ короткий; «белый список» трактовок заранее |
| First click | Заметность/находимость элемента | Success (первый клик в целевой зоне), время до клика (медиана/среднее), промахи, карта кликов | В задании нет названия элемента; при сравнении экранов считать значимость |
| 5-секундный тест | Первое впечатление, считываемость | Что вспомнили, как поняли посыл, запомнили ли CTA | Не предупреждать, что запоминать; ≤3–5 вопросов; для сложных экранов 10–20 с |
| Preference (side-by-side) | Какой вариант субъективно нравится/понятнее/вызывает доверие | Доля выбравших, значимость различия | Варианты различаются одной заметной деталью; один критерий в вопросе; случайный порядок; 2–3 варианта; не сравнивать со сторонним сервисом; результат ≠ поведение (A/B может не совпасть) |
| Card sorting открытая / закрытая / обратная (tree test) | Как люди группируют сущности; проверка иерархии | Матрица схожести, дендрограмма; для tree test — успех нахождения | 200–300 респондентов для массовой аудитории по курсу; открытая — когда структура неизвестна |
| Сценарное | Короткий простой флоу | Успешность, время, дропаут, субъективная лёгкость | Желательно законченный кликабельный прототип; чем больше развилок, тем больше смысла в модерируемом |

Общие правила: приветствие и контекст, задание, экран благодарности, описание аудитории и квот; **ханипот/контрольный вопрос**
и минимальное время для отсева невнимательных; логика переходов (ветвление по ответам) и логика отображения (показ/скрытие вопросов
на экране); при сравнении вариантов — тест значимости (хи-квадрат / z-тест для долей) до выводов. Объём: «рабочее число» курса
для массовых сегментов — около 300 ответов; для узких B2B-сегментов меньше. Доверительный интервал доли при 95%:
`±1,96·√(p(1−p)/n)` (при n=300, p=0,5 — около ±5,7 п.п.).

Ориентиры порогов, названные в курсе (калибровать под продукт, это не законы): интерпретация ≥80% верных; first click ≥80% успех и
время ≲2 с, ≤60% — плохо заметно; 5-секундный ≥70% верно назвали продукт; preference — разница >10 п.п. при p≤0,05 решающая, <5 п.п. — ничья.

### 4. Метрики теста (формулы)
| Группа | Метрика | Как считать |
|---|---|---|
| Эффективность | Успешность задания | Шкала 0 — не выполнил, 1 — с ошибками, 2 — с первого раза; Success Rate = выполнившие / валидные участники |
| Продуктивность | Время на задачу | Медиана по валидным (среднее искажают выбросы); число шагов, возвратов назад, неверных попыток |
| Удовлетворённость | Субъективная сложность | Ожидаемая (до) и фактическая (после) по шкале; SEQ (7 баллов) — среднее по валидным; разрыв «ожидание − факт» |
| Общая оценка | SUS (после сессии) | Шкала 0–100 по стандартной анкете |

Validity: исключать записи быстрее минимального времени и с проваленной ловушкой; считать на валидных, указывать n.
Целевые значения (например, Success ≥80%, SEQ ≥5, медиана ≤60 с) задавать **до запуска** под конкретный сценарий.

### 5. Приоритизация проблем
Проблема — не только провал задачи: замешательство при успехе, лишний шаг/возврат, пауза >3 с, вопрос участника, нарушение привычного паттерна.
Severity (общая шкала с [[M-ux-heuristics]]): 0 — косметика (скачет шрифт при фокусе); 1 — замедляет, не ломает (скролл длиннее ожидаемого); 2 — трение (заметная доля идёт по ложному пути, например ~30 % кликов мимо); 3 — блокирует часть пользователей (~50 % не видят целевое действие); 4 — блокирует задачу/доход/релиз. Правило: в первую очередь severity ≥3 или частота ≥50%; ниже — «серый
хвост». Формула курса: Severity = Влияние × Частота × Бизнес-риск (нормировать в 0–4).

**Реплицируемость теста:** один и тот же гайд, одинаковые формулировки заданий и порядок для всех участников — иначе результаты не воспроизводимы и сравнение версий/до-после теряет смысл.

### 6. Отчёт на один слайд
Фича и цель теста → метрики факт vs цель (n указать) → топ-проблемы (severity ≥3) с числом участников и цитатой с тайм-кодом →
решения, владелец, срок → дата ретеста. Исполнительное резюме: 5–7 проблем с влиянием и рекомендациями; детали и видео — в приложении.
Каждый тезис привязан к наблюдению/цитате/метрике.

## Шаблон / чек-лист

**Гайд (скелет):** цель и решение | гипотезы (≤3) | сегмент и рекрут | вводные вопросы | задания дословно | ожидаемый путь и сигналы
успеха | вопросы после действия | завершающие вопросы | план «Б» (PNG) | таймкод-таблица.

**Запись наблюдения:** `Участник | Время | Шаг | Что сделал/сказал (дословно) | Метка | Severity | Гипотеза причины (отдельно от факта)`.

**Перед запуском:** гипотезы измеримы; задания без UI-терминов; прототип прошёл сухой прогон; запись и согласие; пилот; шаблон заметок
открыт; контрольный вопрос (немодер); пороги метрик зафиксированы.

## Типичные ошибки
| Ошибка | Эффект | Как избежать |
|---|---|---|
| Подсказки и наводящие вопросы («а если через поиск?») | Искажённое поведение | «Какие ещё варианты приходят в голову?» |
| В задании названия кнопок/разделов | Тест проверяет чтение, не находимость | Описывать цель и контекст |
| Вопросы про элементы, которые участник не упоминал | Навязывание | Спрашивать только про сказанное/сделанное |
| Выводы только из слов респондента | Расхождение слова и поведения | Слова + действия + метрики |
| Не записывать/не уточнять причины | Нельзя доказать выводы | Запись, тайм-коды, «почему» после шага |
| Много гипотез/задач | Усталость, поверхностность | ≤3 сценария, ≤45 мин |
| Нет ловушки в немодерируемом тесте | Боты и невнимательные портят данные | Контрольный вопрос, минимальное время |
| Preference-тест с похожими вариантами и без значимости | Ложный победитель | Одно заметное различие, считать значимость |
| Тест на коллегах/своих | Не видно реальных барьеров | Рекрутировать ЦА |
| Приравнять результат UX-теста к эффекту на конверсию | Ложная уверенность | Подтверждать экспериментом |
| Отчёт на 30 слайдов, без владельца и даты ретеста | Решения не принимаются | One-pager + владельцы + ретест |

## Вопросы, которые могут изменить решение
- Решение, которое зависит от теста: идти в разработку, перерисовать или закрыть идею? Какой порог результата его меняет?
- Сценарий простой и линейный (достаточно немодерируемого) или со многими развилками (нужен модерируемый)?
- Есть ли готовый прототип, или сначала нужен [[M-ux-heuristics]]-обзор и дешёвая бумажная версия?
- Важен ли реальный контекст (улица, склад, связь)? Если да — лаборатория даст искажение.
- Достижима ли целевая аудитория для рекрута за срок? Иначе результат — гипотеза.
- Нужна ли количественная оценка эффекта на метрику? Тогда после теста — [[M-mvp-pilots]] / эксперимент.
