# SQL для продуктовой аналитики

## Когда применять
Нужно самому проверить гипотезу на данных: где течёт воронка, как ведут себя когорты, сколько ARPU/ARPPU и частотность, почему упала метрика. Быстрый собственный запрос вместо постановки задачи аналитику — плюс проверка качества данных до любых расчётов.

## Суть

### Базовые принципы
- Каждая продуктовая метрика — агрегат: `COUNT`, `SUM`, `AVG` + `GROUP BY`; каждая гипотеза — фильтр (`WHERE` до агрегации, `HAVING` — фильтр по агрегату после `GROUP BY`).
- Всё, что не агрегируется, должно быть в `GROUP BY`; `COUNT(DISTINCT …)` — для пользователей/заказов (дедупликация); `NULL` в `GROUP BY` образует отдельную группу, в агрегатах игнорируется (`SUM` по NULL-строкам не падает, деление на ноль — лечить `NULLIF`).
- Агрегация поверх агрегации (подзапрос/CTE): сначала заказы на пользователя, потом среднее по региону — так строятся сложные метрики вроде «retention по когорте и региону».
- Безопасность: работать с read-only репликой/витринами, не гонять тяжёлые запросы по продакшн-базе, ограничивать выборку (`LIMIT` на разведке), не публиковать креды.

### Типовые продуктовые запросы

**DAU/WAU/MAU (активность):**
```sql
SELECT DATE(submitted_at_dttm) AS day,
       COUNT(DISTINCT customer_id) AS dau
FROM orders_delivery
GROUP BY day ORDER BY day;         -- WAU: DATE_TRUNC('week', …), MAU: 'month'
```

**Воронка (уникальные пользователи на каждом шаге):**
```sql
SELECT
  COUNT(DISTINCT CASE WHEN event_type = 'registration' THEN user_id END) AS step1,
  COUNT(DISTINCT CASE WHEN event_type = 'add_to_cart'  THEN user_id END) AS step2,
  COUNT(DISTINCT CASE WHEN event_type = 'checkout'     THEN user_id END) AS step3,
  COUNT(DISTINCT CASE WHEN event_type = 'payment'      THEN user_id END) AS step4
FROM events
WHERE event_time >= '2025-10-01';
-- шаговая CR = шаг(n)/шаг(n−1); сквозная = шаг4/шаг1; разница шагов = «просадка»
```
Для честной воронки добавляют окно последовательности: шаг засчитывается только если пользователь дошёл до него после предыдущего (см. оконные функции ниже).

**Когортный retention (первое действие → возвраты):**
```sql
WITH first_orders AS (
  SELECT customer_id, MIN(DATE(submitted_at_dttm)) AS first_day
  FROM orders_delivery GROUP BY customer_id
),
activity AS (
  SELECT DISTINCT customer_id, DATE(submitted_at_dttm) AS activity_day
  FROM orders_delivery
)
SELECT f.first_day, a.activity_day,
       COUNT(DISTINCT a.customer_id) AS active_users,
       ROUND(100.0 * COUNT(DISTINCT a.customer_id)
             / COUNT(DISTINCT f.customer_id), 2) AS retention_rate
FROM first_orders f
JOIN activity a ON f.customer_id = a.customer_id
GROUP BY f.first_day, a.activity_day
ORDER BY f.first_day, a.activity_day;
-- результат = когортная матрица; для D7 фильтр a.activity_day = f.first_day + INTERVAL '7 days'
```
Нулевая точка (первое событие) должна быть определена однозначно — сдвиг нулевой точки завышает retention.

**Выручка, средний чек, ARPU/ARPPU:**
```sql
-- выручка и средний чек по дням
SELECT DATE(o.submitted_at_dttm) AS day,
       SUM(i.price * i.quantity) AS revenue,
       SUM(i.price * i.quantity) / COUNT(DISTINCT o.order_id) AS avg_check
FROM order_items i
JOIN orders_delivery o USING (order_id)
GROUP BY day ORDER BY day;

-- ARPU и ARPPU за период (требуется таблица пользователей/активности)
-- ARPU  = SUM(выручка периода) / COUNT(DISTINCT активные пользователи периода)
-- ARPPU = SUM(выручка периода) / COUNT(DISTINCT платившие пользователи периода)
```
Проверки: числитель и знаменатель — один период и одна когорта; ARPU по активным, ARPPU по платящим — не подменять; позиций в заказе может быть много → дедуплицировать заказ при делении.

**Повторные заказы и частотность:**
```sql
-- доля клиентов с >1 заказом (repeat rate)
SELECT ROUND(100.0 * COUNT(DISTINCT CASE WHEN orders_count > 1 THEN customer_id END)
             / COUNT(DISTINCT customer_id), 2) AS repeat_rate
FROM (SELECT customer_id, COUNT(order_id) AS orders_count
      FROM orders_delivery GROUP BY customer_id) t;

-- частотность: заказов на клиенте в день его «жизни»
SELECT customer_id, COUNT(order_id) AS order_count,
       ROUND(COUNT(order_id)::NUMERIC /
             (DATE_PART('day', MAX(submitted_at_dttm) - MIN(submitted_at_dttm)) + 1), 2)
       AS orders_per_day
FROM orders_delivery GROUP BY customer_id;
```
Frequency + Recency + Monetary (сумма) = основа RFM-сегментации (`CASE WHEN` по порогам → сегменты New/Active/Loyal).

**Диагностика падения метрики:** разрезы по региону/категории/платформе за два периода и сравнение (`WHERE DATE BETWEEN … GROUP BY region`), затем сужение к сегменту, где падение сконцентрировано; сверка с прошлым годом на сезонность.

### JOIN и UNION
- **INNER JOIN** — только совпадения (обе стороны); **LEFT JOIN** — все строки левой + совпадения правой (NULL там, где нет): стандарт «заказы + доставки», «пользователи + действия»; **RIGHT JOIN** — зеркально; **FULL JOIN** — всё из обеих (поиск расхождений между системами).
- После LEFT JOIN правая таблица может дублировать строки левой (связь 1:N, например заказ → позиции): агрегаты по левой таблице считайте до или после — задвоение искажает суммы.
- **UNION ALL** — просто склеивает (быстро, дубли остаются); **UNION** — склеивает и дедуплицирует (дороже). Типовое применение — склейка периодов/источников одинаковой структуры.
- Условие соединения с диапазоном (`BETWEEN first_day AND first_day + INTERVAL '7 days'`) — основа ретеншен-расчётов.

### CTE (WITH … AS) и подзапросы
CTE — именованный подзапрос внутри одного SELECT: делает большие запросы читабельными, позволяет переиспользовать результат (например, `first_orders`), упрощает отладку по шагам, заменяет временные таблицы. Ограничения: живёт только внутри одного запроса, должна быть объявлена до использования, сама по себе не ускоряет выполнение (оптимизатор может считать её многократно — для тяжёлых случаев материализовать в таблицу).

### Оконные функции (window functions)
Считают агрегат по группе строк, **не сворачивая их** (в отличие от `GROUP BY`), и добавляют значение к каждой строке:
```sql
<функция>() OVER (PARTITION BY ключ   -- независимые группы (пользователь/регион)
                  ORDER BY колонка)   -- порядок внутри группы
```
- `ROW_NUMBER()` — уникальный номер строки в окне: нумерация заказов клиента, дедупликация (`WHERE rn = 1`), «первое/последнее событие».
- `RANK()` / `DENSE_RANK()` — ранжирование с одинаковых значений: RANK пропускает номера (1,2,2,4), DENSE_RANK — нет (1,2,2,3). Топы по выручке/категориям.
- `LAG(col, 1)` / `LEAD(col, 1)` — предыдущее/следующее значение в окне: интервалы между заказами, дельта к прошлому периоду, проверка последовательности шагов воронки.
```sql
-- дни между заказами клиента (частотность и паттерны возврата)
SELECT customer_id, submitted_at_dttm,
       submitted_at_dttm - LAG(submitted_at_dttm) OVER (
         PARTITION BY customer_id ORDER BY submitted_at_dttm) AS days_between
FROM orders_delivery;
```
- Окно без `PARTITION BY` — по всей таблице (общий рейтинг). `ORDER BY` внутри окна почти всегда обязателен. Типовые задачи: ранжирование, последовательности событий, сравнение соседних значений, накопительные метрики, когортный анализ.

### Чек-лист качества данных перед расчётом
1. **Полнота:** источники DWH пересчитались; нет «дыр» по датам; свежесть данных (до какой даты вообще есть события).
2. **Дубликаты:** нет задвоенных строк за день (классика: резкий «рост и откат» на графике — почти всегда дубль в данных, а не поведение пользователей); `COUNT(*)` vs `COUNT(DISTINCT id)`.
3. **Определения:** нулевая точка когорты, окно воронки, что считается «активностью» и «платежом» — зафиксированы и совпадают с паспортом метрики; события не переименовывались.
4. **Сегменты и фильтры:** тестовые пользователи/внутренние аккаунты исключены; фильтры платформ/регионов применены осознанно.
5. **Типы и NULL:** даты — даты (не строки); деление защищено `NULLIF(...,0)`; доля возвратов через `CASE WHEN flag THEN 1 ELSE 0 END`.
6. **Связи:** после JOIN число строк не «взорвалось» (1:N); LEFT JOIN не потерял пользователей контроля.
7. **Sanity-check:** метрика хотя бы одного дня пересчитана руками; итоги сопоставлены с дашбордом/известным фактом.

## Процедура
1. Сформулировать вопрос в терминах метрики, периода и сегмента (паспорт метрики из [[M-product-metrics]]).
2. Проверить качество данных по чек-листу выше.
3. Начать с разведки: структура таблиц, `LIMIT`, число строк; затем CTE по шагам (первое событие → активность → агрегат).
4. Посчитать базовые агрегаты (DAU/выручка/воронка), затем усложнить: когорты, ratio-метрики, оконные функции.
5. Сделать разрезы (сегмент/период/платформа) и сравнение периодов; проверить сезонность прошлым годом.
6. Пересчитать вручную контрольную точку и только после этого делать вывод или передавать результат (в дашборд, [[M-ab-testing]], [[M-traction-model]]).

## Типичные ошибки
- `WHERE` и `HAVING` перепутаны; колонки вне агрегатов забыты в `GROUP BY`.
- JOIN 1:N задваивает выручку/пользователей; LEFT JOIN молча превращает INNER из-за фильтра правой таблицы в `WHERE`.
- UNION вместо UNION ALL там, где нужны дубли (или наоборот — скрытые дубли).
- NULL теряется: `SUM` игнорирует NULL, но `COUNT(col) ≠ COUNT(*)`; деление на ноль без `NULLIF`.
- Смещённая нулевая точка когорты или плавающее окно воронки — retention «улучшается» от переопределения, а не продукта.
- Сквозную конверсию сравнивают с шаговой; ARPU считают по всем, а ARPPU по активным.
- Тяжёлый запрос на продакшн-базе; нет `LIMIT` на разведке; «резкий рост и откат» принимают за поведение пользователей, не проверив дубликаты.

## Вопросы, которые могут изменить решение
- Все ли события логируются с нужной даты и не переименовывались ли события?
- Какая связь между таблицами (1:1/1:N) и не задваивает ли join числитель или знаменатель?
- Что здесь нулевая точка и окно — и совпадают ли они с паспортом метрики?
- Не лежит ли «падение» целиком в одном сегменте/платформе/регионе?
- Воспроизводим ли результат: сходится ли пересчёт с дашбордом и прошлым периодом?
