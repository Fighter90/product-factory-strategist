# Трекшн-модель (модель роста): построение, эффекты, валидация

## Когда применять
«Какой рост и выручку даст инициатива/продукт?», «на какие гипотезы ставить?», «как защитить прогноз перед руководством или инвестором?», «можно ли складывать эффекты гипотез?», «проверить чужую модель на ошибки». Модель — основа бизнес-кейса, приоритизации и отслеживания факта против плана.

## Суть
**Трекшн-модель** (бизнес-кейс, продуктовая модель, growth model) — прогноз инкрементального эффекта запуска продукта/инициативы: `Каналы привлечения + Ценность продукта (и рост ценности) + Монетизация = Бизнес-результат`. Отвечает: за счёт чего, как и на каком горизонте растёт продукт.

**Слои гипотез** (прогноз — «большая гипотеза» из вложенных предположений):
1. Рынок — TAM/SAM/SOM, средний чек, доли конкурентов, законодательство → «проверка сверху» ([[M-market-sizing]]).
2. Baseline («если ничего не делать») — динамика воронки, базы, цен, влияние других продуктов.
3. Драйверы роста («если повлиять») — изменение воронки/базы/метрик от конкретных инициатив.
4. Монетизация — как меняется доход при реализации драйверов (чек, конверсия в оплату, ценообразование).
Расширение в скилле монетизации: 5 — монетизация, 6 — прогноз выручки, 7 — затраты (постоянные и driver-based), 8 — эффективность (UE, окупаемость, NPV, IRR, EBITDA). Нумерация в скиллах расходится (в traction-modeling монетизация = слой 4); в картах использовать схему «4 слоя гипотез + блоки выручка / затраты / эффективность».

Два типа структуры: **growth** (новые пользователи, активная база, конверсия, ARPU, Revenue) и **efficiency** (cost-to-serve, маржинальность, LTV/CAC, операционные расходы).

Метрики по стадиям жизненного цикла: MVP/Pilot — retention, activation, NPS; Рост — growth rate, CAC, LTV, конверсии воронки; Зрелость — ARPU, доля рынка, маржа; Спад — churn, cost-to-serve, harvest.

### Выбор подхода
| Ситуация | Подход |
|---|---|
| Есть история, рынок и сезонность стабильны | baseline из временных рядов (например, Prophet) + наложение драйверов |
| Данных нет (новый продукт) | baseline отсутствует; top-down сценарии разной оптимистичности |
| После MVP, есть CAC/LTV/retention | bottom-up, консервативная оценка; сверка с top-down |
| Нужен инкремент от фичи/канала/гео | bottom-up с драйверами |
| Стратегическая рамка, инвесторы, «проверка сверху» | top-down |

**Top-down:** TAM→SAM → доля рынка → динамика (CAGR, макрофакторы) → SOM → внутренние факторы. Слабое место — допущения: усреднённый retention, ложная сезонность (промо-пики приняты за сезонность), недооценка cost-to-serve.
**Bottom-up:** модули (PU, ARPPU, retention, конверсии), когорты (не агрегировать), прозрачные формулы, встроенная sensitivity. Ограничен при нехватке данных и для «видения» на годы вперёд. **Зелёная зона: расхождение bottom-up с top-down < 15%.**

### Шаблон traction-модели курса (Excel)
Эталонная структура листов — основа для Excel-шаблонов агента:

**Лист `Assumptions`** — таблица параметров: `# (код) | Параметр | Значение | Ед. | Источник / обоснование | Confidence (high/medium/low)`. Группы кодов:
- `M1–M6` рыночные допущения (top-down): TAM/SAM, доля SOM, AOV рынка, рост SAM %/мес, рост SOM п.п./мес;
- `D1–D9` demand side (воронка): MAU, CR MAU→поиск, CR поиск→запрос, CR запрос→подтверждение, доля отмен, AOV, рост AOV %/мес, take rate, рост MAU %/год;
- `S1–S6` supply side: объявления, доля активных, доля PRO, ARPU продавца/мес, рост ARPU %/мес, рост базы %/год;
- `SS1–SS12` сезонные коэффициенты по месяцам (контрольная строка: сумма = 12.0).
Каждый параметр — с источником и классом уверенности; захардкоженные значения = редактируемые ячейки (blue cells), вся модель — формулы (см. [[M-model-topdown-bottomup]]).

**Лист `Traction model (Scenario N)`** — строки = метрики, столбцы = 60 месяцев (5 лет); строка 2 = маркер года; годовые итоги через `SUMIF` по маркеру года, средние через `AVERAGEIFS`. Блоки строк:
1. MARKET (ограничение сверху): `SAM_GMV_мес = TAM × SAM% × AOV / 12`; рост MoM; `SOM_cap = SAM × SOM%` (растёт п.п./мес); сезонный коэффициент из Assumptions.
2. BASELINE Demand side (драйверное дерево): `MAU_мес = MAU × сезонный коэфф.` → `×CR_поиск` → `×CR_запрос` → `×CR_подтверждение` → `Orders paid` → `×(1 − доля отмен) = Orders fulfilled (NSM)` → `×AOV = GMV` → `×Take rate = Revenue: комиссии`.
3. BASELINE Supply side: `Active listings = объявления × доля активных × сезонный коэфф.`; `Revenue: VAS = Active listings × ARPU_мес` (растёт %/мес).
4. TOTAL: `Total Revenue = комиссии + VAS`; `Revenue YoY growth`; чек `GMV < SOM cap` (TRUE = OK) — bottom-up не должен пробивать top-down потолок.
Каждый месяц считается от предыдущего «продлением на формулах»: `значение_N = значение_(N−1) × (1 + ставка роста)` + сезонный коэффициент; старт первого месяца — ссылка на Assumptions.

**Блок гипотез** (таблица в Assumptions или отдельный лист): `Гипотеза | Метрика (что меняем) | Status (done/wip/not started) | Confidence | Confidence rate | uplift | % раскатки | Источник / обоснование | Метод проверки | Риск каннибализации | Комментарий (сценарий 1/2, включено/не включено)`. В модели uplift применяется к строке конкретной метрики с месяца запуска: `значение = baseline × (1 + uplift × % раскатки)`. Переключатель сценария (включено/не включено гипотез) — ручка для сценариев base/optimistic/pessimistic: base = гипотезы выключены или с базовым uplift, оптимистичный = high-confidence гипотезы включены, пессимистичный = только done-гипотезы/пониженные uplift.

**Лист `Costs assumptions`**: Cost of Sales (затраты на маркетинг на заказ, логистику на заказ — переменные, в юнитку), Staff cost (FTE × средняя зарплата с налогами), Marketing, IT (лицензии, IT для новых людей), прочее (travel). Сверху над выручкой это даёт вклад в P&L; переменные расходы на заказ — вход в UE ([[M-unit-economics]]).

**Гигиена шаблона:** ни одного захардкоженного числа в расчётных строках (всё — ссылки на Assumptions); ретроспектива (факт из дашбордов) отделена от прогноза; вспомогательная строка коэффициентов вместо ручного заполнения месяцев.

## Процедура
1. **Цель и аудитория модели** (решение, финансирование, трекинг); горизонт; стадия.
2. **Предусловия:** стабилен ли рынок? устойчива ли сезонность? глубина истории? известны ли макрофакторы (инфляция, налоги, ставки)? Для чего модель? Ответы выбирают подход.
3. **Target-метрика** разложить до атомарных драйверов: `MRR = Клиенты × ARPU`, дальше каждый компонент либо драйвер, либо раскладывается. Критерий достаточности: все компоненты объяснены драйверами.
4. **Baseline:** история и тренды, сезонность, поведение когорт (новые когорты ведут себя иначе), инерция прошлых запусков, инфляция, повышение цен, влияние соседних продуктов. Нет данных — три сценария вместо baseline.
5. **Гипотезы-драйверы:** для каждой — целевая метрика (активация / привлечение / удержание / виральность), формулировка «изменение X → результат Y», размер эффекта, источник/бенчмарк ([[M-benchmarking]]), класс достоверности.
6. **Эффекты:** время, сложение, затухание (см. ниже). Каннибализация — явным блоком ([[M-cannibalization]]).
7. **Монетизация и экономика:** выручка (`Revenue = ARPPU × PU` или по формуле модели, [[M-monetization]]), затраты, UE ([[M-unit-economics]]).
8. **Sensitivity:** по каждому ключевому драйверу три сценария (pessimistic/base/optimistic); показать, какие 2–3 драйвера двигают результат.
9. **Сверка сверху:** модель ≤ SOM; расхождение с top-down; сумма каналов ≤ TAM.
10. **Валидация** (ниже) и ревью независимым человеком; документировать статус OK/WARNING/ERROR.

### Сложение эффектов
Эффекты гипотез чаще **не аддитивны**: складывать можно только гипотезы на разные сегменты/каналы без пересечения (акция на ассортимент + performance-канал). Пересекаются — партнёрский канал и рассылка по одной базе («задвоение»).
Чек-лист из 4 вопросов: (1) один драйвер/метрика? (2) один календарный период? (3) суммарный рост > 10% (двузначный)? (4) один сегмент/канал? **Если «да» минимум на два — применять дисконт:** `Итого = Σ Эффект_i × k`, `k` обычно 0,5–0,8 (чем больше пересечение, тем ниже).
Пример (иллюстрация): две гипотезы на конверсию в одном сегменте, +6% и +5% → сумма 11%, «да» на все 4 вопроса → итог 5,5–8,8% при k 0,5–0,8.

### Эластичность и плато
Эффекты почти всегда нелинейны: затухают (новизна, привыкание) или накапливаются. Определи момент выхода на плато по бенчмаркам и затуханию интереса; на первых периодах раскладывай эффект по неделям, не кварталам; проверь здравый смысл потолка (покупатель обуви вряд ли купит больше 12 пар за раз). **Хоккейная клюшка — красный флаг**; допустима лишь при быстром физическом масштабировании (выход в новую географию).

### Каннибализация в модели (кратко)
`Рост = (Было − Каннибализация) × K_роста` (до гипотез) или `Рост = (Было × K_роста) × (1 − K_канн)` (после суммарного эффекта). Формулы эквивалентны, если `K_канн = Каннибализация / Было`; фиксируй, к какой базе отнесён коэффициент. Цена как драйвер: `Revenue = ARPPU × PU` — оцени размен роста ARPPU против падения PU. Подробности — [[M-cannibalization]].

### Внешние факторы (карта влияния)
Потребители (поведение, демография) → число покупателей, сделки, чек; законы и экономика (ставка, налоги) → размер рынка, чек, себестоимость; конкуренты → доля, CAC; технологии (ИИ-агенты и др.) → размер рынка, поиск, CAC. Привязывай к сценариям из [[M-trends-scenarios]].

### Связь с оценкой стоимости
Модель — вход для DCF (дисконтированные будущие cash flow; чувствителен к WACC и terminal value; поздние раунды, устойчивые проекты), CCA (мультипликаторы похожих компаний; зависит от выбора аналогов) и Precedent Transactions (мультипликаторы сделок M&A; данные могут устареть).

## Шаблон / чек-лист
Структура листов: `Assumptions` (все допущения с источником и классом) → `Baseline` → `Drivers` (гипотезы, эффекты) → `Monetization` → `Costs/Efficiency` → `Scenarios/Sensitivity` → `CHECKS`.

Таблица гипотез:
| Гипотеза | Слой | Метрика | Эффект (min/base/max) | Сегмент/канал | Период и кривая | Пересечения | Источник, класс |
|---|---|---|---|---|---|---|---|

### Валидация: четыре типа технических ошибок
1. **Округление:** округлять только финал; сумма помесячных округлений ≠ годовая сумма. Проверка: `=IF(ABS(SUM(B10:M10)-N10)>0.1;1;0)`.
2. **Временная привязка** (самая частая): затраты момента против доходов за годы; точечные и накопительные метрики смешаны. `MAU(N) = MAU(N−1) + New(N) − Churned(N)` для баланса базы.
3. **Противоречия формул:** одна величина считается в двух местах по-разному. Правило SSOT (Single Source of Truth): считать в одном месте, остальные листы ссылаются; именованные диапазоны для ключевых ячеек.
4. **Логическая несогласованность:** баланс `Клиенты_нач + Новые − Ушедшие = Клиенты_кон`; неотрицательность; CR1 85% × CR2 90% = 76,5%, а в модели итог 80% — противоречие.

Вкладка `CHECKS`, бинарно (0 — ок, 1 — ошибка), глобальный статус `=IF(SUM(Check_Range)>0;"ERROR";"OK")`:
```
Битые ячейки:      =IF(SUMPRODUCT(--ISERROR('P&L'!A1:Z1000))>0;1;0)
Отрицательные:     =IF(MIN(B20:M20)<0;1;0)
Границы процентов: =IF(OR(MAX(B25:M25)>1;MIN(B25:M25)<0);1;0)
Монотонность ret.: =IF(SUMPRODUCT(--(B31:M31>B30:M30))>0;1;0)
Не выше TAM:       =IF(SUM(B50:B55)>'Assumptions'!$B$5;"TAM Exceeded";"OK")
```
Бенчмарки в валидации: sanity check, калибровка, объяснение отклонений; бенчмарк — диапазон, сравнивать с той же стадией и сегментом. Нет данных: прокси-метрики (похожий регион/сегмент), интервью экспертов (диапазоны), MVP на 1–2 месяца с экстраполяцией с дисконтом, три сценария.

Ревью (автор слеп: confirmation bias, anchoring, curse of knowledge): аналитик (техника), финансы (экономика), другой продакт (логика), стейкхолдер (цели). Когда валидировать: перед презентацией, после крупных изменений, перед планированием на основе модели, при передаче команде.

| Красные флаги | Зелёные флаги |
|---|---|
| нереалистичные входные метрики или завышенная динамика | рост входных метрик обоснован A/B, исследованиями, трендами |
| недовыполнение периода перенесено без обоснования | тренды и исследования продисконтированы |
| нет истории и трендов в baseline | «доля рынка» не используется как входная метрика |
| не учтена каннибализация | падение одной входной метрики не перекрыто ростом другой |
| нет входных метрик («коммит без inputs») | каннибализация учтена экспертно или по A/B |
| одна сильная предпосылка держит все выходы | малое изменение предпосылки не даёт непропорционального сдвига выходов |

Итоговый чек-лист: драйверы причинно связаны; технические ошибки (хардкод, округления, битые ссылки); допущения сверены с бенчмарками; независимое ревью; резолюция/«светофор». Выход: статус модели, список ошибок по типам, вкладка CHECKS, сравнение с бенчмарками, рекомендации, заполненный чек-лист.

## Типичные ошибки
| Ошибка | Последствие |
|---|---|
| Игнорирование затухания когорты | завышение ARPU/LTV на 30–40% (оценка скилла, без источника) |
| Агрегированный retention без фазирования | неверное распределение бюджета |
| Линейный рост | пропуск сезонности и скачков |
| Ошибка в модели монетизации | неверные ARPU/LTV |
| Слабая гигиена данных | garbage in — garbage out |
| Нет sensitivity | ложная уверенность |
| Эффекты сложены без дисконта | завышенный итог при пересечениях |
| Драйвер — корреляция, а не причина; или команда на него не влияет | нереализуемый план |

## Вопросы, которые могут изменить решение
- Есть ли данные для baseline, насколько они стабильны и глубоки?
- Какие 2–3 допущения определяют >50% результата и какого они класса достоверности?
- Пересекаются ли гипотезы по сегментам, каналам, периодам?
- Запускается ли продукт на существующую базу (тогда каннибализация обязательна)?
- Для чего модель: решение, деньги или трекинг — от этого зависит допустимая точность.
