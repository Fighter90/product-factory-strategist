# Прогнозирование и traction-аналитика для продукта

## Когда применять
Нужно решить «стоит ли вкладываться в идею», поставить цели на период, спланировать бюджет/нагрузку или честно ответить «что будет с метрикой, если мы ничего не сделаем» — это baseline, без которого нельзя посчитать эффект инициативы. Прогноз — не обещание, а сценарий с допущениями; он всегда проверяем и всегда с интервалом.

## Суть

### Прогноз vs драйверная модель
- **Экстраполяция (временные ряды)** — «продлить историю»: тренд + сезонность + шум. Работает, когда есть глубокая стабильная история (12–24 месяца) и рынок не ломается. Это база для baseline.
- **Драйверная модель (traction)** — «собрать метрику из частей»: например, Revenue = PU × TPU × AOV, каждая часть — драйвер с предпосылкой и источником. Работает, когда история короткая/меняется правила игры или нужен эффект конкретной инициативы.
- Правильная практика — гибрид: baseline из временного ряда, поверх — драйверы инициативы. Чистая экстраполяция «как есть» на горизонты с изменениями продукта/рынка — типовая ошибка.

### Компоненты временного ряда
1. **Тренд** — долгосрочное направление (категория растёт 15% год к году).
2. **Сезонность** — повторяющийся паттерн с известным периодом: суточный (день/ночь), недельный (будни/выходные), месячный (зарплатные пики), годовой (декабрь-подъём, январь-провал). Узнаваемая сезонность ≠ проблема продукта.
3. **Шум** — случайные колебания; именно из-за него неделя «+3» при среднем 20 может быть случайностью.
4. **Аномалии** — разовые выбросы: акции, сбои, кампании, A/B-тесты, внешние события. До моделирования — исключаются или заменяются; иначе модель «выучит» аномалию как закономерность.

### Baseline: прогноз «если ничего не делать»
**Baseline — прогноз того, как поведут себя метрики без запуска инициативы.** Это фундамент traction: плохой baseline = неверный uplift = неверное решение. Baseline — НЕ прогноз с фичей, НЕ мнение продакта и НЕ аналитика прошлого; это чистый прогноз на исторических данных.
Зачем: без baseline нельзя отличить эффект фичи от сезонности («в феврале PU каждый год падает на 20%, а с фичей упал на 15% — это успех, а не провал»), нельзя посчитать uplift и сравнить «рост/падение с нормой».
Пошаговое построение:
1. Собрать историю 12–24 месяца, гранулярность день/неделя, разрезы по сегментам.
2. Удалить аномалии: акции, крупные A/B, разовые кампании, выбросы.
3. Применить модель временного ряда: по возрастанию сложности — скользящее среднее/наивный сезонный прогноз (значение = значение прошлого периода × сезонный коэффициент), затем Prophet/ARIMA/ETS, далее градиентные бустинги с признаками — когда много внешних факторов. Модель строится **для каждого сегмента отдельно**.
4. Принудительно наложить сезонность прошлого года там, где модель её недоучитывает: `baseline[t] = тренд + сезонность прошлого года + корректировки на другие продукты`.
5. Проверить, что baseline «не разваливается»: визуально, сверкой с фактами последних месяцев (backtest), анализом остатков (ошибки без систематического смещения), интервалами прогноза. «Прыгает» — переделать.
6. Сегментировать всегда: новые/старые пользователи, категории, платформы, типы тарифов — инициативы влияют на сегменты по-разному, агрегатный baseline об этом молчит.

### Traction (драйверная модель) на входе в инвестиционное решение
Процесс из «ворот» (gate-модель): Gate 0 — идея (дни), Gate 1 — «тракшн на коленке» (оценка логики: драйверы, порядок величин; точность не требуется), Gate 2 — детальная модель (аналитик + продакт, дни-недели), Gate 3 — проверка фактами A/B-теста после пилота.
Состав детальной модели:
1. **Целевая метрика** (Revenue/PU/ARPPU/GMV/retention — по фиче).
2. **Baseline** (см. выше).
3. **Сегментация** (обязательна: одна и та же инициатива может поднять PU в одном сегменте и обрушить ARPPU в другом).
4. **Драйверы** изменения метрик: раскладка целевой на множители (Revenue = PU × TPU × AOV; ARPPU = TPU × AOV) и прогноз каждого драйвера с обоснованием.
5. **Uplift** — эффект инициативы по драйверам; источники: прошлые запуски, A/B других команд, бенчмарки рынка, UX-исследования, экспертная оценка; у каждой предпосылки — **уровень уверенности (например, 50–100%)** и статус (доказано/гипотеза).
6. **Раскатка** — график долей аудитории по месяцам (10% → 30% → 60% → 100%): эффект растягивается во времени, «прибыль января ≠ прибыль июня»; сдвиг сроков сдвигает весь прогноз.
7. **Финальный прогноз** = baseline + uplift × % раскатки, помесячно, с каннибализацией и пересечениями других запусков ([[M-traction-model]]).
Не забыть: логические проверки (bottom-up не пробивает top-down потолок рынка), sensitivity по 2–3 главным допущениям, сценарии base/optimistic/pessimistic.

### Проверка точности прогноза
- **Backtest:** обучить на истории до момента T, предсказать после T, сравнить с фактом. Ошибки: MAE — средняя абсолютная ошибка (в единицах метрики); **MAPE** — средняя абсолютная процентная ошибка, `mean(|факт − прогноз| / факт) × 100%`, применима для положительных метрик; RMSE — квадратичная, штрафует крупные промахи. Ориентир для бизнес-прогнозов — MAPE < 20% (сильнее — <10%); главное — ошибка ниже «экономически значимого» эффекта, который прогноз должен поймать.
- Остатки (факт − прогноз) не должны иметь тренд/сезонность — иначе модель что-то не поймала.
- Прогноз всегда показывать с интервалом (пессимистичный/оптимистичный), а не точкой.
- После запуска: факт vs baseline vs прогноз — регулярная сверка ([[M-model-validation]]).

### Когда прогноз «врать не может» и когда не имеет смысла
- **Baseline на истории не может «врать» как мнение:** это проверяемое утверждение («что было бы без нас») — его можно сверить с фактом и улучшать; в этом смысле он объективен по построению (чистые исторические данные, без желаний).
- **Не прогноз, а планирование:** для нового продукта без истории экстраполяция невозможна — «прогноз» превращается в сценарии с допущениями (top-down от рынка, bottom-up от юнит-экономики, три сценария вместо baseline). Выдавать их за прогноз — ошибка.
- **Прогноз бесполезен/вреден**, если: горизонт за пределами устойчивости допущений (правила игры меняются); главная предпосылка одна и не проверена; точность не измерена; интервалы не показаны. Долгий горизонт = широкий интервал — честно показывать сужение уверенности к горизонту.
- **Прогноз без владельца, допущений и дат сверки факт vs план — не инструмент, а картинка:** допущения вынесены на видное место, за каждое отвечает конкретный человек, сверка запланирована датами.

### Типовые ошибки прогнозирования
1. Линейная экстраполяция «как есть» — пропуск сезонности и насыщения.
2. Игнор сезонности: январь-провал принят за «фича убила продукт» (или наоборот, декабрь-пик — за успех фичи).
3. Плохая очистка данных: аномалии/дубли/сбои вошли в модель.
4. Утечка будущих данных (leakage): в признаки попала информация «из будущего» относительно момента прогноза.
5. Один сценарий вместо трёх; интервалы не показаны; точку выдали за факт.
6. Слепое доверие модели: без бизнес-логики и sanity-check (модель может «предсказывать» физически невозможное).
7. Baseline не сегментирован — uplift усреднён и неверен по каждому сегменту.
8. Раскатка не учтена: эффект 100% аудитории приписан первому месяцу.

### Модели baseline по возрастанию сложности
| Ситуация | Модель | Когда достаточно |
|---|---|---|
| Стабильная сезонность, короткая история | наивный сезонный прогноз: значение = прошлый период × сезонный коэффициент | первая прикидка, Gate 1 |
| Тренд + сезонность, одна метрика | Prophet/ETS/ARIMA (декомпозиция ряда) | базовый рабочий baseline |
| Много внешних факторов, много сегментов | градиентные бустинги с признаками (календарь, акции, погода) | крупные метрики, есть признаки |
| Новый продукт без истории | не прогноз, а сценарии: top-down от рынка + bottom-up от юнит-экономики | три сценария вместо baseline |
Схема построения ML-прогноза (коротко): очистка данных → проверка/задание сезонности → baseline-модель → добавление признаков → модель → интерпретация и sanity-check. Усложнять только если проще не проходит backtest.

## Процедура
1. Определить вопрос и горизонт прогноза; есть ли история (≥12 мес) и стабильны ли правила игры — от этого зависит выбор подхода ([[M-traction-model]]).
2. Собрать и очистить историю (аномалии, дубли, сбои), выбрать гранулярность и сегменты.
3. Построить baseline: наивный сезонный прогноз → модель временного ряда → наложить сезонность прошлого года; проверить backtest'ом и остатками; посчитать MAPE/MAE.
4. Разложить целевую метрику на драйверы; для каждого драйвера указать uplift, источник и уровень уверенности.
5. Наложить uplift на baseline с графиком раскатки; учесть каннибализацию и пересечения; сверить с потолком рынка.
6. Собрать сценарии base/optimistic/pessimistic и sensitivity по 2–3 главным допущениям.
7. Показать прогноз с интервалами и допущениями; договориться о контроле: даты сверки факт vs baseline vs прогноз и условие пересмотра.

## Шаблон / чек-лист
```
Вопрос: ___  Горизонт: ___  Метрика: ___ (единицы, период)
История: ___ мес, сегменты: ___  Аномалии исключены: да/нет
Baseline: метод ___  Backtest MAPE = ___%  Остатки без тренда: да/нет
Драйверы: PU=___ TPU=___ AOV=___  Uplift: ___ (источник, уверенность ___%)
Раскатка: мес 1 ___% … мес N ___%   Каннибализация: ___
Сценарии: base ___ / optim ___ / pess ___   Контроль факта: ___ (даты сверок)
```
Чек-лист: есть baseline, а не только «эффект фичи» · сезонность прошлого года учтена · точность измерена (MAPE) и ниже значимого эффекта · каждый uplift с источником и уверенностью · раскатка помесячная · сценарии и интервалы показаны · назначены даты сверки факт vs baseline.

## Типичные ошибки
- «Продлить линию» вместо baseline с сезонностью; декабрьский пик записать в успех инициативы.
- Аномалии и акции не вычищены — модель их выучила.
- Прогноз точкой без интервала; сценарии подменены «наиболее вероятной» цифрой.
- Uplift из воздуха: ни источника, ни уровня уверенности, ни каннибализации.
- Один агрегированный baseline вместо сегментного; раскатка не отражена.
- Backtest не сделан; MAPE не посчитана; факт с прогнозом никто никогда не сверяет.
- Для нового продукта экстраполяция «по аналогии» выдана за прогноз.

## Вопросы, которые могут изменить решение
- Есть ли достаточно истории и стабильны ли правила игры на всём горизонте?
- Что произойдёт с метрикой без нашей инициативы (baseline) и насколько точен этот baseline (MAPE)?
- Какой драйвер даёт >50% результата и откуда взят его uplift?
- Не «пробивает» ли bottom-up прогноз потолок рынка и не пересекается ли с чужими запусками?
- Что покажет факт через 3 месяца, если прогноз ошибётся на величину интервала, и кто и когда это сверит?
