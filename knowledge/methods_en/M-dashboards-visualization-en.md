# Visualization and Dashboards for PMs (EN summary)

**When:** speeding up decisions and metric-driven hypothesis search; building a dashboard from which the team understands "are we OK" in a minute; auditing an existing dashboard or chart for typical errors. Visualization is not decoration but a way to think faster: a thousand-row table hides an anomaly, a chart shows it in seconds.

**Core:** Wrong visualization = wrong decision: a cropped axis hides a drop, an extra series makes a chart unreadable. A chart (visualization) answers one question; a dashboard is a composition of charts built for a decision, with context, hierarchy and filters — its question is "what's happening with the product and why". Reference 4-level structure read top-down: (1) Intro — name, period, active filters (platform, geo, segment), purpose, data-freshness date — insurance against wrong decisions: without it people read the wrong period/platform and argue about numbers; (2) Hero KPI — "are we OK?": 3–6 main metrics as large cards, each with value + arrow + WoW/MoM/YoY comparison; (3) Diagnostics — "why?": dynamics of key metrics with release/incident annotations, segment breakdowns (bar), funnel, distributions/heatmap, cohorts where needed; (4) Detail — "where to dig?": tables by campaign/category/segment, anomaly lists, exports. Levels must not mix (a KPI card at the bottom and a table on top break the eye's movement and decisions). Quality bar: the product state is readable from the top block in 5 seconds, the whole dashboard in 60. One panel = one thought: each panel answers exactly one question at its own level (Hero — large values; Diagnostics — line dynamics, breakdowns, funnels; Detail — tables); a chaotic "everything at once" grid without hierarchy is the main sign of a bad dashboard. Chart type per question: metric over time → line chart with release/incident annotations, no axis cropping; more/less across categories → bar chart sorted by value, axis from zero; where does the user path fail → funnel with steps in user language and a stated window; distributions/anomalies → histogram, heatmap (not "average across the hospital"); cohort behavior → cohort heatmap (arrival period × lifetime); parts of a whole → stack/shares with only 3–5 parts (avoid pie beyond that or with close values); plan vs fact → two lines/bars + difference with the comparison base stated. Reading someone's dashboard in 60 seconds: Intro (period, filters, data freshness — otherwise don't read on) → Hero (which metrics are red, deviation vs previous period) → Diagnostics for the deviated metric (annotated dynamics, breakdown; what changed before the metric — a leading signal) → Detail (which segment/category exactly; formulate one next check step). If steps 2–3 give no answer about "what's happening", the dashboard is assembled wrong, not "data is scarce". Chart rules: one question per chart with the right type; minimalism (clean axes, no 3D/shadows/decor); a unified palette across the dashboard — max 4–5 colors, gray for secondary series, red only for bad values, green only for good, color accent only where the message is; honest axes (bars always from zero; lines without amplitude-hiding crops, or an explicit note; same scale for comparable panels); labels: axis names, units (₽, %, pcs), period, granularity (day/week), legend when >1 series; annotations mandatory — releases, incidents, campaigns right on the dynamics line, otherwise the team hunts "causes" in the product when it was a competitor's release or an outage; filters (platform/segment/period) at Intro level acting dashboard-wide.

**How:** (1) define the dashboard's one main question and its consumer (who looks, how often, which decision); (2) pick metrics by the pyramid: 3–6 "product health" (Hero), drivers for diagnostics, detail tables — each metric with a passport (formula, units, period); (3) design top-down Intro → Hero → Diagnostics → Detail, checking each level answers its own question; (4) choose charts: one question per panel, correct type, unified palette, honest axes, labels and units; (5) add annotations of releases/promos/incidents and a filter system; (6) pass the "60-second test": an outside person names the product state and one suspicious spot; (7) agree the update frequency, freshness date and dashboard owner.

**Pitfalls:** a dashboard as a pretty picture with no decision and no consumer; no hierarchy — 20 charts of one grid, KPI at the bottom, the dashboard's question unclear; a cropped Y-axis on bars turns ±1% into drama (or hides a fall); a neutral series in bright red, a bad one in green — color stops carrying meaning; a metric without period/units; two charts with different scales compared "by eye"; no annotations — the team ties a dip to a feature when it was an incident or a campaign; unsorted bar charts (the most important not on top); overloaded unsorted tables without highlighted deviations; no filters — a new dashboard per question; no freshness date — decisions on stale data; a dashboard that explains but doesn't help act (no breakdowns, detail, export).
