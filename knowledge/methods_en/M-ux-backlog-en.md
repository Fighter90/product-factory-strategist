# UX Backlog, Knowledge Base and Big Picture (EN summary)

**When:** research volume has grown (or will) and knowledge is being lost, duplicated, going stale: a problem found in an interview or test must reach a solution without losing its evidence, then stay findable, revisable and — if disproved — **retractable**. Also for onboarding new people and preparing workshop material.

**Core:** three linked constructs. 1 **Atomic research** (D. Pidcock): knowledge stored as "atoms" — one insight per card; the chain: experiment ("we did this") → fact ("we saw this") → insight ("this made us think…") → conclusion ("therefore we'll do this"); a nugget = a short observation (what and why) + evidence (video, audio, photos, screenshots) + search tags (method, segment, business area, experience). 2 **UX backlog:** an open shared table of problems and insights answering "why this matters" (context, evidence, impact estimate), while the product backlog answers "what to do"; filled by researchers, designers, PMs, editors; watched by the business. 3 **Big picture:** a large board/file about the product for knowledge transfer, quick access and workshops: last-updated date, base research (drivers/barriers), team ownership zones, CJM, key CSAT/CES measures, workshop boards, notable external research, segments, useful links (dashboards, docs); risk — information overload and stale upkeep. 4 **UJM as storage:** the screen-level journey with steps → frustrations/obstacles/errors → metrics and description → suggestions → links to other teams' designs; shows problems strictly at specific screens. Storage comparison: backlog — easily filtered, anyone can edit; minus — not everyone remembers it, data entry is laborious. Big picture — visual and engaging; minus — overload and upkeep. Jira/Confluence — business-friendly and moves tasks; minus — not everyone has access, structure hard to change. Best combo: the backlog as "why", the tracker as "what to do". Record types define owners: UX problem (an interface deficit affecting task completion/speed/satisfaction — design), CX problem (outside the interface, e.g. pickup-point packaging — support/business), feature request (PM), bug (dev), look & feel (front-end + design system). Principle: **a card without a metric link is an opinion; card + metric is an argument.**

**How:** A. **Capture:** separate the layers — fact (observation/quote/number with timecode and link) → insight (the "why") → hypothesis (what to change and measure) → conclusion/decision; an insight without a fact link is not accepted; fill the atom fields and set status `raw`; add ≤3–4 tags across three planes: segment × journey stage (CJM) × problem type — more is "filter hell". B. **Weekly triage** (PM + UX lead + engineering): deduplicate on the fact+segment pair; assess impact, cost, evidence weight; set status `confirmed` or `needs-evidence`; score: `Score = (10 − Cost) × Impact × EvidenceWeight` (Impact 1–5, Cost 1–10, EvidenceWeight: 1 = one respondent, 2 = several, 3 = metric-confirmed; sprint-entry threshold ~70 in the course, calibrate per team); money alternative: `ROI = (ΔMetric × LTV × Users_affected) / DevCost` — ROI >1 → sprint, 0.3–1 → discuss, <0.3 → defer; every input number has a source and date; pre-measurement estimates are hypotheses; assign owner and type; create/link the tracker task with a mandatory research-link field. C. **Validate and close:** after release, compare the metric vs baseline in the same window and segment (e.g. 14 days before/after, statistical test); status `done` (metric reached) / `reopen` (not reached) / `dropped` (insight retracted). D. **Retractability:** never delete — change status and leave a trail: `superseded_by`, `invalidated_reason`, `invalidated_date`; every claim carries `evidence_ref` (link/file/timecode), `method`, `n`/sample, `date`, `segment`, `confidence` (low/medium/high), `source_type` (interview, test, analytics, observation, **team hypothesis**, **synthetic/AI**); expiry date — mark `stale` after the deadline or a major release and re-validate; conflicting data: both atoms stay, linked `conflicts_with`, the resolution recorded as a separate decision record; a refuted fact cascades `needs-revalidation` onto derived insights and hypotheses; never mix severity/frequency with confidence — "serious but weakly evidenced" is its own category. E. **Support rituals:** weekly digest of new records; quarterly dead-link cleanup and version review; 1–2×/year a stale-insight review; the "paint the red" workshop on the big picture (pick red zones, turn them into an action plan). Roles: the researcher updates statuses and files insights; the designer files interface problems; the PM mines ideas; the business tracks execution; everyone else reads. The lead researcher moderates the process and grows the big picture. Layered storage, each layer referencing the one below (report → transcript → video): raw data (audio, video, logs) → facts/codes → artifacts (CJM, prototypes, reports) → metrics (dashboards) → decisions (epics). Versioning: major = journey rebuild, minor = new pains/metrics, patch = wording edits; change date in the title/properties.

**Pitfalls:** insight without fact ("air", unprovable) → evidence field mandatory; 10+ tags (search noise) → ≤3–4 across the three planes; no owner or status (hanging records) → auto-filled author, weekly triage; duplicates (base bloat) → fact+segment check; card without a metric (opinion, not argument) → `metric_id` mandatory for prioritization; baselines from different windows (false win/loss) → a fixed before/after window; underestimated DevCost (inflated ROI) → post-mortem on actual hours; a file nobody uses (knowledge doesn't reach decisions) → rituals, research-link field in tasks, digest; CX and UX mixed (tasks routed to the wrong people) → type the records; old insights never retracted (decisions on stale data) → expiry dates, `stale` status, re-assessment.
