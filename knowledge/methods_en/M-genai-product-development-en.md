# GenAI Product Development (EN summary)

**When:** deciding whether to build GenAI/LLM into a product or process; planning such a project (timeline, budget, stages); choosing a model for a specific scenario. Key course insight: GenAI projects fail not because of models — models are plentiful — but because teams can't formulate the task, build a measurement, reach quality and close the economics.

**Core:** three forms of GenAI in a product (simplest to most valuable): a standalone GenAI product (wouldn't exist without the technology); a feature inside a product (speeds an existing scenario or opens a new way to solve a task); an internal process (the user never talks to the model but sees the result: moderation, card enrichment, routing, data extraction). Three autonomy modes — value and requirements grow on one scale: **Answers** (gives an answer, human decides; minimum requirement: quality), **Assists** (proposes, human accepts/edits; quality + economics), **Acts** (executes steps and changes data in systems; quality + economics + safety). What makes a GenAI product different from a classic one: the unit of work is a task, not an operation; an open-input interface bounded by instructions and checks; variable cost growing with usage; the product itself formulates statements the company is accountable for (a classic product only shows what was put into it). Hence three mandatory elements of any decision — **quality, economics, safety** — none skippable.

LLM basics that drive product decisions: a **token** is a text fragment (usually a subword); billing and speed are counted in tokens — a language the tokenizer handles poorly is "thicker" in tokens → more expensive and slower. Generation is autoregressive next-token prediction; sampling (temperature and related settings) makes answers diverse but **nondeterministic** — the same query can yield different answers.

The **context window** holds everything the model sees at a step: system prompt, tool descriptions, dialog history, retrieved documents, the user query, reserve for the answer — the user query is often the smallest part. Latency decomposes into TTFT (time to first token, grows with input length) and TPOT (time per generated token, grows under load): latency ≈ TTFT + TPOT × answer length; it can be hidden (streaming, cache, preloading), not removed. Cost per query ≈ input tokens × input price + output tokens × output price, times the number of calls; cached prefixes are cheaper. Training stages explain model defects: pretraining gives plausibility, not truth → hallucinations and stale knowledge; instruction fine-tuning → format and instruction-following; reinforcement learning → verbosity, sycophancy, false refusals, behavior shifts between versions.

**How:** (1) **Justification algorithm**: regulation test — describe the process in four questions (what must be done, where information comes from, how decisions are made, what a good result looks like); if it can't be described, the process isn't built or needs expert judgment — GenAI won't replace it. Choose technology by task: plain code for exactly describable rules; classic ML for closed-list outputs with labeled data and high volume (antifraud, ranking, forecast); GenAI for understanding or creating unstructured content. Check five viability criteria — any can be a stop factor: value (how many decisions/actions taken off humans), data (access, completeness, rights), expertise (who leads the project), economics (does the effect beat inference cost on a rough estimate), risk (acceptable error cost, explainable decisions). Scale check: fixed costs (measurement, control loop, operations) pay off only with volume — hundreds of queries/day is usually "sound idea, but the project is small"; tens of thousands is yes. (2) **Six-stage lifecycle**: problem statement (formulation, target business metric, GenAI justification, expected behavior) → data and knowledge (sources, rights, constraints; this is knowledge fed at query time, not a training set — clean stale and contradictory knowledge BEFORE build) → prototype (working solution without optimizations, on the strongest model, expensive and slow — only to remove quality uncertainty) → quality evaluation (analyze where the prototype errs; agree what a "good answer" is — one that moves the human toward solving the task; build a test set and a reproducible measurement) → tuning (raise quality via prompt, context, external knowledge, architecture; cut cost first with cache — doesn't change quality — then a smaller model and context compression — do change it → re-measure; build the control loop) → operations (live-traffic quality control; errors feed back into problem statement). Management consequences: you can't name a ready-date — only a hypothesis-check deadline; budget by stages, not in full; continue/iterate/close decided by measurement — closing before large spend is a success.

(3) **Model selection "criteria → matrix → cascade"**: five criteria with scenario weights — quality (share of acceptable answers on YOUR task), cost (price per 1k tokens in/out × volume), latency (TTFT/TPOT; moderation and inline suggestions can't wait seconds), privacy (can personal/sensitive data go to an external provider — or stay in your perimeter), stability (version control, degradations, determinism of critical parts). Matrix of four axes: modality (input→output); specialization (search/embedder, reranker, classifier-moderation, generative answer — the pipeline is almost always several models); architecture (encoder "read it all, issue a verdict" for classification/search/rerank/embeddings; decoder for generation; MoE and reasoning modes change price/speed at the same "size" — parameter count is a poor proxy); openness (closed API — usually stronger, but data goes to the vendor and no version control; open weights — own perimeter, fine-tuning, control, but own hosting and license care). Cascade fast→strong: small models (tens of ms, cheap) for classification, routing, first-pass filtering; medium for knowledge-base answers and summarization; large (seconds, expensive) for complex reasoning and multi-step scenarios; "unsolvable" verdicts are issued only on the strongest available model — otherwise two questions are mixed. Don't fine-tune until proven: the default is a ready model + instructions + knowledge in context; fine-tuning is justified for a stable narrow format/domain where the contextual approach can't reach quality with context squeezed — a fine-tuned small model can beat a large one on a narrow task (a cost-reduction path, not the first step).

**Pitfalls:** GenAI where code or classic ML suffices (more expensive, slower, needlessly nondeterministic); planning a ready-date before the experiment (quality attainability is unknown until tested on your data); optimizing cost before quality is confirmed; starting cost-cutting with "a smaller model" (changes quality → full re-measurement; start with cache); choosing a model by parameter count or leaderboard; sending personal/sensitive data to an external API (privacy criterion: own perimeter or masking before sending); concluding "task unsolvable" from a weak model; giving deterministic verdicts (reliability, tolerances) to the model — verdicts belong to rules, the model to phrasing and explanations.
