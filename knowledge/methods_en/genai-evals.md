# LLM evals: measure LLM feature quality before and after release

## When to apply
The LLM feature is designed ([[M-genai-feature-patterns]]) and possibly checked on a prototype ([[M-genai-prototyping]]) — you need a repeatable way to measure quality at every change (prompt, model, RAG, cascade) before release and on live traffic after release. The prototype answers "is the quality achievable at all"; evals are the permanent control loop: an LLM is nondeterministic and degrades unnoticed (API model version rotation, traffic drift). "I looked at a few answers — it got better" is not a measurement; without evals the feature is unmanageable.

## Essence

**The hierarchy of trust: human annotation > a calibrated LLM-as-judge > automatically computed proxies.**

1. **Golden set.** A fixed sample of real examples — random, not cleaned, with hard cases (missing data, contradictions, rare formats) and inadmissible cases (injection attempts, provocations). Hundreds, not a handful; the set version is pinned; it does not change between runs — otherwise comparing runs is meaningless.
2. **Regression run (regression suite).** Every change of prompt, model or architecture = a full run of the golden set with saved inputs, outputs and step histories; comparison with the previous run. A change without a regression run is degradation without witnesses.
3. **Human annotation.** People define what quality is; everything else is an approximation. Order: reading and free-text notes ("what is wrong" in your own words) → a yes/no checklist derived from the notes → binary "acceptable/not" with a threshold named before the run; for comparing versions — paired blind comparison ("did it get better"; the better of two may still be bad).
4. **LLM-as-judge.** A strong model scores the feature's answers against a rubric — it scales evaluation between human runs. Calibration is mandatory: on a sample with human annotation, compute agreement with humans; randomize order in paired comparisons; check the known biases — preference for long answers, self-preference (the judge prefers answers generated by the same model), position effects.
5. **Guardrails.** Checks at the input (injections, banned topics, format validation) and at the output (schema structure, banned content, fact-checking against product data). Inadmissible errors: zero in a run and a hard filter/refusal at runtime; verdicts with a high error cost go to rules, not the model.
6. **A/B against the old path (online check).** The old path vs the LLM feature on live traffic: the target metric + counter-metrics (complaints, manual edits, returns, refusal share). An LLM feature is not an improvement by default — it must win the measurement ([[M-ab-testing]]).
7. **Degradation monitoring.** Canary examples on live traffic; answer logging with sampled scoring (judge or human); alerts on a falling share of acceptable answers, rising refusals, cost and latency; user complaints and "thumbs down" are the source of new errors for the next version of the golden set.

## How to do it
1. Fix the verbal acceptance criterion ("a good answer = …"), the list of inadmissible errors and the threshold share of acceptable answers — all before the first run.
2. Assemble the golden set: a random sample of real inputs + hard cases + inadmissible cases; pin the version; do not change it between runs.
3. Build the regression run into the process: any change = a run + comparison with the previous one; break errors down by source (assembly / data / specification / model).
4. Set up annotation: a human reads the run's sample and fills the checklist; then calibrate LLM-as-judge against human annotation (agreement, order randomization, a self-preference test); the judge for intermediate runs, a human for release ones.
5. Build guardrails: inadmissible cases as a separate run; input and output filters; verdicts go to rules; refusal on missing data.
6. After release: A/B against the old path on the target metric and counter-metrics; monitoring (canary, logs, sampled scoring, alerts); feed new errors from logs and complaints into the next version of the golden set.

## Pitfalls
- **An uncalibrated judge.** The judge model is biased: long answers seem better, its own seem better, order within the pair matters. A judge without comparison to human annotation — you are optimizing the model's taste, not product quality.
- **Fitting the set and the threshold.** "Typical cases", data cleaning and a threshold named after viewing results inflate the score. Random sampling; threshold before the run.
- **One number without a breakdown.** "87% acceptable" does not say what to fix: you need the breakdown by checklist items and a classification of error sources.
- **Degradation after release.** Model version rotation and traffic drift change behavior unnoticed; without monitoring you learn about it from users. Canary + alerts + logs with sampled scoring are the mandatory minimum.
- **The cost and privacy of evals.** Running hundreds of examples on a strong model costs money — price the run; a judge makes annotation cheaper. Logging real conversations for scoring is personal data: masking, rights, retention periods. Guardrails do not replace measurement: a filter hides the symptom but does not fix generation.
