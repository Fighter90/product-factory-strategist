# MVP, MLP and Pilots (EN summary)

**When:** a prioritized solution hypothesis exists; choose the minimal validation format (prototype, pilot, MVP, MLP), assign metrics and success criteria before launch, then interpret the result honestly (scale / rework / kill).

**Core:** Format ladder: Prototype — check the idea, scenario, comprehensibility; a non-working mockup (Figma); the user knows it's a test (Discovery). Pilot — check base hypotheses the fastest, cheapest way: manual implementation, mailings, fake door, solution interviews, marketing; the user usually doesn't know, so behavior is real — the key difference from a prototype; key input metrics; typically 1 month (1–4 weeks online); after Discovery, before development: if base assumptions fail, no need to develop further. MVP — check the product/business on live users: a minimal working product closing a specific need the same way the final product will; real feedback — live behavior can differ critically from interviews and prototypes; scope via user story mapping, JTBD, Kano, RICE/ICE; after a successful pilot. MLP — make the product loved, check retention and NPS: working product + emotion/wow (MVP delivery: "brought the food"; MLP: order tracking, pushes, promos); after MVP, Growth stage. MVP types: single-feature (WhatsApp 2009 — statuses; chat appeared when users started talking through statuses), "Frankenstein" from ready parts (Groupon: WordPress + PDF + email), pre-order, concierge (a human manually, client knows), Wizard of Oz (a human manually, client doesn't know), someone else's product; MVP need not be IT (EdTech cases: thousands of landings instead of a course). Limits: MVP works poorly for revolutionary solutions and new niches (audience not ready, gives no data) and for super-standard products (go almost straight to final); inapplicable where you can't "under-build" (classifieds delivery example). The "right path" order: functionality → reliability → convenience → perfect design; not the reverse — value hypothesis first, then comfort, then beauty; if a launched product already pleases everyone, you're late. PM's goal at MVP stage: maximize awareness of user problems and needs, not control spec compliance. Eight creation steps: problem → segment → competitors → needs/USP/key hypotheses → CJM and user story mapping, feature selection → development and coordination → testing and iteration → decision about the product's future. Metrics: input (controllable: reach, share who saw/clicked/connected — primary on MVP/pilot, fast-changing, easier to control); output (results: conversion to purchase, revenue/AOV, retention, registrations — when testing monetization, LTV, retention, scale); qualitative/counter-metrics (CSAT, NPS, CSI, bugs, complaints, interview feedback — always, to understand causes of success/failure). The metric binds directly to the hypothesis: hypothesis about conversion → measure conversion, not "page openability". The traction model links input and output; funnel example (Trade-In): segment 10,000 → saw the button 3,000 (30%) → clicked 600 (20%) → filled the application 180 (30%) → deal 54 (30%); output metric = deals; for a pilot pick input values whose achievement tests the hypothesis — key results moving toward traction, not the whole backlog. Success criteria fixed before launch, e.g. ≥3% of buyers use Trade-In within 2 weeks, compared with an internal/industry benchmark (3% typical → target 5%). Testing discipline: the segment is chosen at preparation; start with the "core" where pain is sharpest — not on everyone; launch only when every feature without which the test is impossible is done and all approvals received (legal, security, finance, marketing); run as long as needed for statistical significance — end by data volume, not by date; account for purchase cycle (monthly purchases → longer), seasonality, external promos; log every change mid-test or the effect is unattributable; move from MVP through milestones, closing jobs whole. "Failing properly": failure is an investment in knowledge — fix steps, metrics, decisions, conclusions (retrospective); share learnings with the team and other products; localize the error (hypothesis, segment, implementation, timing); convert feedback into new hypotheses or a pivot.

**How:** (1) formulate the hypothesis: problem and segment → solution → expected metric change → success criterion → validation tool; (2) choose the cheapest format removing the main uncertainty: comprehensibility → prototype; demand → fake door/pilot/mailing; usability → usability test; monetization/behavior → MVP; emotion/retention → MLP; (3) select the pilot's base hypotheses (without which going further makes no sense): 1–3 hypotheses, each with the value tested, MDE and threshold, linked input → output, measurable within the pilot term; (4) define segment, channel, volume, duration, counter-metrics with thresholds, stop conditions; (5) fix plan and criteria (date, author), get approvals; (6) launch, keep the change log, watch counter-metrics; (7) analyze: funnel (where the drops are), comparison with criteria, assumption-by-assumption check, unexpected usage scenarios, qualitative feedback; (8) decide and record: success (metrics met, users return/recommend/pay → scale, automate), partial success (some thresholds met, bottleneck found → rework and retest, segment), failure (critical metrics missed → close or radically rethink, record causes); (9) transition gates: prototype → pilot (scenario clear, interest in interviews); pilot → MVP (first payers / minimal traction, no blockers); MVP → MLP (first fans, retention, reviews); MLP → scale.

**Pitfalls:** MVP not closing the key need or not communicating the USP; "the ideal product" instead of a minimum — or too few functions; no clear goal, metrics, criteria; thresholds "adjusted" after the test; launching "on everyone" (noise); stopping too early/late ("two days is enough"); only the final metric without process metrics; ignoring qualitative data; comparing against Big Tech mature-product benchmarks; not using MVP learnings, not collecting feedback, weak time control; applying MVP everywhere or nowhere; starting an MVP without prototyping; scaling on unconvincing results; explaining failure by external causes without data; missing critical participants (analyst, lawyers) so the test gets killed after start.
