# Platform Types and Platformization Criteria (EN summary)

**When:** "is there a platform opportunity here and what should it be?"; "when is a platform justified versus a shared service or local solutions?"; "what distinguishes a real platform product from a set of duplicate solutions?" Entry point to the platform track: before the ecosystem audit and before concept design.

**Core:** two meanings of "platform": an **ecosystem platform** organizes interaction between several participant groups; value arises in the exchange between them (marketplace, app platform, video platform: creators ↔ viewers ↔ advertisers) — framework: Parker, Van Alstyne, Choudary "Platform Revolution"; an **internal platform** gives teams a reusable core and rules to build their own solutions — its "clients" are internal teams. Taxonomy by value locus: **transactional** (ecosystem) — an exchange venue, the deal happens between participants under platform rules (marketplaces, ride and stay aggregators); **innovative** (ecosystem/technical) — a technology others build on (operating systems, messenger bot platforms, API platforms); **integrated** — both exchange and building on the core. Internal platform types: product (reputation, loyalty, promotion); product-tech (notifications, recommendations, verification); technical (APIs, data platforms, developer tooling); infrastructure (compute, storage, observability). Anatomy: **core** (shared data, shared logic, standard product) → **contracts** (APIs, formats, access rights — onboarding rules) → **customization** (settings and extensions within platform-provided limits) → client products. "Already a platform?" test: ≥2 independent clients; the core is separated from extensions (shared code is not edited per case); onboarding, versioning and support exist; the client builds on the core without the platform being reworked per scenario.

Ecosystem concepts: **network effect** — value for a participant grows with the number of participants on the other side (cross-side) or the same side (same-side); determines the launch strategy (which side to grow, and when). **Multi-homing** — a participant uses several platforms simultaneously; the lower the multi-homing costs (moving content, data, habit), the weaker the scale advantage — and the clearer where a challenger can catch up. **Curability** — the platform must govern interaction quality (rules, verification, ratings), otherwise a low-quality flow kills value for the other side; curation is the instrument of liquidity management.

**Four platformization criteria**: (1) scale and repeatability — several teams need it now or in the near plan; the scenario is regular; a stable core can be extracted without hurting teams' goals; (2) economics: `Cost(N × LOCAL) > Cost(CORE + N × INTEGRATION)` where LOCAL includes each team's build, support, fixes and integrations; the platform includes core, onboarding, compatibility and migrations; (3) standardization without losing speed — unified entities, rules and quality guarantees in the core; adaptations keep scenario differences and team pace; (4) client readiness — the value solves the client's problem (not just the company's savings); migration cost counted (integration + data transfer + process change); a sponsor and an owner exist; the onboarding contract defines limits, SLA, responsibility, settings. Illustrative economics: a task needed by 5 teams; local: 2-month build per team (5 × 2 = 10) + repeated rework 20 × 2 days ≈ 2 months + support 5 × 0.2 ≈ 1 month = 13 FTE-months; platform: core 3 + integrations 3 + client migration/launches 5 = 11 FTE-months in year one — closes already in year one; with 6+ clients and zero rework the gap grows. With 2 clients and half-divergent scenarios "keep local" or "shared service" would win — the conclusion is sensitive to client count and divergence depth; compute over a range.

**How:** 1) classify the situation: ecosystem or internal platform; if internal — which of the four types; this sets success metrics (liquidity and side adoption vs team speed and reuse); 2) collect signals that local solutions are exhausted (≥3 is a strong argument): several teams independently build the same function; similar scenarios work by different rules; UX diverges across verticals; supporting local solutions eats ever more time; every connection is done manually; tech debt accumulates; 3) choose one of four options — not everything is "build a platform": **keep local** (one team, unique scenario, repetition unproven); **shared service** (extract the function with an API, no platform model — plans, contracts, support); **minimal platformization** (extract a small common core, leave the rest to teams); **build the platform** (a separate product for several clients with a development plan, contracts, support); 4) run the four criteria;

5) check yourself against the anti-patterns: platform for platform's sake (architecture before the shared problem is confirmed); too-wide core (all possible clients' requirements pre-included); migration without value (moving teams without improving their speed and metrics); universality at any cost (the shared solution breaks important scenario differences); sequence: local MVP and proven repeatability first, then core and contracts; 6) choose the level of generalization — the same capability can be measured at different scales (private feature → function → domain); run the four criteria at each level; platformize the level where all four close; 7) formulate pros/cons for the defense: main changes for the business (less duplication, unified UX and rules, economies of scale, faster onboarding of the next teams, lower operating costs) versus risks (unproven demand, costly migration, overly divergent scenarios, no sponsor, onboarding slows clients down).

**Pitfalls:** calling shared code with one real client and no stable contracts a platform; platformizing before value is confirmed on a local MVP (typical failure: a premature shared reputation/scoring platform — dependencies, migrations and timelines grow before the demand signal); counting only reuse benefits while ignoring support, compatibility and migration — platform economics don't close immediately; building an architectural "space shuttle" that can do everything but onboarding requires understanding the whole model; ignoring client readiness — "company savings" don't motivate the client team bearing the migration cost.
