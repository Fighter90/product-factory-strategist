# Usability Testing (EN summary)

**When:** checking with real people whether an interface or scenario is understandable, and seeing where and why people err — before development (on a prototype) or after launch. A UX test answers "how" and "why", not "what changes in the metric": a button color or page variant chosen for conversion can only be settled by an experiment (A/B); a UX test gives hypotheses and causes.

**Core — formats:** moderated test (qualitative): the researcher watches the participant solve realistic tasks and probes "why"; for new, complex, branching, first concepts; gives emotions and mental model; downsides — observer effect, social desirability, cost. Unmoderated (quantitative "what/how much"): the participant follows a link; the platform logs clicks, time, answers; fast, cheap, scalable; can't probe; a flawed task ruins all data; no context. RITE: after 2–3 sessions a critical problem is fixed immediately and later participants see the new version; prototypes only, designer engaged. Field/contextual format when the environment is critical (a courier in motion, bad signal, sun on screen). Heuristics (in-team, no users) as a fast pre-filter. **Method by goal:** will users notice a block / understand its value → moderated; why do they abandon mid-process (stats known, cause unknown) → moderated (analytics says where, the test says why); real conditions → field moderated / contextual interview; term comprehension → interpretation test; is an element noticeable/findable → first click / 5-second test; which of 2–3 variants is preferred → preference test (subjective; behavior only via A/B); how people group sections → card sorting (open/closed) and tree testing; a simple linear 2–5-screen scenario → scenario-based unmoderated; quick prototype feedback → RITE, micro-checks (5–10 min); conversion impact → A/B only.

A prototype is a way to fail cheaply, not a presentation: clickable screens, connected transitions, all scenario states (error, empty, loading, success); fidelity by goal (understanding — static frames; flow — a clickable path); task rule "3-S": one path, short task, concrete goal; backup PNG slides of all states, incognito link check, a dry run with a colleague. **Moderated session:** brief (question, decision at stake, flow, segments) → hypotheses (≤3 per session; format: problem + place in scenario + expected observable behavior — "notices the filters button in the first 5 s", "chooses the pickup point in ≤20 s without backtracking"; one hypothesis = one task) → guide (intro interview → task wording → success criteria measurable and set before the test → probe questions → closing) → task wording: context + motive + constraints; the goal contains no interface-element names ("click Checkout" is forbidden); identical text for all; don't invent or drop context → recruiting: segment and behavioral profile, right device, exclude UX/IT professionals unless they're the audience, +20% no-show buffer, recording consent; sample 5 per segment (Nielsen ≈80% of problems), 5–8 for a first test of a complex interface, more for 10–15-screen scenarios or several segments → pilot on a colleague → session structure: welcome and role ("we test the product, not you") 2–3 min → process and recording 1 min → intro interview 3–5 min → tasks with think-aloud → SEQ difficulty rating + "what would you change first". **Moderator behavior (~10 rules):** talk ~20% of the time; no hints; no leading questions; hold a ~5-second pause after an action; ask for think-aloud; neutral face and voice; never justify the interface ("it's by design" is a hint); manage the pace; don't cut off final impressions (the last emotions are the most valuable); always record. Probing without hinting: "what did you expect to see?", "what would help here?", "what other options come to mind?"; questions about a **specific UI element only if the participant mentioned it**; third-person questions ("how would others act?") reduce social desirability; a broken prototype → show the PNG, ask "what would you do next?", mark as a technical failure. Probe techniques: soft echo, a chain of short "why" questions, looping back to earlier words, guilt removal ("this spot confuses many people"), emotion mirroring. Non-verbal friction signals (record as observation, not cause): leaning toward the screen, a cursor hovering long in one place, a nervous smile, glances at the moderator. Notes in the moment: `time | step | action/quote | mark (red fail, yellow friction, green wow) | severity`. Same-day analysis: timecoded matrix → group identical problems → patterns (≥2 participants — a candidate, 3 — a regularity) → cause → business effect. Decision: (A) iterate if critical problems; (B) proceed to development if hypotheses confirmed and errors minimal; (C) rebuild the scenario if the concept/mental model mismatches; retest with date and owner assigned. Four risk zones and defenses: lab-ness (field or simulated pressure: time, noise, parallel tasks); prototype failure (atomic paths, per-link checks, PNG backup); social desirability (the "interface, not you" framing; third-person questions); observer effect (remote session, moderator silent ~80%).

**Unmoderated methods:** interpretation test (share of correct readings from coded open answers; ask "what does … mean", not "what does the button do"); first click (success = first click in the target zone, time to click, misses; no element names in the task; compute significance when comparing screens); 5-second test (recall, message understood, CTA remembered; don't warn about memorization; ≤3–5 questions; 10–20 s for complex screens); preference side-by-side (variants differing in one noticeable detail; one criterion; random order; 2–3 variants; result ≠ behavior); card sorting open/closed/reverse tree test (matrix of similarity, dendrogram; 200–300 respondents for mass audiences); scenario-based (success, time, dropout, subjective ease; the more branching, the more moderation helps). Common hygiene: greeting and context, task, thank-you screen, audience and quotas; a **honeypot/control question** and minimum completion time to filter inattentive respondents; branch and display logic; significance test (chi-square / z-test for shares) before conclusions; "working number" ≈300 responses for mass segments. Course thresholds (calibrate per product): interpretation ≥80% correct; first click ≥80% and ≤2 s (≤60% — poorly noticeable); 5-second ≥70% named the product; preference — a difference >10pp at p ≤ 0.05 is decisive, <5pp is a tie.

**Metrics and reporting:** task success (0 failed / 1 with errors / 2 first try; Success Rate = completed / valid participants); time on task (median over valid — the mean is distorted by outliers; steps, backtracks, wrong attempts); subjective difficulty (SEQ, 7 points; expected-vs-actual gap); SUS 0–100 after the session. Validity: exclude records faster than the minimum time or failing the honeypot; report n; set targets (success ≥80%, SEQ ≥5, median ≤60 s) before launch. **Severity**: 0 cosmetic; 1 slows but doesn't break; 2 friction (a noticeable share on a wrong path, ~30% of clicks); 3 blocks some users (~50% miss the target action); 4 blocks task/revenue/release; prioritize severity ≥3 or frequency ≥50% first; `Severity = impact × frequency × business risk` (normalized 0–4). Replicability: the same guide, identical task wording and order for all participants — otherwise version comparisons are meaningless. One-slide report: feature and test goal → metrics fact vs target (with n) → top problems (severity ≥3) with participant counts and a quote with timecode → fixes, owner, deadline → retest date; executive summary 5–7 problems; every claim tied to an observation, quote or metric.

**How:** brief → hypotheses → recruit → build the prototype → pilot → run sessions with think-aloud → record with timecodes and severity → same-day analysis and prioritization → decide (iterate / proceed / rebuild) → retest after fixes; for unmoderated: platform setup with honeypot, quotas and branching, then significance-tested analysis and the one-slide report.

**Pitfalls:** hints and leading questions ("what about via search?") distorting behavior; element names in tasks (tests reading, not findability); asking about elements the participant never mentioned (imposing); conclusions from words only — words + actions + metrics; not recording or probing causes (conclusions unprovable); too many hypotheses/tasks (fatigue — ≤3 scenarios, ≤45 min); no honeypot in an unmoderated test (bots and the inattentive ruin data); a preference test with similar variants and no significance (false winner); testing on colleagues (real barriers invisible); equating a UX-test result with a conversion effect (confirm by experiment); a 30-slide report with no owner and no retest date (no decisions made).
