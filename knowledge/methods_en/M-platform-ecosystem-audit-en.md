# Product Ecosystem Audit for Platform Opportunities (EN summary)

**When:** "where and why in our product portfolio should we build a platform?", "which functions are duplicated across teams and is there a common core?", "what to propose for platformization and how to justify it to stakeholders?" — the first step of the platform track after the basic concepts.

**Core:** The audit answers three questions: where to build a platform, why a platform (and not another solution), and why stakeholders will "buy" it. Start from the problem, not the solution: wrong — "let's create platform X" with architecture designed before the problem and the core's composition; right — several teams solve a similar task in different ways, there is a confirmed client/stakeholder problem, and only then is the form of a shared solution chosen. Four sources of opportunity, found in regular work: (1) product expansion — a mechanic is carried into a new scenario or vertical; (2) shared CJM — similar journey steps are built differently in different places of the product; (3) team requests — several teams ask for similar capabilities; (4) identical changes — the same change repeats across several products (e.g. a monetization-model migration across all directions). Four lenses on a product domain: scenarios → interfaces → implementations → clients. Scenarios — what the user does (offer card view, purchase trust, profile, communication, transaction). Interfaces — where the scenario is implemented (main page, vertical homepages, account, cart). Implementations — what is shared and what differs (common logic and elements vs different fields, conditions, behavior). Clients — who owns the current solutions and who uses them. If implementations contain material for something common (a core) plus differences clients will customize themselves — that's a platformization candidate. Also fix the contracts and rules that already de-facto exist around the common: data formats, serving rules, access rights. If shared rules exist informally ("we agreed so"), that confirms the common core is genuinely in demand — and needs an owner.

**How:** (1) pick a domain and list 3–5 user scenarios in it (user scenarios, not features); (2) fill the scenario map for each: where it occurs in the product → implementation examples across verticals/places → common and differences, splitting (a) what is identical and standardizable — core material, (b) what differs meaningfully and will be customized by clients — customization material, (c) what is unknown — marked as hypothesis, never silently erased; (3) fix owners: each current solution's owning team and user teams; platform-client candidates = owners of similar solutions + teams without a solution who will need one soon; (4) build a shortlist of 2–3 candidates: what repeats, what clients customize, who owns the core, who the clients are; (5) run platformization criteria per candidate: scale, repeatability and common core, economics N × LOCAL > CORE + N × INTEGRATION, standardization, client readiness; (6) check alternatives and explain why a simpler solution won't do: keep local; agree on rules without shared code; build a library/design components; build a service or API; extract a minimal core; (7) assess stakeholder adoption: the candidate must have value for the owner, the clients and the sponsor — otherwise the audit isn't finished; (8) frame the outcome as a hypothesis: the platform will have users and justified economics — verified by an MVP and calculation after the audit; until then these are hypotheses, not facts. Illustrative scenario breakdown — "purchase trust" (a trust badge on the offer card): where it occurs — offer card, vertical main page, results listing; common — the visual element, the details popup on click, the design code, mandatory attributes (image, title, text, button), the issuance fact and history; different — texts and images, the button's action, issuance conditions, extra attributes (award year); conclusion: element, popup and design code go to the core; texts, issuance conditions and extra attributes go to customization; since differences are meaningful, the core should be narrow with settings, not a "universal badge". Typical audit domains to start scanning: user profile (incl. public profile), offer viewing (cards, listing, recommendations), participant rating (ratings, reviews, complaints), communication (notifications, messenger, calls), transactional purchase (payment, delivery, statuses); the same scenario map per domain keeps candidates comparable. Auto-checks: every map row marks fact vs hypothesis and evidence class; "owner" filled for all current implementations; "clients" include non-vertical teams (support, marketing too); each candidate has a named alternative and the reason for rejecting it; enough signals (≥3) from the criteria card — otherwise the audit found "the common" but didn't show that local solutions are exhausted.

**Pitfalls:** starting with "let's build platform X" and fitting the problem to the architecture; confusing feature and scenario — an audit over a feature list doesn't find the common core of the user journey; reading implementation differences as "everyone does it differently, so we need one wide universal standard" — differences can be meaningful and stay in customizations; counting only product verticals and missing horizontal clients (support, marketing, analytics); not marking gaps — "unknown" in the map must stay visible and go into the validation plan, not be erased when the document is re-formatted; unmarked unknowns — a map without "hypothesis" flags turns assumptions into "facts" at the defense.
