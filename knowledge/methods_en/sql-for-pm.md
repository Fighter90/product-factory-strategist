# SQL for Product Analytics (EN summary)

**When:** checking a hypothesis on data yourself: where the funnel leaks, how cohorts behave, what ARPU/ARPPU and frequency are, why a metric fell. A fast own query instead of a ticket to the analyst — plus a data-quality check before any calculation.

**Core — basic principles:** every product metric is an aggregate (`COUNT`, `SUM`, `AVG` + `GROUP BY`); every hypothesis is a filter (`WHERE` before aggregation, `HAVING` — a filter on the aggregate after `GROUP BY`); everything not aggregated must be in `GROUP BY`; `COUNT(DISTINCT …)` for users/orders (deduplication); `NULL` forms its own `GROUP BY` group and is ignored by aggregates (`SUM` doesn't fail on NULL rows; division by zero is handled with `NULLIF`). Aggregation over aggregation (subquery/CTE): first orders per user, then the average per region — that's how compound metrics like "retention by cohort and region" are built. Safety: work on read-only replicas/data marts, don't run heavy queries on the production database, `LIMIT` during exploration, never publish credentials.

**Typical queries:** DAU/WAU/MAU: `SELECT DATE(ts) AS day, COUNT(DISTINCT customer_id) AS dau FROM orders GROUP BY day` (WAU via `DATE_TRUNC('week', …)`, MAU via 'month'). **Funnel** (unique users per step): `COUNT(DISTINCT CASE WHEN event_type = 'registration' THEN user_id END)` per step; step CR = step(n)/step(n−1); through conversion = last step / first; the difference between steps is the "drop"; for an honest funnel add a sequence window — a step counts only if the user reached it after the previous one. **Cohort retention**: CTE `first_orders` (`MIN(DATE(ts))` per customer) joined to activity days; `retention_rate = 100.0 × COUNT(DISTINCT active) / COUNT(DISTINCT cohort)`; for D7 filter `activity_day = first_day + INTERVAL '7 days'`; the result is a cohort matrix; day zero (the first event) must be defined unambiguously — shifting it inflates retention. **Revenue, average check, ARPU/ARPPU**: `SUM(price × quantity)` as revenue; `avg_check = revenue / COUNT(DISTINCT order_id)` (many items per order → deduplicate the order when dividing); ARPU = period revenue / distinct **active** users; ARPPU = period revenue / distinct **paying** users — numerator and denominator must share the period and cohort. **Repeat rate and frequency**: share of clients with >1 order; orders per client per day of their "life" (`COUNT / (DATE_PART('day', MAX(ts) − MIN(ts)) + 1)`); Frequency + Recency + Monetary (sum) = the basis of RFM segmentation (`CASE WHEN` on thresholds → New/Active/Loyal). **Metric-drop diagnostics**: cuts by region/category/platform for two periods with comparison, then narrowing to the segment where the drop concentrates; YoY check for seasonality.

**JOIN and UNION:** INNER JOIN — matches only; LEFT JOIN — all left rows plus matches (NULL where absent): the standard "orders + deliveries", "users + actions"; FULL JOIN — everything from both sides (reconciling systems). After a LEFT JOIN the right table can duplicate left rows (a 1:N relationship, order → items): count aggregates on the left table before or after consciously — duplication distorts sums. UNION ALL glues fast and keeps duplicates; UNION dedupes (slower) — typical use: gluing periods/sources of identical structure. A range join condition (`BETWEEN first_day AND first_day + INTERVAL '7 days'`) is the basis of retention calculations. **CTE** (`WITH … AS`): a named subquery inside one SELECT — makes big queries readable, allows reuse (e.g. `first_orders`), simplifies stepwise debugging, replaces temp tables; lives only inside one query, must be declared before use, doesn't speed execution by itself (the optimizer may evaluate it repeatedly — materialize heavy cases into a table). **Window functions** compute an aggregate over a group of rows **without collapsing them** and attach the value to each row: `fn() OVER (PARTITION BY key ORDER BY column)` — PARTITION BY defines independent groups (user/region), ORDER BY the order within the group (almost always required; without PARTITION BY the window is the whole table). `ROW_NUMBER()` — unique row number in the window: numbering a client's orders, deduplication (`WHERE rn = 1`), first/last event. `RANK()` / `DENSE_RANK()` — ranking with ties: RANK skips numbers (1,2,2,4), DENSE_RANK doesn't (1,2,2,3); tops by revenue/category. `LAG(col,1)` / `LEAD(col,1)` — previous/next value in the window: intervals between orders, delta to the previous period, funnel sequence checks (`ts − LAG(ts) OVER (PARTITION BY customer_id ORDER BY ts)` = days between orders). Typical tasks: ranking, event sequences, neighbor comparisons, cumulative metrics, cohort analysis.

**Data-quality checklist before calculating:** 1) completeness — DWH sources recalculated, no date gaps, data freshness known (up to which date events exist at all); 2) duplicates — no doubled rows for a day (a sharp "growth and rollback" on the chart is almost always a duplicate, not user behavior); `COUNT(*)` vs `COUNT(DISTINCT id)`; 3) definitions — cohort day zero, funnel window, what counts as "activity" and "payment" fixed and matching the metric passport; events not renamed; 4) segments and filters — test users/internal accounts excluded; platform/region filters applied consciously; 5) types and NULL — dates are dates (not strings); division protected with `NULLIF(..., 0)`; return shares via `CASE WHEN flag THEN 1 ELSE 0 END`; 6) relationships — row count didn't "explode" after a JOIN (1:N); the LEFT JOIN didn't silently lose control users; 7) sanity check — one day's metric recomputed by hand; totals reconciled with the dashboard or a known fact.

**How:** 1) phrase the question in metric, period and segment terms (the metric passport); 2) run the data-quality checklist; 3) start with exploration: table structure, `LIMIT`, row counts; then CTEs step by step (first event → activity → aggregate); 4) compute base aggregates (DAU/revenue/funnel), then complicate: cohorts, ratio metrics, window functions; 5) make cuts (segment/period/platform), compare periods, check seasonality against last year; 6) recompute a control point by hand — only then conclude or hand the result off (to a dashboard, an A/B analysis, or the traction model).

**Pitfalls:** `WHERE` and `HAVING` confused; non-aggregated columns forgotten in `GROUP BY`; a 1:N JOIN doubling revenue/users; a LEFT JOIN silently becoming INNER because of a right-table filter in `WHERE`; UNION vs UNION ALL misuse (hidden duplicates or lost ones); NULL handling (SUM ignores NULL but `COUNT(col) ≠ COUNT(*)`; division without `NULLIF`); a shifted cohort day zero or a floating funnel window — retention "improves" by redefinition, not by the product; comparing through with step conversion; ARPU computed over everyone while ARPPU over actives; a heavy query on the production base; no `LIMIT` during exploration; "growth and rollback" taken as user behavior without checking duplicates.
