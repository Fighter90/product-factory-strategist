# GenAI Prototype: Design, Build, Test (EN summary)

**When:** the solution is designed and the key question is whether the needed quality is achievable on your data — checked in days, not weeks — then decide: develop, iterate, or close. A prototype is a source of knowledge about the task, not product v1: "the competitor makes it work" proves nothing — different data, load, audience.

**Core:** Four jobs of a prototype, one decisive: the solution image (partially replaceable by a mockup); value (checked by interviews and behavior analytics — a prototype gives signals, not statistics); quality achievability — checkable by nothing but a prototype; cost order (not a budget figure: optimizations push cost down, long dialogs and repeat visits push it up). Requirements making results trustworthy: validity — sample random from real data, strongest available model; interpretability — visible which cases failed and why; speed — days, deadline named before start; cost of the check a fraction of build cost. Typical failure: three weeks on 15 hand-picked examples and a "we can ship" verdict — violates three of four requirements. Scope: the main scenario whole (the product is made for it); real uncleaned data (cleaning inflates results); typical and hard cases; strongest model (separates "unsolvable" from "weak model"); simple build tool; no speed, error-handling or code-quality optimizations; run outputs saved — otherwise versions aren't comparable. Tools differ by what must be done for a result: chat with a model (probe the prompt, can the model cope at all); sandbox/console (system prompt and parameters separate, tool declarations, code export — won't execute the function itself); assistant builder (persistent instruction + own files, internal helper; can't be embedded into your product); app generator (solution image and live-user checks, but sample runs built separately); visual workflow platform (block workflow, per-element sample runs with per-step history — exactly what achievability testing needs); code (everything possible, edits via a developer). Choice criteria: is a sample run needed, own interface, learning speed, who on the team can build it. Problem statement (written before building): 01 Input — trigger, data, user query; 02 Output — format (human-readable text / structured for UI) and mandatory elements of every answer — the basis of the acceptance criterion; 03 Data sources — what the system reads besides the input; 04 Behavior rules — what it never asserts, what it does with missing data (say so or refuse), what it won't discuss without clarification; 05 Acceptance criterion — verbal description of an acceptable answer, who accepts (PM + experts), what counts as failure. Statement trap: describing form, not substance — "there is a recommendation" is satisfied literally and uselessly ("take the first one" without rationale); word requirements so they cannot be met meaninglessly ("the recommendation rests on differences named in the answer, each claim backed by listing data, no invented facts"). Minimal build: base scheme trigger → model call (system prompt + input) → answer; a scenario adds input validation, a second call or field-by-field response; sample runs must be built into the tool mechanics (data passed as a list of items — each node processes each item, no loop-writing; prompts assembled from table-field expressions); roles even in a 3–4 person group: builder (workflow, screen), prompt author, tester (brings diverse examples, spots bad answers), reporter; build errors show immediately (crash/silence), quality errors only on diverse examples; run hygiene: a single element's failure doesn't stop the run ("continue" error handling); run history stores input/output of each node; answers written back into the sample's run-column, evaluation into a neighboring eval-column; sample unchanged between measurements. Testing algorithm: (1) scenarios from the statement — main scenario and hard cases (missing data, contradictory data, incomparable pairs) are the test situations; (2) golden set — fixed sample of real examples (hundreds, not units), random, uncleaned, with hard cases; stored and unchanged between runs; (3) regression run — full processing of the golden set by the current version; answers and step history saved; any prompt/model/architecture edit = rerun the same set; (4) quality labeling — read first, count later: free-text notes first (on the first 20–30 answers, in your own words: "invented a nonexistent attribute", not "bad"); then a checklist (yes/no items taken from the notes: differences backed by data? recommendation rests on differences? no invented facts? — shows what to fix, not one number); binary acceptable/not-acceptable labeling (when the acceptance criterion is formulated; threshold named before the run — a share chosen after viewing = fitting); blind pairwise comparison ("is it better" vs current experience or previous version; the better of two can still be bad); (5) metrics of three kinds: quality (share acceptable by binary labeling + checklist breakdown + zero disallowed errors), cost (price per answer by in/out tokens and call count; check whether the cheapest model converges at the same volume), latency (response time on the sample, TTFT/TPOT); (6) root-cause every bad error, cheapest checks first: did the data reach the model? (run history → fix the build: expressions, field parsing); is the answer in the data at all? (→ data: missing-data rule, external source); does the prompt literally ask for what the user needs? (→ statement: requirements, hard-case rules); everything fine but the answer bad (→ model: simplify/split the task, example of a good answer, verification step, stronger model). Frequent traps: rewriting the prompt when the model simply didn't get the data; demanding an answer that isn't in the data (it will be invented); changing the model when the prompt is executed literally; declaring the task unsolvable from a weak model. (7) Decide the prototype's fate: acceptance met (share acceptable ≥ threshold, zero disallowed errors) → develop (build with the learnings; remaining errors handed over as known risks); fixable errors (build, data, statement) → iterate (plan: what we change / how we check / when we stop — one error source per iteration, same run on the same sample, threshold and iteration limit named before the first run); only model errors, verified on the strongest model and with changed architecture → close (record why; a completed answer about achievability obtained in weeks, not a failure). Economics decides independently of quality: if even on the cheapest model an answer costs more than the product is willing to pay — close; if it fits, tuning lowers the price but doesn't change the decision; never raise the threshold after the run.

**How:** (1) write the problem statement (trigger, input, output format + mandatory elements, sources, behavior rules, verbal acceptance criterion, who accepts, what counts as failure, deadline in days) before building; (2) assemble minimally per the base scheme with a sample-run built into the tool mechanics; (3) test by the algorithm: scenarios → golden set → regression run → labeling (notes → checklist → binary → pairwise) → metrics (quality, cost, latency) → root-cause each bad error by the four-question ladder → decide develop / iterate / close with the acceptance threshold and iteration limits named before the first run.

**Pitfalls:** the prototype dragged into production ("three weeks of work" with hacks — the prototype is discarded; development starts from the learnings); hand-picked "pretty" examples (results untrustworthy — random sample from real data); cleaning data before the run (inflates results; production data will be dirty); "works at the competitor" as proof (other data, load, audience — own prototype on own data); computing the metric before reading answers (you measure what's easy, not what breaks — notes → checklist → binary); acceptance threshold set after viewing results (fitting); a single "82 of 100 acceptable" figure (says nothing about what to fix — checklist breakdown + error-source classification); fixing everything at once (one error source per iteration, same run); polishing the prototype beyond the acceptance threshold "to ideal" (prompt tuning doesn't transfer to the product — different architecture); an "unsolvable" verdict from a budget model (infeasibility verdicts only on the strongest model).
